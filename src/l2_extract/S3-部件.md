## 1. 先把关系讲清楚

### 1.1 一次真实的失败长什么样

目标产品是 `qemu_arm_linux_min`，构建时发生的是这样一条链：

```text
产品配置 config.json:28
  { "subsystem": "hiviewdfx", "components": [{ "component": "hilog" }] }
        │
        ▼  按名字找 hilog 的 bundle.json
  找到，读 bundle.json:23 的 deps.components：
  ["bounds_checking_function", "c_utils", "ffrt", "init", "napi", "zlib", "runtime_core"]
        │
        ▼  再按名字找这 7 个部件的 bundle.json
  任何一个找不到
        │
        ▼
  OHOS component : (xxx) not found        ← 这就是 BUILD-003
```

S3 做的事，就是**在构建开始之前把这条链走一遍**：把「产品选中的部件」和「这些部件又依赖的部件」全部收集起来，逐个看源码树里有没有对应的 `bundle.json`。

它不看代码、不编译、不联网——只读 JSON 里的名字和依赖。

### 1.2 子系统、部件、模块、产品：谁是谁

用上例画出来：

```text
产品 qemu_arm_linux_min
└── 子系统 hiviewdfx                        ← 只是分组 / 命名空间
    └── 部件 hilog                          ← 产品选择与依赖声明的单位
        ├── 模块 //base/…/services/hilogd:hilogd              ← 真正被编译的东西
        ├── 模块 //base/…/interfaces/native/innerkits:libhilog
        └── 依赖部件 c_utils、init、zlib、ffrt…               ← 部件级依赖
```

四条关系，逐条对应真实文件：

| 关系                           | 事实                                                          | 证据                  | 意义                 |
| ------------------------------ | ------------------------------------------------------------- | --------------------- | -------------------- |
| 产品 **包含** 子系统实例 | 产品配置有 `subsystems[]`，每项 = 「某子系统 + 它要的部件」 | `config.json:12`    | 产品按子系统组织清单 |
| 子系统实例 **包含** 部件 | `subsystems[].components[].component`                       | `config.json:28`    | 产品只选到部件       |
| 部件 **属于** 一个子系统 | `bundle.json` 的 `component.subsystem`                    | `bundle.json:14`    | 部件自带归属         |
| 部件 **依赖** 部件       | `component.deps.components`                                 | `bundle.json:23`    | 闭包的边             |
| 部件 **产出** 模块       | `component.build.sub_component` / `inner_kits`            | `bundle.json:38-51` | 部件展开成构建目标   |
| 模块 **依赖** 模块       | `BUILD.gn` 的 `deps` / `public_deps`                    | 不在 S3 范围          | 由 GN 自己解决       |
| 仓 **包含** 部件         | 一个仓可以有多个 `bundle.json`                              | 3.2 检出有 4 个       | 仓 ≠ 部件           |
| 产品 **不引用** 模块     | 产品配置里没有任何 `//path:target`                          | 实测                  | 产品到部件为止       |

三个容易混的点：

1. **子系统不是提取单位。** 它只是分组和命名空间，没有 `bundle.json`、没有依赖、「子系统找不到」这种错误不存在。
2. **模块不是提取单位。** 原因见 1.3。
3. **部件名不是包名。** 部件叫 `hilog`，包名是 `@ohos/hilog`（`bundle.json` 顶层的 `name`）。产品配置引用的是前者。详见 §2.1。

### 1.3 为什么提取部件，而不是仓或模块

| 候选单位                 | 粒度           | 用不用       | 理由                                                                                                                         |
| ------------------------ | -------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 仓 repo                  | 太粗           | 不用         | 一个仓可以有 4 个部件（`hiviewdfx_hilog` 的 3.2 检出）。「仓在」不等于「产品要的那个部件在」；仓目录名和部件名也不一一对应 |
| **部件 component** | **正好** | **用** | 产品只选到这一层；构建报错也停在这一层；树里有明确的清单文件（`bundle.json` / `ohos.build`）                             |
| 模块 module              | 太细           | 不用         | 数量是部件的 10–50 倍；判断「模块在不在」要解析 GN、还要看工具链和目标平台——那是 S1/S2/S4 的事；产品配置根本不引用模块    |

再补三条硬理由：

1. **可判定**：部件的「有 / 没有」是纯 JSON 集合问题；模块的「能不能编」需要环境。
2. **稳定**：部件名跨仓跨版本稳定（`hilog` 在 3.2 / 4.0 / 6.1 都叫 `hilog`）；模块路径会随目录调整。
3. **可指认**：部件缺失能直接指到产品配置的哪一行；模块缺失往往要追很多层 GN。

### 1.4 提取的到底是什么：一份采购单 + 每件货的说明书

打个比方：

- **产品配置** = 采购单。人写的：「这个产品要 `hilog`、`init`、`hitrace`…」。
- **`bundle.json`** = 每件货的说明书。部件作者写的：「`hilog` 这个部件，自己还需要 `c_utils`、`zlib`…」。
- **验证** = 拿着采购单，把每件货的说明书也翻出来，把「直接买的」和「说明书里提到的配件」合成一张总清单，再去仓库逐个对货。

所以提取的不是代码，是三类信息、四条记录：

| 类别               | 含义                             | 从哪读                                                                                                   | 真实例子                                    | 记录类型                     |
| ------------------ | -------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ---------------------------- |
| **定义**     | 树中已声明的部件（含所属子系统） | `bundle.json` 的 `component.name` / `component.subsystem`；老格式看 `ohos.build` 的 `parts` 键 | `hilog` @ `hiviewdfx`                   | `S3-bundle`                |
| **选择**     | 产品配置明确选中的部件           | 产品 `config.json` 的 `subsystems[].components[]`                                                    | `qemu_arm_linux_min` 选中 `hilog`       | `S3-product`               |
| **继承选择** | 产品继承清单中选中的部件         | 产品 `config.json` 的 `inherit` 指向的文件                                                           | `system_arm64_default` 继承 `rich.json` | `S3-product`（`medium`） |
| **依赖**     | 部件声明为构建所需的其他部件     | `bundle.json` 的 `deps.components`                                                                   | `hilog` 依赖 `c_utils`                  | `S3-dep`                   |

#### 1.4.1 「选择」和「依赖」差在哪

用一条真实链看：

```text
产品配置 config.json:28      { "component": "hilog" }          ← 选择（人挑的）
hilog 的 bundle.json:24-30   deps: c_utils, init, zlib…        ← 依赖（部件作者写的）
产品配置里并没有写 c_utils                                    ← 但它也得查
```

区别只有一句话：**「选择」是人挑的，「依赖」是部件自己声明的。**

为什么分开记，而不是合成一个「要」的清单？两个原因：

1. **报告要能说清是谁要的。**
   - 缺 `hilog` → 「产品配置第 28 行写的」→ 改产品配置；
   - 缺 `c_utils` → 「`hilog` 的说明书里要它」→ 改 `bundle.json` 或补仓。
     两者的修复动作不一样。
2. **展开依赖需要方向。** 依赖记录的是「谁指向谁」（`hilog → c_utils`），展开时靠这个方向；选择只是一张名单，没有方向。

#### 1.4.2 「继承清单」是什么

有些产品把清单拆成两个文件写。`productdefine/common/products/system_arm64_default.json:10`：

```json
"inherit": [ "productdefine/common/inherit/rich.json" ],
"subsystems": [ ...自己那份清单... ]
```

意思是：「除了下面我列的，再并上 `rich.json` 那份清单」。

所以 `rich.json` 不是另一个产品，只是**这个产品清单的一部分，单独放在一个文件里**。提取时要把它也读进来，否则会漏掉里面列的部件。这也是为什么它的置信度标 `medium`——它是片段，不是完整产品。

**S3 在提取阶段不下结论**：它只把「谁有、谁要、谁依赖谁」摆出来，判断留给 L3。

### 1.5 在算什么

把三类信息摆成集合：

```text
D 定义集   = 树里所有 bundle 定义的部件
S 选择集   = 产品配置 + inherit 里明确列出的部件（习惯上叫「种子」）
E 依赖边   = bundle 里 X → Y 的边
C 闭包     = 从 S 出发，沿 E 一路展开，直到不再出现新名字
M 缺失集   = C − D
```

一句话：

> **缺 = 闭包 − 定义集**

在探测树上用 `qemu_arm_linux_min` 实跑：

| 集合             | 值                                                                            |
| ---------------- | ----------------------------------------------------------------------------- |
| D 定义集         | 4：`hilog`、`hilog_native`、`hilog_service`、`hiviewdfx_hilog_native` |
| S 选择集（种子） | 19                                                                            |
| C 闭包           | 24（19 个选中的 + `hilog` 依赖的 7 个，去重后 24）                          |
| M 缺失集         | 23                                                                            |

**为什么必须算闭包，不能只看选择集？** 因为问题会藏在第二层、第三层：

- 产品写了 `hilog`，仓库里也有 `hilog` → 只看选择集，会判「通过」；
- 但 `hilog` 的说明书写着它还要 `c_utils`，而仓库里没有 `c_utils` → 构建照样炸。

闭包就是沿着依赖一路展开，把第二层、第三层需要的也收进来。

上面这些集合的构造全是 JSON 解析 + 集合运算、不碰环境、结果确定，所以 S3 是七个提取器里**最适合做 golden test** 的一个。

### 1.6 验证什么，不验证什么

| 验证                                                         | 不验证（归谁）                                             |
| ------------------------------------------------------------ | ---------------------------------------------------------- |
| 产品选中的每个部件，在树里有定义                             | 代码能不能编译 → 不在本工具范围                           |
| 这些部件**依赖的依赖**（第二层、第三层）在树里也有定义 | 模块 target 是否存在、可构建 → S1 / S2 / S4（第 2、3 关） |
| 每个缺失都能指到「哪一行要它」和「哪个父部件带来它」         | `features` 取值是否合法 → S7（第 4 关的另一条）         |
|                                                              | 仓是否同步、提交是否对 → `v_tree`（第 0 关）            |
|                                                              | 部件版本是否兼容 → K2 / `p_base`                        |

一句话：**S3 只回答「部件图闭不闭合」，不回答「部件能不能跑」。**

## 2. 部件声明长什么样

### 2.1 定义：`bundle.json`

真实文件：`hiviewdfx_hilog-OpenHarmony-6.1-Release/bundle.json`（节选，行号对应原文件）。

```json
{
  "name": "@ohos/hilog",
  "version": "3.1",
  "component": {
    "name": "hilog",
    "subsystem": "hiviewdfx",
    "adapted_system_type": ["standard"],
    "deps": {
      "components": [
        "bounds_checking_function",
        "c_utils",
        "ffrt",
        "init",
        "napi",
        "zlib",
        "runtime_core"
      ]
    },
    "build": {
      "sub_component": [
        "//base/hiviewdfx/hilog/services/hilogd:hilogd",
        "//base/hiviewdfx/hilog/interfaces/native/innerkits:libhilog"
      ],
      "inner_kits": [
        {
          "name": "//base/hiviewdfx/hilog/interfaces/native/innerkits:libhilog",
          "header": {
            "header_files": ["hilog/log.h", "hilog/log_c.h"],
            "header_base": "//base/hiviewdfx/hilog/interfaces/native/innerkits/include"
          }
        }
      ]
    }
  }
}
```

**这里有一个必须记住的坑：两个 `name` 不是一回事。**

| 字段                           | 值              | 谁用它                                     |
| ------------------------------ | --------------- | ------------------------------------------ |
| 顶层 `name`（第 2 行）       | `@ohos/hilog` | 包名（npm 风格），**产品配置不用它** |
| `component.name`（第 13 行） | `hilog`       | 部件 id，**产品配置引用的就是它**    |

实测 6 个 `bundle.json`，顶层名全部带 `@ohos/` 前缀或长名，`component.name` 全部是短名：

| 文件                                                     | 顶层 `name`                    | `component.name`         |
| -------------------------------------------------------- | -------------------------------- | -------------------------- |
| `hiviewdfx_hilog-…/bundle.json`（3.2/4.0/6.1 各一份） | `@ohos/hilog`                  | `hilog`                  |
| `…/interfaces/bundle.json`                            | `@ohos/hilog_native`           | `hilog_native`           |
| `…/services/bundle.json`                              | `@ohos/hilog_service`          | `hilog_service`          |
| `…/interfaces/native/bundle.json`                     | `@ohos/hiviewdfx_hilog_native` | `hiviewdfx_hilog_native` |

**所以索引必须用 `component.name` 建。** 用顶层 `name` 会把所有部件都判成「缺失」。

### 2.2 选择：产品配置 `config.json`

真实文件：`vendor_ohemu-OpenHarmony-4.0-Release/qemu_arm_linux_min/config.json`（节选）。

```json
{
  "product_name": "qemu_arm_linux_min",
  "device_company": "qemu",
  "board": "arm_virt",
  "kernel_type": "liteos_a",
  "subsystems": [
    {
      "subsystem": "hiviewdfx",
      "components": [
        { "component": "hilog", "features": [] },
        { "component": "hiviewdfx_hilog_native", "optional": "true" }
      ]
    },
    {
      "subsystem": "startup",
      "components": [
        { "component": "init" }
      ]
    }
  ]
}
```

三个字段值得注意：

| 字段                                       | 作用                                     | 注意                                                  |
| ------------------------------------------ | ---------------------------------------- | ----------------------------------------------------- |
| `subsystem` + `components[].component` | 产品选中的部件（**选择集**，种子） | 用的是 `component.name`，不是包名                   |
| `optional`                               | 这个部件可以缺                           | 值是**字符串** `"true"`，不是布尔——实测如此 |
| `features`                               | 编译特性开关                             | 影响编出来的东西，不影响「部件在不在」                |

### 2.3 片段：`productdefine/common/inherit/*.json`

产品配置可以拆成多份，`inherit/` 是其中一份。真实文件 `productdefine_common-OpenHarmony-6.1-Release/inherit/2in1.json`：

```json
{
  "version": "3.0",
  "subsystems": [
    {
      "subsystem": "updater",
      "components": [
        { "component": "sys_installer", "features": ["sys_installer_feature_ohos_cfg = true"] },
        { "component": "update_service", "features": [] },
        { "component": "updater", "features": [] }
      ]
    }
  ]
}
```

它**没有** `product_name` / `board` / `target_cpu`——所以它不是完整产品配置，只是「部件清单片段」。S3 在收集选择集里的部件时可以把它并进来；但 meta 里的 `product` 只认真正的产品 `config.json`。

### 2.4 老格式：`ohos.build`

真实文件：`device_qemu-OpenHarmony-4.0-Release/SmartL_E802/ohos.build`（全文）。

```json
{
  "parts": {
    "device_SmartL_E802": {
      "module_list": [
        "//device/qemu/SmartL_E802:SmartL_E802"
      ]
    }
  },
  "subsystem": "device_SmartL_E802"
}
```

2.x / 3.0 时代没有 `bundle.json`，用 `ohos.build`：`parts` 的**键**承担部件名的角色，`subsystem` 单独一个字段。

**必须同时认这两种格式**——否则 2.2/3.0 的部件会全漏（这正是 `docs/08` 列出的历史盲区之一）。

### 2.5 其他系统里的「同类文件」

「部件」这个概念不专属 OHOS，只是叫法不同。下表用来对照，**本版的闭包计算只对 OHOS 生效**（原因见 §3.1 末尾）。

| 系统           | 定义文件                         | 部件名                            | 依赖                                                |
| -------------- | -------------------------------- | --------------------------------- | --------------------------------------------------- |
| **OHOS** | `bundle.json` / `ohos.build` | `component.name` / `parts` 键 | `deps.components`                                 |
| Debian         | `debian/control`               | `Package:`                      | `Depends:` / `Build-Depends:`                   |
| Yocto          | `*.bb`                         | `PN`（通常等于文件名）          | `DEPENDS` / `RDEPENDS`                          |
| Buildroot      | `Config.in`                    | `config BR2_PACKAGE_<PKG>`      | `select` / `depends on`                         |
| AOSP           | `Android.bp`                   | 模块的 `name:`                  | `static_libs` / `shared_libs` / `header_libs` |
| npm            | `package.json`                 | `name`                          | `dependencies`                                    |
| Cargo          | `Cargo.toml`                   | `[package] name`                | `[dependencies]`                                  |
| Go             | `go.mod`                       | `module`                        | `require`                                         |

真实片段（各取一行）：

```text
# Debian hello —— debian/control
Source: hello
Build-Depends: debhelper-compat (= 9)
Package: hello
Depends: ${shlibs:Depends}, ${misc:Depends}

# Yocto busybox —— busybox.inc:6
DEPENDS += "kern-tools-native virtual/crypt"

# Buildroot —— package/busybox/Config.in
config BR2_PACKAGE_BUSYBOX
	bool "BusyBox"
	default y

# AOSP —— system/core/init/Android.bp:282
cc_binary {
    name: "init_second_stage",
    static_libs: ["libinit"],
}

# npm express —— package.json:34
"dependencies": { "accepts": "^2.0.0", "body-parser": "^2.3.0", ... }

# Cargo ripgrep —— Cargo.toml
[package]
name = "ripgrep"

# Go gin —— go.mod
module github.com/gin-gonic/gin
require ( github.com/bytedance/sonic v1.15.0 ... )
```

## 3. 提取器 S3：输入、步骤、产出

### 3.1 输入

L1 已经把这些文件挑出来了（`filelists.json` 里 `classes` 含 `S3` 的记录）：

| L1 大类          | 文件                                                                               | 提供什么                                 |
| ---------------- | ---------------------------------------------------------------------------------- | ---------------------------------------- |
| C3 模块/包清单   | `bundle.json`、`ohos.build`                                                    | **定义**（部件名、子系统、依赖边） |
| C4 板级/产品配置 | `vendor/**/config.json`、`productdefine/common/{products,inherit,base}/*.json` | **选择集**（产品选中的部件）       |

另外还需要一个参数：**`meta.product`**（`config.yaml` 里的 `product`），决定读哪一份产品配置。没有它就无法确定「这次要验哪些部件」。

> **为什么只对 OHOS 算闭包**：Debian/npm/Cargo 的「可用部件集合」不在源码树里，而在发行版仓库或 registry 里。本工具不联网，所以对这些系统只能提取「声明了什么依赖」，不能判断依赖是否可解析。这条边界写在 §6。

### 3.2 五步算法

```text
① 建索引    遍历 C3 文件 → {component.name: [bundle 路径]}
              ├─ bundle.json：component.name + deps.components
              └─ ohos.build：parts 的键（老格式）
② 取选择集    读 meta.product（选择集也叫「种子」） 指向的 config.json → subsystems[].components[].component
              （若同时提供 inherit 片段，一并并入）
③ 展开依赖   从选择集出发，沿 deps.components 一路展开，得到闭包（seen 集合防环）
④ 展开      每个「定义」一条记录（S3-bundle）
              每个「引用点」一条记录（S3-product 或 S3-dep）
⑤ 差集      留给 L3（见 §5）——L2 只负责把两边的事实都落到 requirements.json
```

**第 ⑤ 步为什么不在 L2 做？** 因为 L3 的纪律是「不碰源码树」。只要 L2 把「谁定义了谁」「谁引用了谁」都写成记录，L3 就能纯做集合运算，不必回头解析 JSON。

### 3.3 在探测树上真实跑一遍

用 `qemu_arm_linux_min` 这个产品（`vendor_ohemu-OpenHarmony-4.0-Release/…/config.json`）：

| 步骤           | 结果                                                                                                                       |
| -------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 定义（索引）   | 6 个 `bundle.json` → **4 个不同部件**：`hilog`、`hilog_native`、`hilog_service`、`hiviewdfx_hilog_native` |
| 选择集（种子） | **19 个**：`common`、`init`、`hilog`、`hitrace`、`faultloggerd`、`hisysevent`…                          |
| 闭包           | **24 个**（19 个选中的 + `hilog` 的 7 个依赖，去重后 24）                                                          |
| 命中           | **1 个**：`hilog`                                                                                                  |
| 缺失           | **23 个**：`access_token`、`bounds_checking_function`、`c_utils`、`init`…                                   |

**23 个缺失不代表工具有问题**——探测树只有 5 个子仓，绝大多数部件本来就不在里面。这个数字恰好说明：**在部分树上跑，S3 会把「树不全」如实报成「部件缺失」**，所以它必须排在 `v_tree`（第 0 关）之后。

### 3.4 产出：`requirements.json` 里的记录

每个部件产生两类记录。**定义**一条：

```json
{
  "id": "REQ-00042",
  "kind": "component",
  "name": "hilog",
  "declared_at": "hiviewdfx_hilog-OpenHarmony-6.1-Release/bundle.json:13",
  "declared_as": "\"name\": \"hilog\"",
  "extractor": "S3-bundle",
  "confidence": "high",
  "check": "CHK-COMPONENT-RESOLVABLE",
  "maps_to": ["BUILD-003"]
}
```

**引用**一条（产品在 `config.json:28` 点名要 `hilog`）：

```json
{
  "id": "REQ-00043",
  "kind": "component",
  "name": "hilog",
  "declared_at": "vendor_ohemu-OpenHarmony-4.0-Release/qemu_arm_linux_min/config.json:28",
  "declared_as": "{ \"component\": \"hilog\", \"features\":[] }",
  "extractor": "S3-product",
  "confidence": "high",
  "check": "CHK-COMPONENT-RESOLVABLE",
  "maps_to": ["BUILD-003"]
}
```

依赖边同理，只是 `extractor` 用 `S3-dep`：

```json
{
  "id": "REQ-00044",
  "kind": "component",
  "name": "c_utils",
  "declared_at": "hiviewdfx_hilog-OpenHarmony-6.1-Release/bundle.json:26",
  "declared_as": "\"c_utils\",",
  "extractor": "S3-dep",
  "confidence": "high",
  "check": "CHK-COMPONENT-RESOLVABLE",
  "maps_to": ["BUILD-003"]
}
```

字段怎么填：

| 字段            | 值                                                                    | 理由                                        |
| --------------- | --------------------------------------------------------------------- | ------------------------------------------- |
| `kind`        | `component`                                                         | 12 种 kind 之一，决定派给 `v_consistency` |
| `name`        | 部件 id（`component.name` / `parts` 键 / 配置里的 `component`） | **始终是短名**，不带 `@ohos/`       |
| `declared_at` | `相对路径:行号`                                                     | 报告要能直接指到行                          |
| `declared_as` | 原文片段，逐字                                                        | 让人看出是哪种写法被识别                    |
| `extractor`   | `S3-bundle` / `S3-product` / `S3-dep`                           | L3 靠它区分「定义」和「引用」               |
| `confidence`  | 见下表                                                                | 决定报告里这条有多可信                      |
| `check`       | `CHK-COMPONENT-RESOLVABLE`                                          | 唯一的组件路由                              |
| `maps_to`     | `["BUILD-003"]`                                                     | 对应原始问题清单                            |

置信度：

| 情况                                            | confidence |
| ----------------------------------------------- | ---------- |
| `bundle.json` / 产品 `config.json` 正常解析 | `high`   |
| `ohos.build` 老格式（`parts` 键当部件名）   | `medium` |
| `inherit/*.json` 片段（不是完整产品）         | `medium` |
| 同名部件多处定义、字段缺失、靠猜路径            | `low`    |

**去重规则**：

- **定义**按 `name` 去重：4 个部件只有 4 条定义记录，`declared_at` 指向其中一份（其它路径记在 `declared_as` 或另起 info）。同一部件在 3.2/4.0/6.1 三个版本目录里各有一份 `bundle.json`，按 name 合并。
- **引用**不按 name 去重：同一个部件在 3 个地方被引用，就留 3 条（每条都能独立指到行）。

## 4. 完成验证需要接收什么

L3 的 `v_consistency` 只接收三样：

| 输入                                          | 来源 | 必需 | 用途                             |
| --------------------------------------------- | ---- | ---- | -------------------------------- |
| `requirements` 中 `kind=component` 的记录 | L2   | 是   | 拆成「定义集」和「引用集」       |
| `meta.product`                              | L2   | 是   | 报告里写明「验的是哪个产品」     |
| `severity` / `optional` 标记              | L2   | 否   | 缺失时判 `block` 还是 `warn` |

**不需要的东西**（这是设计要点）：

- ❌ 源码树——L3 不碰文件；
- ❌ 网络 / 系统命令——纯集合运算；
- ❌ GN / ninja——部件图在 L2 已经变成记录了。

## 5. 怎么验证

### 5.1 位置：第 4 关，`v_consistency`

`component` 和 `arch` 都归 `v_consistency`（[`docs/02` §29.3](../../docs/02-流水线与关.md)）。它是五个验证器里唯一**完全不接触系统**的，因此最稳定、最容易做单元测试。

### 5.2 算法

```python
defined    = {r.name for r in reqs
              if r.kind == "component" and r.extractor == "S3-bundle"}
referenced = {r.name for r in reqs
              if r.kind == "component" and r.extractor in {"S3-product", "S3-dep"}}

for r in refs:                     # 每个引用点各出一条 finding
    result = "ok" if r.name in defined else "missing"
```

注意：差集只算一次，但 **finding 按引用点出**——同一个缺失部件被 3 处引用，就报告 3 次，每处都能指到行。

### 5.3 结果与档位

| 结果                                        | 条件                                | severity                   |
| ------------------------------------------- | ----------------------------------- | -------------------------- |
| `ok`                                      | 名字在定义集里                      | —（仍出 finding，`ok`） |
| `missing`                                 | 名字不在定义集里                    | `block`                  |
| `missing` + 该引用带 `optional: "true"` | 同上                                | `warn`                   |
| `skip`                                    | 没有 `meta.product`，或定义集为空 | `info`                   |

`skip` 很重要：如果产品名没给，不能把「没验」伪装成「全缺」。

### 5.4 `findings.json` 示例

缺失：

```json
{
  "id": "F-0031",
  "req": "REQ-00050",
  "gate": "g4",
  "severity": "block",
  "kind": "component",
  "name": "hitrace",
  "result": "missing",
  "evidence": "product qemu_arm_linux_min 引用 hitrace（config.json:29）；部件索引里没有 component.name=hitrace"
}
```

命中：

```json
{
  "id": "F-0032",
  "req": "REQ-00043",
  "gate": "g4",
  "severity": "info",
  "kind": "component",
  "name": "hilog",
  "result": "ok",
  "evidence": "hilog 定义于 hiviewdfx_hilog-OpenHarmony-6.1-Release/bundle.json:13"
}
```

`evidence` 必须同时写**两侧**：引用在哪、定义在哪（或「没找到」）。只写「缺失」的报告等于没写。

## 6. 边界与已知坑（全部来自实测）

| #  | 坑                                  | 实测现象                                                                                     | 处理                                                                                                                                      |
| -- | ----------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 1  | 顶层 `name` ≠ `component.name` | 6/6 个 `bundle.json` 都不同（`@ohos/hilog` vs `hilog`）                                | **索引键用 `component.name`**                                                                                                     |
| 2  | 一个仓多个部件                      | `hiviewdfx_hilog` 仓有 4 个 `bundle.json`                                                | 每个文件独立成一条定义                                                                                                                    |
| 3  | 多版本目录重复定义                  | 3.2 / 4.0 / 6.1 各有一份 `hilog`                                                           | 按 name 去重，记录所有路径                                                                                                                |
| 4  | mini 产品用 lite 部件               | `qemu_riscv32_mini_system_demo` 的 13 个选中的部件（`hilog_lite`…）在探测树里一个都没有 | 必须用**正确的 product**；选错产品会得到「全缺」                                                                                    |
| 5  | `optional` 是字符串               | `"optional": "true"`                                                                       | 判 `== "true"`，别用布尔                                                                                                                |
| 6  | inherit 片段不是产品                | `inherit/2in1.json` 没有 `product_name` / `target_cpu`                                 | 只用于补选择清单，不用于认定 meta.product                                                                                                 |
| 7  | 老格式 `ohos.build`               | `parts` 的键才是部件名                                                                     | 与 `bundle.json` 合并进同一索引                                                                                                         |
| 8  | 依赖成环                            | 理论上 A→B→A                                                                               | 展开时用 `seen` 集合，进过就不再展开                                                                                                    |
| 9  | 畸形 `bundle.json`                | `JSONDecodeError`                                                                          | **已知缺陷**：当前草图是静默 `continue`，会漏部件；实现时应记一条 `warn` finding（`extractor=S3-bundle`, `result=unknown`） |
| 10 | 树不全                              | 探测树 24 个闭包部件只命中 1 个                                                              | S3 必须在 `v_tree` 之后跑；报告里要写明「树不完整」的免责声明                                                                           |
| 11 | 同名不同子系统                      | 理论上两个子系统各有一个 `init`                                                            | 索引键是 `name` 单键；若真出现，需升级为 `(subsystem, name)`——目前未遇到                                                            |

## 8. 附：最小手工验证脚本

在任意 OHOS 树上跑（只依赖标准库）：

```python
import json, sys
from pathlib import Path

root = Path(sys.argv[1]); product = root / sys.argv[2]
defined, edges = set(), {}
for p in root.rglob("bundle.json"):
    try: d = json.loads(p.read_text(encoding="utf-8"))
    except Exception: continue
    c = d.get("component") or {}
    if c.get("name"):
        defined.add(c["name"])
        edges[c["name"]] = (c.get("deps") or {}).get("components") or []

cfg = json.loads(product.read_text(encoding="utf-8"))
seeds = [c["component"] for s in cfg["subsystems"] for c in s["components"]]
seen, stack = set(), list(seeds)
while stack:
    n = stack.pop()
    if n in seen: continue
    seen.add(n); stack.extend(edges.get(n, []))
print("定义", len(defined), "闭包", len(seen), "缺失", len(seen - defined))
```
