# S4 工具链 · S7 配置与架构

> **本文回答**：工具链到底是什么、配置与架构到底是什么；它们和外部的普通工具（如 Python）有什么区别；提取时要读哪些文件、产出什么；验证时要检查什么；为什么必须按产品收窄。
> **对应**：[`docs/02` §29.2](../../docs/02-流水线与关.md)（任务表）、[`L2` README §19.4 / §19.7](README.md)、[`L3` README](../l3_verify/README.md)。
> **状态**：设计说明。L2 的 S4/S7 提取器与 L3 的对应验证器尚未实现。

---

## 1. 为什么把这两个放在一起

它们回答的是同一件事的两半：

| 对象 | 回答的问题 | 一句话 |
| ---- | ---------- | ------ |
| **S4 工具链** | 用什么工具编？ | 编译器、目标三元组、sysroot、目标选项 |
| **S7 配置与架构** | 按什么配置、什么架构编？ | 开关的 schema 与取值；产品架构与内核/工具链架构的对应 |

两者必须**互相咬合**：

```text
产品配置 target_cpu ──┐
板级配置 board_arch ──┼──> 必须指向同一个目标
工具链前缀 / 三元组 ──┘
```

任何一处对不上，构建要么直接失败，要么编出一个跑不起来的产物。

## 2. S4 工具链

### 2.1 定义：工具链是一个「四元组」，不是一个命令

| 组成 | 说明 | 例子 |
| ---- | ---- | ---- |
| 编译器 / 链接器 / 汇编器 | 可执行文件 | `arm-none-eabi-gcc`、`csky-elfabiv2-gcc`、`clang` |
| 目标三元组 | 这套工具给谁编 | `arm-none-eabi`、`aarch64-linux-ohos` |
| sysroot | 目标系统的头文件与库 | `--sysroot=/path/to/sysroot` |
| 目标选项 | 架构、浮点、ABI、指令集 | `-march=armv7-a -mfpu=neon -mfloat-abi=softfp` |

只检查第一个（命令存在）是不够的——**同名工具可能编出完全不同的东西**。

### 2.2 和普通外部工具（Python、mcopy）的区别

| 维度 | 普通工具 | 工具链 |
| ---- | -------- | ------ |
| 归属 | 主机环境（host） | 目标环境（target） |
| 需求 | 「命令存在，版本够」 | 「这套工具是给这块板子的」 |
| 验证 | `command -v`、`--version` | `-dumpmachine`、`--version`、sysroot、头文件搜索路径 |
| 出错后果 | 命令找不到，任务直接失败 | **可能编过一部分，但产物跑不了**：架构错、ABI 错、链接错 |
| 谁声明 | 脚本 / GN action / Make recipe | 板级 `config.gni`、`BoardConfig.mk`、CMake toolchain 文件 |
| 换一块板 | 不变 | **换一套** |

一句话：

> **普通工具验「有没有」，工具链验「是不是那一个」。**

两个典型反例：

1. 机器上有 `/usr/bin/gcc`，`command -v gcc` 通过；但它是宿主机的 x86 编译器，不是 `arm-none-eabi-gcc`。用它编 ARM 代码，配置阶段全绿，编译阶段报架构错误。
2. `arm-none-eabi-gcc` 和 `arm-linux-gnueabihf-gcc` 都是 ARM，但一个是裸机（无 libc），一个是 Linux（glibc）。名字像，ABI 完全不同。

### 2.3 声明在哪些文件里（真实例子）

#### OHOS lite 板级：`config.gni`

真实文件（`device_qemu-OpenHarmony-4.0-Release/SmartL_E802/liteos_m/config.gni`）：

```gn
kernel_type = "liteos_m"
board_cpu = "e802"
board_arch = "ck802"
board_toolchain = "csky-elfabiv2-gcc"
board_toolchain_prefix = "csky-elfabiv2-"
board_toolchain_type = "gcc"
board_cflags = ["-mthumb", "-Wall", "-fdata-sections"]
board_include_dirs = ["//kernel/liteos_m/kernel/arch/csky/v2/gcc", ...]
```

同一棵树里不同板子的工具链完全不同：

| 板级目录 | `board_toolchain` | `board_cpu` / `board_arch` |
| -------- | ----------------- | -------------------------- |
| `arm_mps2_an386` | `arm-none-eabi-gcc` | `cortex-m4` |
| `riscv32_virt` | `riscv32-unknown-elf` | `rv32imac` |
| `esp32` | `xtensa-esp32-elf-gcc` | — |
| `SmartL_E802` | `csky-elfabiv2-gcc` | `e802` / `ck802` |

#### OHOS 标准系统：`build/config` 下的 GN 配置

标准系统通常不写「某个 gcc」，而是「clang + 目标三元组 + sysroot」：

```gn
# 形式示意，具体变量名以所在版本为准
cc = "clang"
cflags_cc = [ "--target=aarch64-linux-ohos", "--sysroot=..." ]
```

#### 其他系统的同类声明

| 系统 | 声明位置 | 关键字段 |
| ---- | -------- | -------- |
| AOSP | `BoardConfig.mk` | `TARGET_ARCH`、`TARGET_ARCH_VARIANT`、`TARGET_TOOLCHAIN_PREFIX` |
| CMake | toolchain 文件 | `CMAKE_C_COMPILER`、`CMAKE_SYSTEM_PROCESSOR`、`CMAKE_SYSROOT` |
| Zephyr | `CMakeLists.txt` / 环境 | `ZEPHYR_TOOLCHAIN_VARIANT`、`CONFIG_ARCH` |
| Yocto | `machine.conf` / `local.conf` | `MACHINE`、`TUNE_*`、`CC` |
| Buildroot | `*_defconfig` / toolchain 配置 | `BR2_TOOLCHAIN_EXTERNAL_*` |
| RT-Thread | `rtconfig.py` | `CROSS_TOOL`、`PREFIX`、`ARCH`、`CPU` |

### 2.4 提取什么

**一条需求 = 一个期望元组**，不是一堆零散字段：

```json
{
  "kind": "toolchain",
  "name": "csky-elfabiv2-gcc",
  "declared_at": "device/qemu/SmartL_E802/liteos_m/config.gni:12",
  "declared_as": "board_toolchain = \"csky-elfabiv2-gcc\"",
  "extractor": "S4-toolchain",
  "confidence": "high",
  "check": "CHK-EXISTS-CMD"
}
```

配套的目标信息（架构、前缀、sysroot、选项）作为同一来源的附加记录或字段：

| 字段 | 来源 | 用途 |
| ---- | ---- | ---- |
| 编译器名 | `board_toolchain` / `CMAKE_C_COMPILER` / `CC` | 找可执行文件 |
| 前缀 | `board_toolchain_prefix` / `TARGET_TOOLCHAIN_PREFIX` | 拼 `gcc`/`g++`/`ar`/`ld` |
| 架构 | `board_arch` / `board_cpu` / `CMAKE_SYSTEM_PROCESSOR` | 与 S7 交叉校验 |
| 三元组 | 显式字段，或由前缀推断 | `-dumpmachine` 比对 |
| sysroot | `--sysroot` / `CMAKE_SYSROOT` | 头文件与库可达性 |
| 目标选项 | `board_cflags` / `TARGET_*FLAGS` | 记录，不做求值 |

### 2.5 验证什么

| # | 检查 | 命令 / 方法 | 失败意味着 |
| - | ---- | ----------- | ---------- |
| 1 | 可执行文件存在 | `command -v <cc>` | 工具链没装 / 不在 PATH |
| 2 | 身份正确 | `<cc> -dumpmachine` 与期望三元组比对 | 装的是另一套工具链 |
| 3 | 版本满足 | `<cc> --version` 解析 | 版本过低/过高 |
| 4 | sysroot 存在 | `<cc> -print-sysroot` 或读取声明的路径 | 头文件/库找不到，编到一半失败 |
| 5 | 目标头文件可达 | `printf '' \| <cc> -E -v -xc -` 看搜索路径 | 目标头文件缺失（和 S6 联动） |
| 6 | 与 S7 一致 | 产品 `target_cpu` ↔ 板级 `board_arch` ↔ 工具链前缀 | 架构不匹配 |

注意第 2 条：**存在 ≠ 对**。这是 S4 和 S1 最本质的区别。

### 2.6 常见错误形态

| 现象 | 根因 |
| ---- | ---- |
| `command -v arm-none-eabi-gcc` 通过，但编译报 `unrecognized command line option '-mthumb'` | 装的是别的架构的 GCC |
| 编译报 `stdio.h: No such file or directory` | sysroot 没配或路径不对 |
| 链接报 `cannot find -lc` | sysroot 里没有目标 libc |
| 编出来的产物 `file` 显示 x86-64 | 用了宿主编译器 |
| `-dumpmachine` 输出 `arm-none-eabi`，但产品是 `arm-linux` | 裸机工具链 / Linux 工具链混用 |

### 2.7 必须按产品收窄

同一棵树里有 10 块板、4 种工具链。全量扫描会同时要求 ARM、RISC-V、Xtensa、C-SKY——每一条都是「未满足」。

所以 S4 的读取范围是：

```text
产品配置（vendor/<vendor>/<product>/config.json）
+ 该产品的板级目录（device/<board>/… 的 config.gni / BoardConfig.mk）
+ 全局构建配置（build/config 下的 toolchain 设置）
```

**不读**其它板子的 `config.gni`。

## 3. S7 配置与架构

### 3.1 定义：两件事

| 部分 | 内容 | 例子 |
| ---- | ---- | ---- |
| **配置开关** | 有哪些开关（schema）、这次选了什么值 | `Kconfig` 定义；`defconfig`/`.config`/`prj.conf` 取值 |
| **架构映射** | 产品说的架构名 ↔ 内核/工具链用的架构名 | `target_cpu=arm64` ↔ `ARCH=arm64`、`aarch64-…` |

### 3.2 声明在哪些文件里

| 类型 | 文件 | 例子 |
| ---- | ---- | ---- |
| 开关 schema | `Kconfig`、`Kconfig.*`、`Config.in` | `config SOC_STM32F429IG` |
| 开关取值 | `*_defconfig`、`.config`、`prj.conf` | `CONFIG_ARCH="arm"`、`LOSCFG_COMPILER_GCC=y` |
| 产品架构 | 产品 `config.json` | `"target_cpu": "arm64"`、`"board": "arm_virt"` |
| 板级架构 | `config.gni` | `board_arch = "ck802"`、`board_cpu = "cortex-m4"` |
| 部件特性 | `bundle.json` 的 `features` | `hilog_feature_support_usr_symlink` |

真实例子：

```json
// vendor/ohemu/qemu_arm_linux_min/config.json
{ "product_name": "qemu_arm_linux_min", "board": "arm_virt", "kernel_type": "liteos_a" }
```

```text
# vendor/.../kernel_configs/debug.config
LOSCFG_COMPILER_GCC=y
LOSCFG_KERNEL_MMU is not set
```

### 3.3 提取什么

| 记录 | 内容 | 例子 |
| ---- | ---- | ---- |
| `kind=config`（schema） | 开关名、类型、默认值、依赖 | `SOC_STM32F429IG: bool` |
| `kind=config`（取值） | 开关名、取值、来源 | `LOSCFG_KERNEL_MMU = n` |
| `kind=arch` | 产品/板级/工具的架构名 | `target_cpu=arm64`、`board_arch=ck802` |

### 3.4 验证什么

| # | 检查 | 方法 | 失败意味着 |
| - | ---- | ---- | ---------- |
| 1 | 取值有对应 schema | 在 `Kconfig` 里找 `config <NAME>` | 写了不存在的开关（拼错/版本不符） |
| 2 | 取值类型正确 | `bool` 只接受 y/n；`int`/`string` 对应 | 配置写错格式 |
| 3 | 依赖满足 | `depends on` / `select` 链 | 选了互相矛盾的组合 |
| 4 | **架构三方一致** | 产品 `target_cpu` ↔ 板级 `board_arch` ↔ 工具链前缀/三元组 | 架构不匹配 |
| 5 | 架构映射存在 | `target_cpu` 在映射表里（如 `x86_64→x86`） | 新架构没登记 |
| 6 | 板级配置存在 | 该板卡的 `defconfig` / 目录在树里 | 板级源码缺失 |

架构映射表的常见项：

| 产品写的 | 内核/工具链用的 |
| -------- | --------------- |
| `arm64` | `arm64`、`aarch64-…` |
| `arm` | `arm`、`arm-…` |
| `x86_64` | `x86` |
| `riscv64` | `riscv` |
| `ck802` | `csky` |

### 3.5 常见错误形态

| 现象 | 根因 |
| ---- | ---- |
| 内核报「没有为该架构生成 defconfig」 | `target_cpu` 在映射表里错了，或该架构的 defconfig 不存在 |
| 编出来的内核架构不对 | 选了 `arm64`，但用的是 `arm` 的 defconfig |
| 开关明明写了却不生效 | 开关名拼错，或依赖没满足（`depends on` 不成立） |
| 板级配置找不到 | `board` 名与 `device/` 目录不一致 |

### 3.6 必须按产品收窄

全量读 `defconfig`/`Kconfig` 会把所有板卡、所有内核版本的配置混在一起：

- 同一开关在不同内核版本里名字不同（`CONFIG_ARM64` vs `LOSCFG_…`）；
- 不同板卡的默认值互相冲突。

所以 S7 只读：

```text
该产品的 config.json
+ 该板卡的 config.gni / defconfig / .config
+ 该内核版本对应的 Kconfig
```

## 4. 三者的交叉关系

```text
              S1 普通工具
              （只要存在）
                   │
                   │ 工具链也是工具，但要求更高
                   ▼
S4 工具链  ◄──── 架构必须一致 ────►  S7 配置与架构
（编译器、三元组、sysroot）          （target_cpu、board_arch、开关取值）
                   │
                   ▼
            构建产物（镜像 / 可执行文件）
```

| 关系 | 检查 | 后果 |
| ---- | ---- | ---- |
| S4 ↔ S7 | 工具链前缀/三元组 vs `board_arch`/`target_cpu` | 不一致 → 编错架构 |
| S4 ↔ S5 | 工具链的 sysroot 里有没有 `-l` 要的库 | 缺库 → 链接失败 |
| S4 ↔ S6 | sysroot 与工具链的 include 路径 | 缺头文件 → 编译失败 |
| S7 ↔ S3 | 产品 `target_cpu` 与组件 `adapted_system_type`/`features` | 部件不支持该形态 |

### 一个走一遍的例子

```text
产品：qemu_arm_linux_min
  target_cpu: arm64（若为标准产品）
  board: arm_virt
        │
        ▼
板级：device/qemu/arm_virt/…/config.gni
  board_cpu = "cortex-a7"
  board_toolchain = "arm-none-eabi-gcc"（lite 示例）
        │
        ▼
S4 期望：arm-none-eabi-gcc，前缀 arm-none-eabi-，架构 cortex-a7
S7 期望：target_cpu=arm64 ↔ board_arch=armv8-a ↔ 工具链前缀 aarch64-
        │
        ▼
验证：命令存在？-dumpmachine 匹配？sysroot 在？架构三方一致？
```

任何一步不匹配，就是构建前应当拦下来的问题。

## 5. 处理规则（实现层）

### 5.1 S4 的提取规则

| 文件 | 抽取字段 |
| ---- | -------- |
| `config.gni` | `board_toolchain`、`board_toolchain_prefix`、`board_toolchain_type`、`board_cpu`、`board_arch`、`board_cflags` |
| `BoardConfig.mk` | `TARGET_ARCH`、`TARGET_ARCH_VARIANT`、`TARGET_TOOLCHAIN_PREFIX` |
| CMake toolchain | `CMAKE_C_COMPILER`、`CMAKE_SYSTEM_PROCESSOR`、`CMAKE_SYSROOT` |
| `rtconfig.py` | `CROSS_TOOL`、`PREFIX`、`ARCH`、`CPU` |

**置信度**：

- `high`：字段明确、路径在板级目录内；
- `medium`：由前缀推断三元组，或工具链来自全局配置；
- `low`：只写了编译器名、没有架构/前缀信息。

### 5.2 S4 的验证命令

```bash
command -v <cc>                 # 存在
<cc> -dumpmachine               # 身份
<cc> --version                  # 版本
<cc> -print-sysroot             # sysroot
echo | <cc> -E -v -xc -         # 头文件搜索路径
```

**三态结果**：存在 / 不存在 / 存在但不可执行（权限或架构不对）。

### 5.3 S7 的提取规则

| 文件 | 抽取 |
| ---- | ---- |
| `Kconfig` | `config X`、类型、`default`、`depends on`、`select` |
| `*_defconfig` / `.config` / `prj.conf` | `NAME=value` 或 `# NAME is not set` |
| 产品 JSON | `target_cpu`、`board`、`kernel_type`、`features` |
| `config.gni` | `board_arch`、`board_cpu` |

### 5.4 S7 的验证规则

| 检查 | 方法 |
| ---- | ---- |
| 开关存在 | 在 `Kconfig` 里找到 `config <NAME>` |
| 类型正确 | 按 Kconfig 类型判断取值合法性 |
| 架构映射 | 查映射表；未登记报 `warn` |
| 三方一致 | 产品 / 板级 / 工具链三处架构字符串归一后比较 |
| 板级文件存在 | `defconfig` 路径 `test -f` |

## 6. 和「产品域」的关系

S4/S7 是最容易被全量提取带偏的两个对象：

| 全量扫描的后果 | 具体表现 |
| -------------- | -------- |
| 同时要求多套工具链 | ARM、RISC-V、Xtensa、C-SKY 全被报「缺失」 |
| 架构互相冲突 | 产品是 arm64，却扫到 ck802 的板级配置 |
| 开关名混版本 | 4.19 与 6.6 的 defconfig 互相覆盖 |
| 成本 | 板级配置数量是产品数的几十倍 |

所以它们必须和 S3 共用同一个 **ProductScope**：

```text
ProductScope = 产品配置 + 递归 inherit + 组件闭包 + 该板卡 vendor/device + 全局 build 配置
```

### 建议的实现顺序

1. **先做 ProductScope**：S4/S7 都依赖它；
2. **S4 先做「存在 + 身份」**：这两条最容易出错，也最容易验证；
3. **S7 先做「架构三方一致」**：不需要解析全部 Kconfig，收益最高；
4. **最后做开关 schema 校验**：成本最高，可以先用「开关名存在性」代替完整依赖求值。

## 8. 边界

- **不做 GN 求值**：工具链变量可能来自 `import` 的 `.gni`，静态读取只能拿到字面量；
- **不做条件编译**：同一份源码在不同开关下编不同分支，静态扫描会过度报告；
- **不保证可构建**：S4/S7 只证明「声明之间一致、工具在目标环境可用」，不代替实际编译。
