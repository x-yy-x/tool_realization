## 30.0 为什么 L4 是两半拼起来的

L4 的输入是 findings，输出有两样**性质完全不同**的东西：

| 半边              | 产出                            | 会改东西吗 | 谁来判                    |
| ----------------- | ------------------------------- | ---------- | ------------------------- |
| **判读**    | 定级 + 聚合 + 出口决定          | ❌         | **脚本**（确定性）  |
| **修改**    | 分诊决定 + 修复执行 + 回环      | ✅         | **Agent 出决定，脚本执行** |

**两半的判据来源不同，所以不能混在一个模块里**：

- 判读靠**规则**（severity 表 + 出口条件），必须可复现、可审计
- 修改靠**Agent**（它要读证据、给候选根因），但**被围栏锁死**（只能四选一，见 [`06` §28.4](../../docs/06-修复段.md)）

> **这条分界不是洁癖，是安全要求。**
> `ENV-002`（Ubuntu 版本不在支持范围）如果让 Agent 自由发挥，它可能去跑 `do-release-upgrade`——**那是灾难性的**。
> 把「决定」和「执行」拆开，是**从结构上**让它够不着，比在提示词里叮嘱它别做可靠得多。

## 30.1 判读半边：三个动作

### ① 定级

每条 finding 落到 `block` / `warn` / `info`：

| 档        | 判据                              | 例子                              |
| --------- | --------------------------------- | --------------------------------- |
| `block` | 这条不满足，**构建必然失败** | 工具不存在、仓缺失、revision 不符 |
| `warn`  | 需要人判，或**可能是假阳性** | S1 疑似工具名、`BUILD-008` 缺口 |
| `info`  | 只是提示，不影响构建              | `ENV-014`（Node 14）、low 置信 |

**提取时给的是「默认档」，L4 可以按验证结果上调。**

`requirements.json` 里就带 `severity`，但那是**跟着 `check` 走的默认值**——提取的时候还不知道验证会返回什么。同一个 `kind=tool` 的需求，`v_exists` 报 `missing` 是 `block`，报「存在但不可执行」可能只该是 `warn`。

| 谁       | 做什么                                            |
| -------- | ------------------------------------------------- |
| 提取时   | 填默认档（由 `check` 决定：`CHK-EXISTS-CMD` → `block`） |
| **L4**   | **按 `result` 上调或下调**，改动理由写进报告 |

**默认档的规则写在代码里，不写在 `knowledge.yaml`**：它是每个 `check` 的**固定属性**，不是可配置的知识。这样出口条件才可复现；`knowledge.yaml` 只放「同一档内部的语义判断」（[`L2` §19.7](../l2_extract/README.md)）。

### ② 聚合

**同一根因的 findings 要并排，否则人看不出关联。** 三类聚合：

| 聚合                       | 把什么并在一起                              |
| -------------------------- | ------------------------------------------- |
| **工具链 × 目标**    | 第 4/5 关的 triple / 架构映射，合成一节     |
| **仓库 × 可达性**    | 第 6 关的缺失仓 + 它们的 HTTP 状态码        |
| **部件缺失闭包**     | 第 5 关的缺失集，按「谁依赖谁」串成一条链   |

**不聚合的话，30 个缺仓会报成 30 条独立 finding**——人看不出「它们其实是同一个 manifest 没声明」。

### ③ 出口决定

```
出口条件：block 清零 —— 不是 findings 清零
```

| 情况              | 决定                                     |
| ----------------- | ---------------------------------------- |
| `block` 全部修好  | 继续（补拉缺失仓 → `hb build`）        |
| `block` 里有「放弃」 | **停**，输出重建方案，不编译         |
| 还有未处置的 `block` | 异常，回分诊重判（本不该发生）           |

**`warn` / `info` 可以带着编译**——因为 `warn` 里有一部分是 S1 的假阳性（[`L2` §19.3.7](../l2_extract/README.md)），要求清零等于要求修假问题。

## 30.2 修改半边：一次 L4 的时序

```
第 N 关跑完
   │
   ├─ 判读：定级 → 聚合
   │
   ├─ findings 为空？ ── 是 → 进下一关
   │
   └─ 非空 → ① 分诊
              triage.py 组装上下文：
                本关全部 findings + knowledge.yaml + 本关上下文/白名单
                        ↓
              调 Agent（skill 形态，见 README 的「实现形态」）
                        ↓
              ② Agent 四选一（受档位围栏）
                 apply_recipe / propose_patch / escalate / abandon
                        ↓
              ③ executor.py 执行
                 apply_recipe → 跑 recipe（脚本）
                 propose_patch → 出 patch，**默认 dry-run**，人审后才 apply
                 escalate / abandon → 不执行
                        ↓
              ④ loop.py 判回环
                 改的是源码吗？
                   否（A 档）→ 小回环：只重跑产生该 finding 的那几条 CHK
                   是（B 档）→ 大回环：回第 1 关重扫（需求清单本身变了）
                        ↓
              ⑤ 收敛判据（四条）→ 通过则进下一关；不满足则 rollback.py 回滚本轮全部改动
```

**四个模块各管一段，不互相知道细节：**

| 模块            | 只做                                        | 不做                    |
| --------------- | ------------------------------------------- | ----------------------- |
| `triage.py`   | 组装上下文 → 调 Agent → 收「决定」     | 不执行、不判收敛        |
| `executor.py` | 按决定执行（跑 recipe / apply patch）       | 不决定该修什么          |
| `loop.py`     | 判小回环 / 大回环 + 四条收敛判据            | 不执行动作              |
| `rollback.py` | B 档改动的快照与撤销                        | 不判该不该回滚          |

**`triage.py` 只产数据，`executor.py` 只消费数据**——这条和 §15.3「用文件解耦」是同一个思路：[`06` §28.4](../../docs/06-修复段.md) 说的「决定是数据，动作是脚本」，落到模块上就是这两个文件分开。

## 30.4 一个特例：第 2 关的修复对象是「工具自己」

第 2 关（[`L2` §19.8](../l2_extract/README.md)）报的是「某个扩展名的文件没人认领」，**修复动作是加一条提取规则——改的是扫描器自己的代码**，不是环境、不是源码树。

**这不能进 `l4_triage_fix/`**：

|            | 对象                  | 在哪                                   |
| ---------- | --------------------- | -------------------------------------- |
| 运行期修复 | 目标环境 / 源码树     | `src/l4_triage_fix/`                 |
| 自检修复   | **工具自己的代码** | **开发期动作**，产出 patch 给人  |

混在一起的后果是「**工具在运行期把自己改了**」——这种改动没法回滚。

## 30.5 模块接口

```python
# l4_triage_fix/report.py
def render(findings, mode="md") -> str:
    """出报告：缺什么 + 出自哪一行 + 怎么补。第 4/5 关的要聚合成一节。"""

# l4_triage_fix/triage.py
def build_context(gate, findings, knowledge, whitelist) -> dict:
    """组装分诊输入。**上下文不够，Agent 就得自己重扫树**（06 §28.3）。"""

def decide(context) -> list[Decision]:
    """调 Agent，收四选一。返回数据，不执行。"""

# l4_triage_fix/executor.py
def execute(decision, dry_run=True) -> ExecResult:
    """跑 recipe 或 apply patch。propose_patch 默认只落盘到 patches/。"""

# l4_triage_fix/loop.py
LOOP_LIMIT = 5
FIX_LIMIT = 3

def next_step(before, after, attempts, rounds) -> str:
    """返回 'small' / 'large' / 'rollback'。四条收敛判据在这里。"""

# l4_triage_fix/rollback.py
def snapshot(paths) -> Snapshot: ...
def restore(snap) -> None: ...
```
