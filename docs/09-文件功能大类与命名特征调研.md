# 09 · 文件功能大类与命名特征调研（跨系统）

> **本文回答**：L1 该按什么「功能大类」给文件分类；每个大类能喂给哪些提取器；这些大类的命名/位置特征在不同系统之间能迁移多少。
> **对应**：`08` 回答「OHOS 里某个对象写在哪个文件」，本文回答「换一个系统时，怎么凭名字、路径、开头把那个文件认出来」。
> **状态**：调研稿 v1.1（2026-10-26 补实测）。本文只给结论与依据，不含规则实现。名字覆盖率、噪声源、2 KB 判据均已实测；规则阶段还差「人工标注集扩量」与「Debian 一格核对」，见 §33.8.4。

## 33.0 方法与边界

### 33.0.1 三个问题

1. 源码树里的文件，按「它承载什么信息」能分成几个大类？
2. 每个大类分别能喂给 S1/S3/S4/S5/S6/S7 里的哪几个？是「可能承载」还是「一定承载」？
3. 这些大类在各系统里的命名与位置特征是什么？哪些能跨系统复用，哪些只能用一次？

**顺序不能反。** 如果先列「文件有哪些」，大类就会被文件名牵着走，最后又变成「给每个系统抄一遍清单」。所以第 1 节先问「提取器需要读到什么」，第 3 节才问「这东西在不同系统里叫什么」。

### 33.0.2 证据等级

| 级 | 含义 | 本文里的用法 |
| -- | ---- | ------------ |
| **A** | 官方规范 / 官方手册明确写了 | 非 OHOS 系统的主体证据 |
| **B** | 真实仓库里的文件（路径可复现） | OHOS 部分（沿用 `08` 的实测）+ 5 个非 OHOS 系统的稀疏检出（§33.3） |
| **C** | 由 A/B 推出，未直接验证 | 归并原则、映射矩阵、迁移性分级 |

### 33.0.3 本次范围与已知局限

- **OHOS**：沿用 `08` 的真实树实测结论（B 级），本文不重复调研。
- **其他 10 个系统**：Android/AOSP、Yocto、Debian、CMake、Meson、Buildroot、Zephyr、Linux 内核、RT-Thread、NuttX。
  - **A 级**：官方文档逐条对照，全部 10 个系统都做了。
  - **B 级**：**11 个系统都拉了真实仓库**做稀疏检出（只取一个包/一块板/一个目录），核对表里的「载体」是否真的长这样。见 §33.3 各节末尾的「B 级实测」。
  - **仍不是「完整树」**：每棵树只取了一个切片。代价与影响列在 §33.9。
- 之所以挑这十个做 B 级：它们分别代表**配方式**（Yocto）、**包式**（Buildroot）、**CMake 式**（Zephyr、fmt）、**Meson 式**（meson 本体）、**SCons 式**（RT-Thread）、**Kconfig 式**（NuttX）、**Autotools 式**（Debian）、**Soong/make 混合式**（AOSP），覆盖了「同一个概念换一套写法」的主要变体。
- 文档链接的可达性在附录 A 逐条标注；本机网络下 `source.android.com` 与 `gn.googlesource.com` 不可达，这两处改用镜像仓库 + 官方 URL 并列。

### 33.0.4 与 `08` 的分工

| | `08` | 本文 |
| -- | ---- | ---- |
| 问题 | OHOS 里这个对象写在哪个文件 | 换系统后怎么把这类文件认出来 |
| 粒度 | 到 carrier（`bundle` / `productdefine.products` / `ohosbuild`） | 到大类（8 个） |
| 用途 | L2 知道该用哪套 schema 解析 | L1 知道该路由给谁 |
| 关系 | 本文的 8 个大类，每个都由 `08` 的若干 carrier 归并而来；carrier 不进 `filelists.json` | |

## 33.1 从提取器反推：它需要读到什么

依据 [`src/l2_extract/README.md`](../src/l2_extract/README.md) §19.1–19.7。

| 提取器 | 必须读到的信息 | 在文本里可能长什么样（不分系统） |
| ------ | -------------- | -------------------------------- |
| **S1 工具** | 一条可执行的命令行：程序名 + 参数 | 脚本里的一行；Make recipe；`action { script = }`；`add_custom_command`；BitBake 任务函数体；`subprocess.run` |
| **S3 组件** | 模块名、依赖谁、产出什么 | JSON 的 `name`/`deps`；`.bp` 的模块类型 + `static_libs`；`.bb` 的 `DEPENDS`/`RDEPENDS`；`debian/control` 的 `Package`/`Depends`；`Config.in` 的 `select`/`depends on` |
| **S4 工具链** | 编译器/链接器、编译选项、目标架构 | `CC`/`CROSS_COMPILE`；GN `toolchain()`；CMake toolchain 文件；`BoardConfig.mk` 的 `TARGET_*`；machine conf；defconfig |
| **S5 库与符号** | 链接用的库名、链接选项、符号定义/导出 | `libs`/`ldflags`；`LDLIBS`/`LDFLAGS`；`shared_libs`；`target_link_libraries`；命令行里的 `-lfoo`；`.ld` 的 `ENTRY()`；`.map` 的 `global:` |
| **S6 头文件缺口** | 用了什么类型、有没有对应声明 | C/C++ 源码与头文件；清单里对外导出的头（`inner_kits`、`export_include_dirs`、`PUBLIC_HEADER`） |
| **S7 配置与架构** | 开关名 + 取值、目标平台/架构 | `Kconfig` 的 schema + `defconfig`/`.config`/`prj.conf` 的取值；产品 JSON 的 `target_cpu`；machine conf 的 `MACHINE` |

**两条立刻能看出来的事实：**

1. **没有一个对象只靠一种文件。** S1 分布在至少 6 种写法里；S3 在每个系统都换一套。
2. **同一个文件经常同时喂两个提取器。** `BUILD.gn` 喂 S1/S4/S5/S7，`.bb` 喂 S1/S3，`debian/control` 喂 S3/S4/S7。所以「一个文件一个大类」这个假设从一开始就不成立。

## 33.2 八个功能大类

### 33.2.1 归并原则

归并的判据不是「这些文件长得像」，而是 **「读它们的人要用同一套办法去读」**：同样的定位方式、同样的解析手法、同样的误报来源。满足这三条才合成一类。

另外三条纪律：

- **按信息内容定义，不按文件名定义。** 定义里不能出现 `bundle.json`，只能出现「声明了一个模块的名字和依赖」。
- **宁宽勿窄。** 一个文件只要**可能**承载某类信息，就该进这个大类。多路由的代价是 L2 多打开一个文件，漏路由的代价是整条链看不见它。
- **允许重叠。** 一个文件可以同时属于多个大类，输出时取并集。

### 33.2.2 八个大类

| # | 大类 | 定义（按信息内容） | 判据举例 | 主要喂给 |
| - | ---- | ------------------ | -------- | -------- |
| **C1** | 可执行脚本 | 会被某个解释器执行的文本，内容是一串命令 | `*.sh`、`*.py`、shebang、`scripts/` 下无后缀的可执行文件 | S1（主）、S5、S6 |
| **C2** | 构建描述 | 用某种 DSL 描述「有哪些目标、由哪些源文件构成、依赖谁、怎么编」 | `Makefile`、`BUILD.gn`、`CMakeLists.txt`、`meson.build`、`Android.bp`、`*.bb`、`SConscript`、`Kbuild` | S1、S4、S5、S7、S3 |
| **C3** | 模块/包清单 | 声明一个可交付单元的身份、版本、依赖、产出物 | `bundle.json`、`ohos.build`、`debian/control`、`package.json`、`Config.in`、`.bb` 的变量段 | S3（主）、S6、S1 |
| **C4** | 产品/板级/工具链配置 | 为某块板、某个产品、某套工具链**选定取值**：架构、CPU、编译器、开哪些开关、包含哪些模块 | `vendor/*/*/config.json`、`BoardConfig.mk`、`conf/machine/*.conf`、`configs/*_defconfig`、`prj.conf`、toolchain 文件 | S4（主）、S7（主）、S3、S5 |
| **C5** | 链接与符号 | 描述链接期怎么摆放代码/数据段、导出哪些符号 | `*.ld`、`*.lds`、`*.map`、`*.symbols`、`ENTRY(`、`SECTIONS` | S5（主）、S7 |
| **C6** | C/C++ 源码与头文件 | 编译器直接吃的源文本 | `*.c/.cc/.cpp/.h/.hpp/.inl` | S6（主） |
| **C7** | 配置开关 schema | 定义「有哪些开关、取值范围、默认值、依赖关系」，本身不含某次构建的取值 | `Kconfig`、`Kconfig.*`；内容 `config X` / `menuconfig` / `choice` / `depends on` | S7（主）、S3 |
| **C8** | 设备树 / 硬件描述 | 描述板上有哪些设备、地址、中断、兼容性 | `*.dts`、`*.dtsi`、`*.overlay`；OHOS 的 `*.hcs`（HDF 硬件配置）；首行 `/dts-v1/;` | S7（弱）、S4（弱） |

**几处容易混的边界：**

| 疑问 | 答案 |
| ---- | ---- |
| `Kconfig` 和 `defconfig` 为什么分开？ | `Kconfig` 是**定义有哪些开关**（schema），`defconfig` 是**这次选了哪些值**。前者给 C7，后者给 C4。S7 两边都要。 |
| 链接参数（`libs=`/`LDFLAGS`）算 C5 吗？ | 不算。它写在构建描述里，归 C2（顺带喂 S5）。C5 只收**专门的链接脚本/符号表**。 |
| `.bb` 到底算 C2 还是 C3？ | 两个都算。它既是构建脚本（`do_compile`），又是包清单（`DEPENDS`/`SRC_URI`/`LICENSE`）。重叠是设计，不是错误。 |
| `AndroidManifest.xml` 算 C3 吗？ | **不算。** 那是 App 的清单，不是构建单元清单。这是「同名不同义」的典型。 |
| `west.yml` / `bblayers.conf` / `.repo/manifest.xml` 去哪了？ | 有意不设类。它们描述「工程由哪些仓组成」，原本服务 S2；S2 已从研究范围移除，硬塞给 S3 属于过度联想。 |

### 33.2.3 映射矩阵：每个大类喂谁

「主」= 该大类的主要消费者；「次」= 可能承载，但别指望它一定全。

| 大类 | S1 | S3 | S4 | S5 | S6 | S7 |
| ---- | -- | -- | -- | -- | -- | -- |
| C1 脚本 | **主** | — | 次（`CC`/`CROSS_COMPILE`） | 次（脚本里的 `-l`） | 次（`pushd`/`shopt` 缺口） | — |
| C2 构建描述 | **主**（`action`/recipe/自定义命令） | 次（目标清单） | **主** | **主** | — | 次（`target_cpu`/`ARCH`） |
| C3 模块清单 | 次（`Build-Depends`、`install_requires`） | **主** | 次（`Architecture:`） | 次（`shared_libs`） | 次（对外头文件） | — |
| C4 板级配置 | 次 | 次（产品包含的模块） | **主** | 次（`board_ld_flags`/`force_link_libs`） | — | **主** |
| C5 链接符号 | — | — | — | **主** | — | 次（内存布局） |
| C6 C 源码 | 次（极少，`system()`） | — | — | — | **主** | — |
| C7 开关 schema | — | 次（开关定义的模块） | — | — | — | **主** |
| C8 设备树 | — | — | 次（CPU/compatible） | — | — | 次（板级硬件） |

### 33.2.4 三项核对

**核对一：每一行（每个 S）至少有一个「主」。**

S1→C1/C2；S3→C3；S4→C2/C4；S5→C2/C5；S6→C6；S7→C4/C7。**无空行。**

**核对二：每一列（每个大类）至少有一个 S。** 见上表，八列均非空。

**核对三：`08` §19.9 列出的盲区是否都有落点。**

| 盲区 | 原来 | 现在 |
| ---- | ---- | ---- |
| `*.py` 没有 kind | S1 的 Python 路径不可达 | C1 |
| `*.map` 没有 kind | S5 的符号导出一半丢失 | C5 |
| `*.dts` 没人认领 | 设备树里的板级声明丢失 | C8 |
| 非 `vendor/*` 的产品配置 | S3/S4/S7 读不到 | C4（按「声明了板级/产品取值」认，不按路径认） |
| `ohos.build` | 2.2/3.0 组件全漏 | C3（`08` 已实测） |

**核对三说明：** 换一套按信息内容定义的大类，五个历史盲区里四个自动有了落点。这正是「不要按文件名分类」的收益。

## 33.3 各系统的载体

每张表只列**代表性**载体，不求穷尽；穷尽清单在各自的 carrier 层（`08` 的写法），不进本文。

### 33.3.1 OpenHarmony（B 级，来自 `08`）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `build/build_scripts/*.sh`、`build/hb/**/*.py`、`*.sh`、`*.py` | 后缀 + shebang |
| C2 | `BUILD.gn`、`*.gni`、`Makefile`、`*.mk` | 整名 / 后缀 |
| C3 | `bundle.json`、`ohos.build`、`productdefine/common/{products,inherit,base}/*.json`、`build/lite/product/*.json`、`build/lite/platform/*/platform.json` | 整名 + 路径 |
| C4 | `vendor/*/*/config.json`、`config.gni`、`productdefine/common/device/*.json`、`*_defconfig`、`*.para`、`*.cfg`、`*.config` | 路径 + 键名 |
| C5 | `*.ld`、`*.lds`、`*.map` | 后缀为主，`.map` 需含 `{ global:` |
| C6 | `*.c/.cc/.cpp/.h/.hpp` | 后缀 |
| C7 | `Kconfig*`、`kernel/linux/config/**/*_defconfig` | 整名 / 路径 |
| C8 | `*.dts`、`*.dtsi`、`*.hcs` | 后缀 |

**四个「后缀认不出」的 OHOS 载体**（实测计数见 §33.8）：`.hcs` 是 HDF 驱动的硬件配置（26 个），`.para` 是系统参数取值（20 个），`.cfg`（20 个）与 `.config`（18 个）是开关取值。这四个后缀在通用后缀表里都没有位置，**名字规则必然漏掉**，只能靠内容锚点（`hdf_manager` / `name=` / `CONFIG_*=y`）补。

### 33.3.2 Android / AOSP（A 级 + 仓库镜像 [R01][R02] + B 级 [R20]）

| 大类 | 载体 | 判据 | 备注 |
| ---- | ---- | ---- | ---- |
| C1 | `build/envsetup.sh`、`*.sh`、`*.py`、`build/soong/**/*.go` | 后缀 / shebang | Go 代码是构建系统的实现，不是被扫描的脚本，**不路由** |
| C2 | `Android.bp`、`Android.mk`、`*.mk`、`build/make/core/*.mk` | 整名 / 后缀 | `Android.bp` 是本系统最核心的载体 |
| C3 | `Android.bp` 的模块段（`cc_library`/`cc_binary`/`prebuilt_etc`/`filegroup`）、`Android.mk` 的 `LOCAL_*` | 整名 + 内容模块类型 | `AndroidManifest.xml` **不算** |
| C4 | `BoardConfig.mk`、`device/*/*.mk`、`build/make/target/product/*.mk` | 整名 + 内容 `TARGET_*`/`PRODUCT_*` | `PRODUCT_PACKAGES` 是「产品包含哪些模块」 |
| C5 | `*.ld`/`*.lds`、`libc.map.txt` 一类版本脚本 | 后缀 + 内容 | |
| C6 | `*.c/.cc/.cpp/.h` | 后缀 | |
| C7 | 仅内核与部分外部项目有 `Kconfig` | 整名 | 用户态不用 Kconfig |
| C8 | `device/**/kernel-dts/*.dts`、内核 `arch/*/boot/dts` | 后缀 | |

**B 级实测**（`aosp-mirror/platform_build` 的 `core/`，230 个文件）：

- **主体是 `.mk`**：`core/` 下近 200 个 `.mk`（`base_rules.mk`、`binary.mk`、`board_config*.mk`、`clang/HOST_*.mk`…），一个后缀覆盖了构建描述与板级配置两类；根目录的 `Android.bp` 是 Soong 入口。
- **`.flags` 不是载体**：`core/proguard.flags`、`proguard.jacoco.flags` 是 ProGuard 的 keep 规则（`-keep class ...`），实测 5 个。路由时必须排除，否则会被当成配置。
- **`.xml` 也不是**：`core/*_test_config.xml`、`instrumentation_test_config_template.xml` 是测试配置，不是 `AndroidManifest.xml`（后者本来也不算 C3）。
- `buildspec.mk.default` 是给用户抄的模板，不是实际取值——`default` 后缀可作「模板」信号。
- 实测这批文件里没有 `BoardConfig.mk`（它在 `device/` 仓里），所以板级规则只能靠文档证据。

### 33.3.3 Yocto / BitBake（A 级 [R03][R04] + B 级 [R15]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `scripts/*.py`、`*.sh`、`lib/bb/**`（BitBake 本体）、recipe 旁的 `files/` 下 init 脚本 | 后缀 / shebang |
| C2 | `*.bb`、`*.bbappend`、`*.bbclass`、`*.inc` | 后缀 |
| C3 | `*.bb`/`*.inc` 的 `SRC_URI`/`DEPENDS`/`RDEPENDS`/`LICENSE`/`do_install` | 后缀 + 变量名 |
| C4 | `conf/machine/*.conf`、`conf/distro/*.conf`、`conf/local.conf`、`conf/bblayers.conf`、`meta/conf/machine/include/*.inc`、包内的 `*.cfg` 片段 | 路径 + `MACHINE`/`TUNE_*`；`*.cfg` 靠内容 `CONFIG_*=y` |
| C5 | recipe 里的 `LDFLAGS`/`LDLIBS` | 变量名 |
| C6 | `*.c/.h` | 后缀 |
| C7 | 少见（Yocto 用 `PACKAGECONFIG` 而非 Kconfig） | — |
| C8 | 内核 recipe 里的 `*.dts` | 后缀 |

**B 级实测**（`poky` 的 `scarthgap` 分支，稀疏检出 `meta/conf` + `meta/recipes-core/busybox`）：

- `meta/conf/machine/qemuarm64.conf` 前 3 行是 `#@TYPE: Machine` / `#@NAME:` / `#@DESCRIPTION:`。**这是比路径更硬的锚点**——文件被挪出 `conf/machine/` 也认得出是板级配置。
- `busybox_1.36.1.bb` 只有 `require busybox.inc` 加一长串 `SRC_URI`；真正的 `DEPENDS`/`LICENSE`/`do_install` 在 `busybox.inc` 里。**后缀能认出 C2/C3，但要读全信息必须跟进 `require` 链**——这一条对所有配方式工程都成立。
- `busybox/defconfig` 首段是 `# Automatically generated make config: don't edit`。生成物标记，与内核 `.config`、NuttX `defconfig` 是同一句话。
- `busybox/*.cfg`（`mdev.cfg`、`syslog.cfg` 等 12 个）内容是纯 `CONFIG_MDEV=y`，后缀不是 `.config`。**名字规则漏，内容锚点能补。**
- `files/mdev`、`files/rcS`、`files/inetd` 首行 `#!/bin/sh` → C1；`files/*.service.in` 是 systemd 单元模板（`.in` 是占位符，不是源码）。
- `meta/conf/bitbake.conf` 里 `TARGET_ARCH = "${TUNE_ARCH}"`、`MACHINE_ARCH`、`PACKAGE_ARCHS` 集中出现——**工具链与架构信息可以只在一个文件里汇总**，不必逐个 recipe 扫。

### 33.3.4 Debian（A 级 [R05][R06] + B 级 [R21]）

| 大类 | 载体 | 判据 | 备注 |
| ---- | ---- | ---- | ---- |
| C1 | `debian/rules`（Makefile）、`debian/*.postinst`/`*.preinst`（shell）、`debian/tests/*` | shebang / 后缀 | `debian/rules` 同时是 C2 |
| C2 | `debian/rules` | 路径 `debian/` + 整名 `rules` | |
| C3 | `debian/control`、`debian/*.install`、`debian/*.links`、`debian/changelog` | 路径 `debian/` | `control` 是 RFC822 式段落，字段 `Source`/`Package`/`Depends`/`Build-Depends` |
| C4 | `debian/control` 的 `Architecture:`/`Build-Profiles`、`debian/rules` 里的 `DEB_HOST_ARCH` | 字段名 | |
| C5 | **`debian/*.symbols`**、`debian/*.shlibs` | 路径 + 后缀 | Debian 独有的符号导出载体，正好补 S5 |
| C6 | 源码本身 | 后缀 | |
| C7/C8 | — | — | Debian 源码包没有这两类 |

**B 级实测**（`salsa.debian.org/debian/hello`，29 个文件）：

- `debian/control` **只能靠路径认**：同名文件在别处不是包清单，内容里的 `Source:`/`Package:` 是第二道保险。
- `debian/rules` 首行是 `#!/usr/bin/make -f`——**它是 Makefile，不是普通脚本**。只看 shebang 会判成 C1，按路径 `debian/rules` 判 C2 才对（C2 的 classes 本来就含 S1，不会丢信息）。
- **Autotools 整族后缀表里都没有**：`configure.ac`、`Makefile.am`、`Makefile.in`、`aclocal.m4` 全都是构建描述。这四类在别的老工程里也大量存在，是这次实测补出来的缺口。
- **大小写陷阱**：这个包的 `config.in`（小写）是 autoheader 生成的 C 头模板（`#undef COPYRIGHT_YEAR`）；Buildroot 的 `Config.in`（大写 C）才是 Kconfig。**同名不同义，只能大小写敏感地判**，不能先 `.lower()`。
- `hello.1`、`NEWS`、`INSTALL`、`ABOUT-NLS` 等不路由。

### 33.3.5 CMake（A 级 [R07] + B 级 [R22]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `*.cmake` 脚本模式（`cmake -P`）、`*.sh` | 后缀 |
| C2 | `CMakeLists.txt`、`*.cmake` | 整名 / 后缀 |
| C3 | 无标准清单；`project()` + `install()` + CPack 是弱等价物 | 内容命令 |
| C4 | toolchain 文件（`*.cmake`）、`CMakePresets.json`、`CMAKE_*` 缓存变量 | 整名 / 变量名 |
| C5 | `target_link_libraries()`、`link_options`、`*.ld` | 内容命令 / 后缀 |
| C6 | `*.c/.h` | 后缀 |
| C7 | `option()`、`set(... CACHE ...)`——写在 C2 里，不单独成类 | 内容命令 |
| C8 | `*.dts` | 后缀 |

**B 级实测**（`fmtlib/fmt` 的 `include/` + `src/` + `test/`，96 个文件）：

- 载体只有两种：`CMakeLists.txt`（C2）和 `*.h`/`*.cc`（C6）。`test/cuda-test/*.cu` 是 CUDA，**不在 C6 的 `.c/.h` 范围**，不路由。
- 剩余 4 个无后缀文件（`.clang-format` 一类）读内容后仍不命中——正确，它们不是载体。
- **一个误报教训**：最初拿 `project(` 当 CMake 的内容锚点，结果把普通 JSON 里出现 `project(foo)` 这个**字符串**的文件判成了 C2。改成 `cmake_minimum_required` / `add_executable(` / `add_library(` / `target_link_libraries(` 才稳——`project(` 太泛，Meson 也用。

### 33.3.6 Meson（A 级 [R08] + B 级 [R23]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `*.sh`、`scripts/` | 后缀 / 路径 |
| C2 | `meson.build`、`meson_options.txt` / `meson.options` | 整名 |
| C3 | `project()` + `dependency()`；`subprojects/*.wrap` 描述外部依赖 | 内容命令 / 后缀 |
| C4 | cross file / native file（`*.ini`）、`-D` 选项 | 路径 + 后缀 |
| C5 | `link_with`、`link_args`、`dependency()` | 内容命令 |

| C8 | `*.dts` | 后缀 |

**B 级实测**（`mesonbuild/meson` 的 `mesonbuild/` + `test cases/common`，1878 个文件）：

- `meson.build` 有 **525 个**，全部靠整名判 C2——这个后缀（`.build`）太容易被别的系统占用，**只能整名匹配**。
- `subprojects/*.wrap` 是外部依赖声明（`[wrap-file]` + `source_url`/`directory`/`revision`），共 20 个 → C3。**后缀表里原来没有 `.wrap`**，是这次补的。
- `test cases/` 下大量 `.json` 是测试规格，不是载体（72 个未路由）。
- 两个误报，都是实测抓出来的：`.pylintrc` 被「`key=value`」规则判成 C4；某个测试 JSON 里的 `project(` 被 CMake 锚点命中。处置：**删掉 `key=value` 这条弱规则**（`.para` 已由后缀覆盖），**收紧 CMake 锚点**。
- 内容层在这棵树上只读了 112 个文件（占 6%），却把 `.wrap` 之外的东西基本判对——说明「先名字、后内容」的成本控制是有效的。

### 33.3.7 Buildroot（A 级 [R09] + B 级 [R16]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `support/scripts/*.py`、`board/*/*.sh`、`*.sh` | 后缀 |
| C2 | `package/<pkg>/<pkg>.mk`、顶层 `Makefile`、`*.mk` | 后缀 + 路径 |
| C3 | `package/<pkg>/Config.in`、`<pkg>.mk` 里的 `VERSION`/`SITE`/`DEPENDENCIES` | 路径 + 变量名 |
| C4 | `configs/*_defconfig`、`board/*/`、`BR2_*` 选项、`toolchain/` | 路径 + 变量前缀 |
| C5 | `.mk` 里的 `*_LIBS` | 变量名 |
| C6 | 外部源码，树内少 | 后缀 |
| C7 | `Config.in`（Kconfig 语法） | 整名 + 内容 |
| C8 | `board/*/*.dts` | 后缀 |

**B 级实测**（`package/busybox` 一个包 + `docs/manual`）：

- 一个包目录里同时住着 `Config.in`（开关 schema，C7）、`busybox.mk`（构建描述，C2/C3）、`busybox.config` 与 `busybox-minimal.config`（取值，C4）、12 个 `.patch`、以及 `S01logging`/`S10mdev` 一类 init 脚本（C1）。**包目录 = 一个垂直切片**，这正是按目录聚合路由的理由。
- `.mk` 里的 `BUSYBOX_CFLAGS = $(TARGET_CFLAGS)` 与 `BUSYBOX_CFLAGS += ...`（[`package/busybox/busybox.mk`](https://github.com/buildroot/buildroot/tree/master/package/busybox) 第 31、94 行）证明**包级编译选项确实存在**，但它由包自己定义——`package/pkg-generic.mk`（1338 行）里一次都没有引用 `CFLAGS`，通用包基础设施不消费这个变量。所以「`<PKG>_CFLAGS`」只能作为**弱**同义键，不能当作 Buildroot 的通用约定。
- `.patch` 文件量大（一个包十几个），**不属于八大类**：它们不改声明，只改外部源码。路由时要显式排除，否则会淹没 C6。

### 33.3.8 Zephyr（A 级 [R10] + B 级 [R17]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `scripts/*.py`、`*.sh` | 后缀 |
| C2 | `CMakeLists.txt`、`*.cmake` | 整名 / 后缀 |
| C3 | `west.yml`、`zephyr/module.yml`、CMake target | 整名 |
| C4 | `boards/<vendor>/<board>/<board>_defconfig`、`soc/*/Kconfig.defconfig`、`prj.conf` | 路径 + 后缀 |
| C5 | CMake `target_link_libraries` | 内容命令 |
| C6 | `*.c/.h` | 后缀 |
| C7 | `Kconfig*`、`Kconfig.defconfig` | 整名 |
| C8 | `*.dts`、`*.dtsi`、`*.overlay` | 后缀 + 首行 |

**B 级实测**（`zephyrproject-rtos/example-application`）：

- 仓库根只有 6 个文件：`CMakeLists.txt`、`Kconfig`、`west.yml`、`README.md`、`LICENSE`、`.gitignore`。**「Zephyr 模块」的最小形态就是一个 CMake 入口 + 一个 Kconfig 入口**，两者都靠 `zephyr/module.yml` 声明。
- `CMakeLists.txt` 第 1–2 行是版权 + `SPDX-License-Identifier: Apache-2.0`，第 5–6 行仍是注释——**认格式信号被推到第 8 个有效行之后**。这正是 §33.5.3 要求「先跳注释再取 2 KB」的实证。
- `Kconfig` 只有 3 行有效内容（`rsource "drivers/Kconfig"` / `rsource "lib/Kconfig"`）——**这个文件本身不含任何开关定义**，只是入口。按 `Kconfig` 整名路由到 C7 没有错，但不能指望从入口文件直接读出一组开关，必须跟 `rsource`。
- `west.yml` 描述「工程由哪些仓组成」，按 §33.2.2 的裁决**不设类、不路由**（S2 已出范围）。

### 33.3.9 Linux 内核（A 级 [R11] + B 级 [R24]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `scripts/*.sh`、`scripts/*.py` | 路径 + 后缀 |
| C2 | `Makefile`、`Kbuild`、`*.mk` | 整名 / 后缀 |
| C3 | 无中央清单；`obj-$(CONFIG_X)` + `Kconfig` 组合是等价物 | — |
| C4 | `arch/<arch>/configs/*_defconfig`、`.config` | 路径 + 后缀 |
| C5 | `vmlinux.lds.S`、`Module.symvers`、`*.lds` | 整名 / 后缀 |
| C6 | `*.c/.h`、`*.S` | 后缀 |
| C7 | `Kconfig`、`Kconfig.*` | 整名 |
| C8 | `arch/*/boot/dts/**/*.dts` | 路径 + 后缀 |

**B 级实测**（`torvalds/linux` 稀疏检出 `arch/arm64/boot/dts/qcom` + `scripts/kconfig` + `kernel/configs`，1161 个文件）：

- `.dts`/`.dtsi` 约 1000 个，后缀一条就全收；**`.dtso`（overlay）30 个**是 6.x 新增的后缀，通用后缀表里没有，这次补上。
- `Kconfig` 家族照旧走整名；`scripts/kconfig/tests/**` 里有一批**无后缀**文件（`config`、`expected_config`），内容是 `CONFIG_*=y`——只能靠内容判 C4。这正是「名字认不出就读 2 KB」的用武之地。
- `scripts/` 下 33 个无后缀脚本（`bloat-o-meter`、`checkpatch`…）靠 shebang 判 C1。
- **`.xpm` 不是载体**：`drivers/video/logo/*.xpm` 是启动图标，实测 13 个。凡「后缀像配置、其实是资源」的，都要在噪声清单里挡掉。

### 33.3.10 RT-Thread（B 级 [R18]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `tools/*.py`（ENV 工具）、`*.sh` | 后缀；**BSP 根的 `rtconfig.py` 是反例，见下** |
| C2 | `SConscript`、`SConstruct`、`makefile.targets` | 整名 |
| C3 | `SConscript` 的 `DefineGroup(name, src, depend, **parameters)`；包管理器的 `PKG_<name>_VERSION` | 内容命令 / 变量名 |
| C4 | `rtconfig.py`（`ARCH`/`CPU`/`CROSS_TOOL`/`PREFIX`）、`.config`、`rtconfig.h` | 内容键名 |
| C5 | `DefineGroup(..., LIBS=[...])`、链接脚本 | 内容参数 |
| C6 | `*.c/.h` | 后缀 |
| C7 | `Kconfig`（`config RT_USING_*`、`menuconfig BSP_USING_*`） | 整名 + 内容 |
| C8 | 部分 BSP 的 `*.dts` | 后缀 |

**B 级实测**（`bsp/stm32/stm32f429-fire-challenger` 一块板）：

- 板目录里同时有 `SConscript`、`SConstruct`、`rtconfig.py`、`rtconfig.h`、`.config`、`Kconfig`、`makefile.targets`，**以及 12 个 Keil/IAR 工程文件**（`project.uvprojx`、`template.ewp` 等）。后者是 IDE 工程，不是我们的载体——**噪声来源之一，且后缀极杂**。
- `rtconfig.py` 名字是 `.py`，内容却是 `BUILD = 'debug'`、`PREFIX = 'arm-none-eabi-'`、`CC = PREFIX + 'gcc'`——**它从不被 Python 执行，是被 SCons 当配置导入的**。按后缀路由会把它判成 C1（脚本），实际是 C4（工具链配置）。这是「后缀最不可迁移」的又一实例。
- `rtconfig.h` 由 `.config` 生成（`#define SOC_STM32F429IG`），`.config` 首行直接就是 `CONFIG_SOC_STM32F429IG=y`——**没有注释头，第一个有效行就在第 1 行**。
- `SConscript` 首行 `# for module compiling`，随后 `import os` / `Import('RTT_ROOT')`——Python 语法，但不是可执行脚本，且**没有后缀**，名字规则给不出任何线索。
- `Kconfig` 用 4 空格缩进（`config SOC_STM32F429IG` 下面缩进 4 格的 `bool`），与 Linux Kconfig 的 tab 缩进写法不同。解析器要按「缩进更深即子项」处理，不能死认 tab。

### 33.3.11 NuttX（B 级 [R19]）

| 大类 | 载体 | 判据 |
| ---- | ---- | ---- |
| C1 | `tools/*.sh`、`tools/*.py` | 后缀 |
| C2 | `Makefile`、`Make.defs`、`CMakeLists.txt` | 整名 |
| C3 | `CONFIGURED_APPS`（`Make.defs`）、`apps/<name>/Kconfig` | 变量名 + 路径 |
| C4 | `boards/<arch>/<chip>/<board>/configs/<cfg>/defconfig`、`boards/**/include/board.h`、`scripts/Make.defs` | 路径 + 键名 |
| C5 | `ld.script`、`memory.ld`、`kernel-space.ld`、`user-space.ld` | 整名 / 后缀 |
| C6 | `*.c/.h` | 后缀 |
| C7 | `Kconfig`（**每个目录一份**） | 整名 + 内容 |
| C8 | 无设备树；板级硬件写在 `board.h` 与 `src/*.c` 里 | — |

**B 级实测**（`boards/arm/stm32f4/stm32f4discovery` 一块板）：

- `configs/nsh/defconfig` 前 7 行是 `# This file is autogenerated: PLEASE DO NOT EDIT IT.` + `make savedefconfig` 提示——**又是生成物标记**，且文件名是**无后缀的 `defconfig`**，`*_defconfig` 这条通用规则**匹配不到它**（规则要写成「名字等于 `defconfig` 或以 `_defconfig` 结尾」）。
- `defconfig` 内容 `CONFIG_ARCH="arm"`、`CONFIG_ARCH_BOARD="stm32f4discovery"`——板名直接写在取值里，**从文件内容就能确定这块板是哪个**，不依赖目录名。
- `include/board.h` 前 20 行是 Apache 许可证头，之后才是 `BOARD_*` 宏。**板级取值写在 C 头文件里**，所以 C4 与 C6 在这里重叠：按后缀是 C6，按内容键名是 C4。
- `scripts/` 下四个链接脚本：`ld.script`（无 `.ld` 后缀）、`memory.ld`、`kernel-space.ld`、`user-space.ld`。**后缀规则只覆盖后三个**，`ld.script` 只能靠整名。

### 33.3.12 小结：这张表说明了什么

- **C2 和 C6 几乎每个系统都有**，只是名字不同。
- **C3 是最分裂的一类**：十一个系统十一种写法，没有一种能覆盖另一种。
- **C5 有一半藏在 C2 里**（链接参数写在构建描述中），只有链接脚本和符号表是独立载体。
- **C7 只出现在「内核系」系统**（Linux、Zephyr、Buildroot、RT-Thread、NuttX、OHOS）。
- **C8 只出现在「嵌入式系」系统**，桌面/服务端系统没有。NuttX 是例外：它把板级硬件写在 `board.h` 里，没有设备树。
- **两个 RTOS（RT-Thread、NuttX）把「命名不可靠」展示得最充分**：`rtconfig.py` 不是脚本、`defconfig` 没有 `_defconfig`、`ld.script` 没有 `.ld`——三条都是「整名 > 后缀」的直接证据。

## 33.4 命名与位置特征：横向对比

### 33.4.1 五种特征

| 代号 | 特征 | 例子 | 稳定性 |
| ---- | ---- | ---- | ------ |
| F1 | 后缀 | `.gn`、`.bp`、`.bb` | 生态内稳定，跨生态几乎不迁移 |
| F2 | 完整文件名 | `bundle.json`、`CMakeLists.txt` | 生态内很稳定，跨生态不迁移 |
| F3 | 文件名里的**词** | 名字含 `build`/`config`/`board`/`deps` | **部分可迁移** |
| F4 | 目录名 / 路径 | `vendor/`、`device/`、`scripts/`、`debian/` | **部分可迁移**，但词义会漂移 |
| F5 | 内容锚点（首个语句/键名） | `ENTRY(`、`target_link_libraries(`、`DEPENDS =`、`config X` | **最可迁移** |

### 33.4.2 可迁移性排序

「系统数」按本次调研的 11 个系统计（OHOS、AOSP、Yocto、Debian、CMake、Meson、Buildroot、Zephyr、Linux、RT-Thread、NuttX）；引用 U-Boot / glibc 时在单元格里注明「旁证」，不计入系统数。

| 特征 | 系统数 | 出现在 | 分级 |
| ---- | ------ | ------ | ---- |
| `#!` shebang | 11 | 全部 | **通用** |
| `*.c` / `*.h` / `*.cc` / `*.cpp` | 11 | 全部 | **通用** |
| `-l<name>` 形式的库引用 | 11 | 全部 | **通用** |
| 名字里含 `build`/`config`/`board`/`toolchain`/`deps` | 11 | 全部 | **通用** |
| `Makefile` | 10 | 除 Meson 外全部 | **通用** |
| `Kconfig` | 6 | Linux、Zephyr、Buildroot、RT-Thread、NuttX、OHOS | **通用（内核系）** |
| `*_defconfig` | 6 | OHOS、Linux、Zephyr、Buildroot、U-Boot、NuttX | **通用（内核系）** |
| `LDFLAGS` / `LDLIBS` | 6 | OHOS、Linux、Yocto、Buildroot、RT-Thread、U-Boot | **通用** |
| `ENTRY(` / `SECTIONS` | 6 | OHOS、Linux、AOSP、Zephyr、RT-Thread、NuttX | **通用** |
| `*.ld` / `*.lds` | 6 | 同上（NuttX 另有 `ld.script` 无后缀，见末行） | **通用** |
| `CROSS_COMPILE` / `CC=` | 5 | OHOS、Linux、U-Boot、RT-Thread、Buildroot | **通用** |
| 目录 `scripts/` | 5 | OHOS、Linux、Zephyr、Buildroot、Yocto | **通用** |
| `*.dts` / `*.dtsi` | 4 | Linux、Zephyr、AOSP、OHOS | **通用（嵌入式）** |
| `*.mk` | 4 | OHOS、AOSP、Buildroot、Linux | **半通用** |
| `CMakeLists.txt` | 3 | CMake 生态、Zephyr、NuttX | **半通用** |
| `ARCH=` | 3 | Linux、U-Boot、Zephyr（`CONFIG_ARCH`） | **半通用** |
| `TARGET_*` | 2 | AOSP、OHOS（小写 `target_cpu`） | **半通用** |
| 目录 `device/` | 2 | AOSP、OHOS | **半通用** |
| 目录 `vendor/` | 2 | AOSP、OHOS | **半通用** |
| `*.map` / 版本脚本 / `*.symbols` | 3 | OHOS、glibc 系、Debian | **半通用** |
| `Android.bp` / `*.bp` | 1 | AOSP | **专属** |
| `*.bb` / `*.bbappend` | 1 | Yocto | **专属** |
| `bundle.json` / `ohos.build` / `productdefine/**` | 1 | OHOS | **专属** |
| `debian/` 整个目录 | 1 | Debian | **专属** |
| `conf/machine/*.conf` / `TUNE_*` | 1 | Yocto | **专属** |
| `package/*/Config.in` | 1 | Buildroot | **专属** |
| `prj.conf` / `west.yml` / `module.yml` | 1 | Zephyr | **专属** |
| `SConscript` | 1 | RT-Thread | **专属** |
| `*.gni` / `config.gni` | 1 | OHOS | **专属** |
| `#@TYPE: Machine` 一类魔术注释 | 1 | Yocto（`conf/machine/*.conf` 头三行） | **专属**，但**内容锚点强于路径** |
| 无后缀整名：`defconfig`（NuttX）、`ld.script`（NuttX）、`bundle`（Yocto） | 1 | NuttX / Yocto | **专属**，证明「整名 > 后缀」 |

**这一版新增的两行说明了一个共同点：** 命名最不可靠的地方往往**没有后缀**。有后缀时可退到后缀表；没有后缀时只剩两条路——整名精确匹配，或读内容。这也是 §33.8.1 里 `other` 中「无后缀 42 个」必须逐个看的原因。

### 33.4.3 从 OHOS 的经验里能迁移什么

把 `08` 里 OHOS 的规则逐条改写成「按长相认」，能直接落到别的系统上：

| OHOS 原规则 | 改写后的写法 | 在哪些系统命中 |
| ----------- | ------------ | -------------- |
| `vendor/*/config.json` = 板级配置 | 路径含 `vendor/` 或 `device/`，且（名字含 `config`/`board`/`machine`，或内容含 `target_cpu`/`TARGET_ARCH`/`MACHINE`） | OHOS `config.json`；AOSP `BoardConfig.mk`；Yocto `conf/machine/*.conf` |
| `bundle.json` = 组件清单 | 结构化文件里同时出现模块名与依赖（JSON `name`+`dependencies`，或 `Package:`+`Depends:`，或 `DEPENDS =`） | OHOS `bundle.json`；Debian `control`；Yocto `.bb`；npm `package.json` |
| `*.ld` = 链接脚本 | 后缀 `.ld`/`.lds`，或内容含 `ENTRY(`/`SECTIONS` | OHOS、Linux、AOSP、Zephyr、RT-Thread |
| `config.gni` 的 `board_cpu` | 内容含 `board_cpu`/`target_cpu`/`TARGET_ARCH`/`ARCH=`/`BR2_<arch>` 中的任一个 | OHOS、AOSP、Linux、Buildroot、Zephyr |
| `BUILD.gn` 的 `libs`/`ldflags` | 内容含 `libs =`/`ldflags =`/`shared_libs`/`shared_libs`/`target_link_libraries(`/`LDLIBS`/`LDFLAGS` | OHOS、AOSP、CMake、Linux、Buildroot、Yocto |
| `Kconfig` + `*_defconfig` | 整名 `Kconfig*` + 后缀 `*_defconfig` | OHOS、Linux、Zephyr、Buildroot |

**结论：** 能迁移的是**「这类信息在文件里长什么样」**，不能迁移的是**「这个文件叫什么」**。`bundle.json` 换个系统就没了，但「模块名 + 依赖」这个组合到处都在。

### 33.4.4 迁移的三个坑

| 坑 | 例子 | 处置 |
| -- | ---- | ---- |
| **同名不同义** | `AndroidManifest.xml`（App 清单）vs `.repo/manifest.xml`（仓清单）；`vendor/` 在 AOSP/OHOS 是板厂，在 JS 生态是第三方依赖 | 路径词只当**弱**信号；强信号必须是内容键名 |
| **同义不同名** | 同一个「产品包含哪些模块」：`PRODUCT_PACKAGES`（AOSP）、`IMAGE_INSTALL`（Yocto）、`BR2_PACKAGE_*`（Buildroot）、`components`（OHOS 产品 JSON） | 建一个「同义键名表」，这是规则阶段的第一件事 |
| **约定不是强制** | 任何系统里都有人不按约定命名；`Makefile` 可以被叫 `GNUmakefile` | 弱信号凑够两个才判；单靠名字的规则一律标低置信 |

- **Buildroot 的编译选项**——已核对：包级 `<PKG>_CFLAGS` **存在**（`busybox.mk` 第 31、94 行），但通用包基础设施 `pkg-generic.mk` 不消费它，所以只能当**弱**同义键。前版写的「实际多以全局 `TARGET_CFLAGS` 生效」方向对、结论偏严。
- **OHOS 的开关定义**——已核对：`declare_args()` 在 23 个子仓里只出现在 7 个文件（`hilog.gni` 等），确认是 GN 语言设施而非 OHOS 约定。当作「开关定义」的锚点时，必须叠加路径（`build/config`）或 `BUILD.gn` 上下文，否则会把任何 GN 参数当成产品开关。
- **Debian 的开关取值**——**仍未核对**：`sources.debian.org` 在本机返回反爬挑战页，取不到真实 `debian/control`。维持「文档级」。后续可用 `apt-get source` 在 Debian 机器上补。

## 33.5 信号出现在文件的哪里

这一节直接回答「到底要不要扫全篇」。

### 33.5.1 先分清两件事

| | 认格式（L1 做的事） | 找对象（L2 做的事） |
| -- | ------------------ | -------------------- |
| 问题 | 这是什么类型的文件 | 这个文件里声明了什么 |
| 信号 | 首行、首个有效语句、第一个键名 | `libs =`、`#include`、`deps` 的具体值 |
| 位置 | **几乎都在开头** | **可能在任何位置** |

所以「要不要扫全篇」这个问题，对 L1 的答案是**不用**，对 L2 的答案是**必须**。两者不矛盾——L1 只负责把文件送到对的提取器门口。

### 33.5.2 认格式的信号位置（分类别估计）

| 大类 | 认格式的信号 | 典型位置 |
| ---- | ------------ | -------- |
| C1 脚本 | shebang | 第 1 行 |
| C2 构建描述 | `project(` / `target(` / `cc_library {` / `do_compile()` / 首个变量赋值 | 第 1–20 个有效行 |
| C3 模块清单 | 第一个键 / 第一个段落字段（`Source:` / `name:` / `DEPENDS =`） | 第 1–10 个有效行 |
| C4 板级配置 | `TARGET_*` / `BR2_*` / `MACHINE` / `target_cpu` | 第 1–50 个有效行 |
| C5 链接符号 | `ENTRY(` / `SECTIONS` / `{ global:` / `OUTPUT_FORMAT(` | 第 1–20 个有效行 |
| C6 C 源码 | `#include` / `#define` / 首个声明 | 第 1–30 个有效行 |
| C7 开关 schema | `config X` / `menuconfig` / `choice` | 第 1–10 个有效行 |
| C8 设备树 | `/dts-v1/;` / `/ {` | 第 1 行 |

### 33.5.3 一个必须处理的干扰：许可证头

现代项目普遍在文件开头放 20–40 行 SPDX/版权注释，**正好吃掉 1–2 KB**。如果直接取前 2 KB，很可能只读到一段注释。

处置：**先跳过开头连续的注释块和空行，再从第一个有效行开始取 2 KB。** 顺带一个副产品：`SPDX-License-Identifier` 本身是「这是现代源码文件」的弱信号。

### 33.5.4 实测：2 KB 到底够不够

**测法。** 对 23 个真实 OHOS 子仓的 1766 个文件（已排除 `.git`/`.repo`/`out`/`__pycache__`），按 §33.5.3 的规则跳过开头连续的空行与注释行，记录**第一个有效行**落在第几行、距文件头多少字节。工具：[`tests/tools/l1_survey.py`](../tests/tools/l1_survey.py)（`--root <源码树> --csv <明细>`），2026-10-26 跑。

**按行（n = 文本文件）：**

| 第一个有效行 | 文件数占比 | 累计 |
| ------------ | ---------- | ---- |
| 第 1 行 | 27.5% | 27.5% |
| ≤5 行 | 8.5% | 36.0% |
| ≤10 行 | 0.6% | 36.6% |
| ≤20 行 | 18.1% | 54.7% |
| ≤30 行 | 27.5% | 82.2% |
| ≤50 行 | 15.1% | **97.3%** |
| >50 行 | 2.7% | 100% |

**按字节（同一批文件，第一个有效行的起始偏移）：**

| 偏移 | 占比 | 累计 |
| ---- | ---- | ---- |
| ≤512 B | 36.9% | 36.9% |
| ≤1 KB | 42.1% | 79.0% |
| ≤2 KB | 18.7% | **97.7%** |
| ≤4 KB | 1.2% | 98.9% |
| ≤8 KB | 1.0% | 99.9% |
| >8 KB | 0.1% | 100% |

**结论：**

1. **「跳过注释 + 取 2 KB」这条规则成立。** 97.7% 的文件在 2 KB 之内就已经进入正文；97.3% 在 50 个有效行内。前版设的判据「≥95% 落在前 30 个有效行」**没达到**（只有 82.2%），但放宽到 50 行的代价为零——因为真正的约束是字节数，而 2 KB 已经覆盖 97.7%。
2. **按行放宽到 30 行是不够的**：有 15.1% 的文件在 31–50 行之间才进入正文（典型是 SPDX 头 + 一段文档注释 + `import` 块）。所以别用「前 N 行」当硬闸，用「跳过注释块后前 2 KB」。
3. **2.7% 的例外怎么处理**：这些文件前 50 个有效行仍是注释或文档字符串（长的许可证头、带大段说明的脚本）。它们不是「认不出格式」，而是**读得慢一点**——L1 遇到这类文件直接按后缀/整名给初判，把内容锚点留给 L2。
4. **副作用**：27.5% 的文件第一个有效行就在第 1 行（Kconfig、defconfig、`.cfg`、`.para` 这类取值文件，本来就没有注释头）。说明「跳过注释」这一步的成本几乎可以忽略。

## 33.6 README 作为补充证据

### 33.6.1 它提供什么

README 是唯一一个**人写下来「这个目录是干什么的」**的地方，正好补上「私有构建写法」这个内容探测救不了的盲区。

### 33.6.2 三种可机械解析的写法

````markdown
├── build/          # 构建脚本和工具链配置     ← 树状图带注释

| 目录 | 说明 |                                  ← 表格
| build/ | 编译脚本 |

- `scripts/` — 辅助构建脚本                      ← 列表
````

只认这三种形态；散文里的一句话（「本仓库包含构建脚本」）不解析——太容易误判。

### 33.6.3 使用纪律

1. **只加不减。** README 没提到的目录，绝不因此跳过。
2. **只认结构化写法。**
3. **就近继承。** 文件按最近的上级 README 取提示；一个 README 管它整棵子树。
4. **不覆盖更强的证据。** 名字/内容已经判出来的类别，README 只能加，不能改。

### 33.6.4 实测：23 个真实 OHOS 子仓（2026-10-26）

**样本。** 本地 `_ohos_probe` 下的 23 个真实子仓：`device_qemu`×2、`hiviewdfx_hilog`×3、`kernel_linux_config`、`vendor_ohemu`×2、`manifest`×13、`productdefine_common`×2，共 696 个目录、1765 个文件。

**方法。** 测量脚本 [`tests/tools/readme_probe.py`](../tests/tools/readme_probe.py)，可复现：

```bash
py -I tests/tools/readme_probe.py --root <源码树目录> [--json pairs.json]
```

解析只认 §33.6.2 的三种写法，外加两处必要的工程处理：

1. **树根 + 缩进**：`├── interfaces` / `│   └── native` 要拼成 `interfaces/native`，逐行独立看会对不上；
2. **跨仓段落**：树根常写成 `device/qemu/`（指向**另一个仓**），这一段标为「跨仓」，不计入准确率。

**结果。**

| 指标 | 实测 | 事先定的判据 | 判定 |
| ---- | ---- | ------------ | ---- |
| 目录覆盖率（本目录有 README） | 38/696 = **5.5%** | ≥20% | ❌ |
| 文件覆盖率（同目录有 README） | 211/1765 = **12.0%** | — | — |
| 可解析率（能抽出 ≥1 对） | 14/62 = **22.6%** | ≥50% | ❌ |
| 结构准确率（树状图条目在树里真实存在） | 101/126 = **80.2%** | ≥90% | ⚠️ |
| 描述到的本地目录 | 40 | — | — |
| 增益（这些目录里名字规则认不出的文件） | **2** | 高于纯内容探测 | ❌ |

**三种写法的出现率**（62 个 README）：树状图 23 个（37%）、表格 14 个（23%）、`路径 — 说明` 列表 2 个（3%）。**六成 README 是纯散文**，机器抽不出任何东西。

**失败的 25 条不是解析错，是名字漂移。** 逐条核对：

| 仓 | README 写的 | 树里实际是 |
| -- | ----------- | ---------- |
| `hiviewdfx_hilog` | `frameworks/native` | 已不存在 |
| `kernel_linux_config` | `hi3516dv300_small_defconfig` | `hispark_taurus_small_defconfig` |
| `kernel_linux_config` | `linux-5.10/form/`、`linux-5.10/product/` | 只有 `linux-5.10/type/` |
| `productdefine_common` 6.1 | `inherit/pc.json`、`default.json`、`watch.json` | 已不在仓里 |
| `vendor_ohemu` | `qemu_riscv_mini_system_demo` | `qemu_riscv32_mini_system_demo`、`qemu_riscv64_linux_min` |

**跨仓 24 条**全部来自 `vendor_ohemu` 的 `device/qemu/` 那一段——README 用的是**整棵源码树**的视角，不是本仓。不认树根，就会把这 24 条误算成准确率损失。

**结论：README 不进 L1 主流程。**

- 覆盖率 5.5%、增益 2 个文件——它救不了任何文件级路由；
- 可解析率 22.6%——六成 README 是散文；
- 结构准确率 80.2%——约两成条目已经过期，当信号会引入**静默错误**；
- 唯一还有价值的是**给人看**：40 个目录有了一句「这是干什么的」，占 5.7%。

定位因此降为：`--deep` 诊断与人工排查时的辅助材料，**不是分类规则的输入**。要真用，得先解决三个工程点（树根识别、缩进层级、跨仓段落）——本文脚本已经做了，但收益不足以进主流程。

## 33.7 结论

1. **大类定为 8 个**（C1–C8），按信息内容定义，不按文件名定义。每个大类喂 1–5 个提取器，允许多对多。
2. **矩阵无空行、无空列**，`08` §19.9 的五个历史盲区里四个有了落点，剩下一个是 heredoc/Make include 这类词法局限，不是分类问题。
3. **能跨系统迁移的不是文件名，是「长相」**：内容锚点（最可迁移）> 文件名里的词 ≈ 路径 > 完整文件名 > 后缀（最不可迁移）。
4. **通用规则只有 12 条左右**（shebang、`.c/.h`、`-l`、`Makefile`、`Kconfig`、`*_defconfig`、`LDFLAGS`、`ENTRY(`、`.ld`、`CROSS_COMPILE`、`scripts/`、名字里的词），其余都是 1–3 个系统的半通用或专属规则。这说明「一套规则覆盖所有系统」不现实，但「通用 12 条 + 每系统 5–10 条」是现实的。
5. **L1 不需要扫全篇，且 2 KB 够了**：认格式的信号在开头，找对象的信号才可能在全篇——后者是 L2 的责任。实测 97.7% 的文件在前 2 KB 内进入正文、97.3% 在前 50 个有效行内（§33.5.4）。规则固定为「跳过开头注释块 + 取 2 KB」。
6. **README 实测后判定为不进主流程**：23 个真实子仓上，目录覆盖率 5.5%、可解析率 22.6%、结构准确率 80.2%、文件级增益 2 个。定位退回「人工诊断辅助」，不参与分类。
7. **名字规则是「够用但有边界」**：剔除 manifest 仓后覆盖 75.1%，60 样本人工核对精度 96.7%，噪声目录占 9.0%。误差全部集中在「同一后缀在不同路径下语义不同」（`config.gni`、`rtconfig.py`）与「后缀表里没有的载体」（`.hcs`/`.para`/`.cfg`/`.config`/无后缀 `defconfig`）。**结论：名字做初判、路径做修正、内容锚点兜底，三者缺一不可。**

### 33.8.2 误报源清单

宽进策略会把非载体文件也路由出去。实测（分母 = 1108 个被路由的文件）：

| 误报源 | 数量 | 占路由 | 具体 | 处置 |
| ------ | ---- | ------ | ---- | ---- |
| **测试目录** | 100 | **9.0%** | `test/` 67、`tests/` 28、`images/` 5；按类分 C6 77、C2 23 | 目录级降权，不排除——测试里也有真实的构建/头文件依赖 |
| 生成物标记 | 26 | 2.3% | **全部是内核 `*_defconfig`** | **不能一律跳过**，见下 |

**生成物标记的坑：** 26 个带 `Automatically generated` / `DO NOT EDIT` 的文件，100% 是内核 defconfig（`kernel_linux_config-*` 下的 `arm64_defconfig`、`hispark_taurus_standard_defconfig` 等）。它们虽然是「生成出来的」，但**正是 S7 要读的取值快照**。所以规则应该是：

- 生成物标记 → **降置信度**，不删；
- 只有「生成物 + 不在任何载体路径 + 内容是重复展开」三条同时成立，才排除。

**后缀误判（真实存在的反例）：**

| 文件 | 后缀规则判成 | 实际 | 证据 |
| ---- | ------------ | ---- | ---- |
| `rtconfig.py`（RT-Thread BSP） | C1 脚本 | **C4 工具链** | 从不被 Python 执行，由 SCons 导入；内容是 `PREFIX='arm-none-eabi-'` |
| `config.gni`（OHOS） | C2 构建描述 | **C4 板级配置** | 只在 `device/*/` 下出现，内容是 `board_*` 取值 |
| `productdefine/common/inherit/*.json`（OHOS） | other | **C3 模块清单** | 声明产品继承哪些组件 |

**漏判（后缀表里没有，但确实是载体）：** `.hcs`（26）、`.para`（20）、`.cfg`（20）、`.config`（18）、无后缀的 `defconfig`（NuttX）、无后缀的 `bundle`/`rcS`（Yocto/Buildroot init 脚本）。

### 33.8.3 60 文件抽样人工标注（试点）

**抽样。** 按大类分层（`json-xml` 18、`build` 14、`manifest-board` 10、`script` 8、`link-kconfig-dts` 5、`c-source` 5），`random.seed(11)`，打印每个文件的前 4 个有效行人工判读。

**结果：58 / 60 与名字规则的判定一致**，2 处不一致：

1. `config.gni` → 后缀 `.gni` 判 C2，实际 C4（见上表）；
2. `productdefine/common/inherit/*.json` → 落在 other，实际 C3。

**判读。** 名字规则在 **OHOS 这类命名规矩的工程里精度已经够用**（96.7%），误差集中在「同一后缀在不同路径下语义不同」这一件事上，而不是「后缀认错了类」。这支持当前设计：**名字给初判 + 路径给修正 + 内容锚点给兜底**，三层依次叠加。

### 33.8.4 还缺什么

| 缺什么 | 现状 | 怎么补 |
| ------ | ---- | ------ |
| **同义键名表** | v1.1 已扩到 11 个系统（§33.4.5），3 个低置信格核了 2 个 | 剩 Debian `Build-Profiles` 一格；`sources.debian.org` 本机不可用（反爬挑战页），需在 Debian 机器上 `apt-get source` 取真实 `debian/control` |
| **误报源清单** | §33.8.2 已测完（9.0% 噪声目录、2.3% 生成物、3 类后缀误判） | 无 |
| **人工标注集 300–500** | 只做了 60 个试点（§33.8.3） | 扩到 300–500，且必须跨系统（Yocto/Buildroot/Zephyr 各抽 50），否则测出来的只是 OHOS 的 precision |
| **README 复测** | 23 个小子仓（§33.6.4），增益仅 2 | 换 3–5 个大仓复测，确认「README 不进主流程」的结论不是样本偏小造成的 |

补齐前两项即可写规则；标注集与 README 复测影响的是**验收**，不影响规则形态。

## 33.9 已知局限

| 局限 | 影响 | 后续 |
| ---- | ---- | ---- |
| Linux 内核只采了两个目录 | 只看了 `arch/arm64/boot/dts/qcom` + `scripts/kconfig` + `kernel/configs`；`Kbuild`/`Makefile` 的实际写法没抽样 | 再取一个 `drivers/` 子目录与 `arch/arm64/Makefile` |
| B 级样本是「单包 / 单板 / 单目录」 | Yocto 只看了 `busybox`，Buildroot 只看了 `busybox`，RT-Thread/NuttX 各只看了一块板，AOSP 只看 `build/core`，Meson 只看测试用例 | 每个系统再抽 3–5 个不同角色的包/板（库、工具、内核、驱动） |
| 名字规则的覆盖与精度只在 OHOS 上测过 | 75.1% 覆盖、96.7% 精度是 OHOS 的数字；换到命名更散的工程（如 AOSP 的外部项目）可能明显下降 | 在 B 级样本上各跑一次 `l1_survey.py`，做跨系统对照 |
| 版本漂移 | Yocto/Android/Zephyr 的约定也在变 | 每条规则标注适用版本 |
| 大类边界有模糊 | `Android.bp` 同时是 C2/C3；`.bb` 同理 | 有意保留重叠，由提取器自筛 |
| 「约定」不等于「强制」 | 任何系统都有不按约定命名的项目 | 弱信号叠加，不做单信号强判 |
| `C8` 设备树价值待评估 | 目前只路由、不提取，S7 能从 defconfig 拿到大部分信息 | 等 S7 实现后再看是否值得解析 |
| README 实测样本偏小 | 23 个小型子仓、1765 个文件，不是完整 OHOS 树；大仓的 README 质量可能不同 | 换 3–5 个大仓复测 |
