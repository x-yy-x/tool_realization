# 上半 · 流水线（横着切）

## 7. 两段预检 + 八关

不是一条流水线，是**三段**——因为有三类昂贵动作，每类前面要一道门。

排序依据**不是一条原则，是三条**：

| 原则                       | 说的是什么                                 | 决定                             |
| -------------------------- | ------------------------------------------ | -------------------------------- |
| **一 · 存在性**     | 一道门只能检查**此刻已经存在**的东西 | **最早能放多早**（硬下界） |
| **二 · 代价**       | 在昂贵动作之前，先花秒级成本确认它能成功   | **最晚该放多晚**（上界）   |
| **三 · 依赖正确性** | 前一步不通过时，后一步会产生**假报** | 区间内两门之间的相对顺序         |

```
每道门都有一个区间，位置 = 区间内由原则三定：

    最早 ──────────────── 最晚
     ↑                      ↑
   原则一                 原则二
  (硬下界)               (上界)
```

最初只用原则二，更早的版本用的是「输入依赖」，把可达性推到了第 6 关——**结论碰巧对，理由错了**（见 26.1 与 26.5）。

### 7.2.1 图解：分诊与闭环控制流

上一张图是「什么在哪跑」。这一张是「**跑出问题之后怎么转**」。

**每个关跑完，该关的 findings 交给一次 Agent 分诊**；分诊出决定，脚本执行，执行完重验，不通过就回滚。

```mermaid
flowchart TB
    A["第 N 关 跑完<br/>产出该关的 findings.json"] --> B{"有 findings 吗?"}
    B -->|没有| C["进下一关"]
    B -->|有| D["Agent 分诊（本关一次）<br/>输入：本关全部 findings<br/>+ knowledge.yaml<br/>+ 本关上下文 / 白名单"]
    D --> E["四选一（受档位围栏）<br/>· apply_recipe　A / B 档<br/>· propose_patch　仅 B 档<br/>· escalate　任意档<br/>· abandon　任意档"]
    E --> F["脚本执行 / apply patch"]
    E --> G["放弃 + 重建方案<br/>D 档附候选根因排序"]
    F --> H{"改的是源码吗?"}
    H -->|否| I["小回环（A 档）<br/>只重跑本关"]
    H -->|是| J["大回环（B 档）<br/>回第 1 关重扫"]
    I --> K["收敛判据<br/>(1) findings 严格变小<br/>(2) 不允许多出新 finding<br/>(3) 单条修复 ≤ 3 次<br/>(4) 整轮 ≤ 5 轮"]
    J --> K
    K -->|通过| L["进下一关"]
    K -->|任一不满足| M["回滚本轮全部改动<br/>+ 转「放弃 + 方案」"]
```

**出口：不是「findings 清零」，是「`block` 清零」。**

```mermaid
flowchart TB
    A["段一 / 段二 / 段三 全部通过之后"] --> B{"block 类是否全部处置?<br/>（修好 或 已放弃）"}
    B -->|是| C{"有「放弃」项吗?"}
    B -->|否| X["异常：回到分诊重判<br/>（本不该发生）"]
    C -->|无| D["编译<br/>hb build"]
    C -->|有| E["停：报告根本性问题<br/>+ 重建方案"]
```

**两条读法：**

1. **`warn` / `info` 可以带着编译。** 出口卡在 `block` 上——因为 `warn` 里有一部分是 S1 的假阳性（19.3.7），要求清零等于要求修假问题。
2. **大回环是必须的。** B 档改了源码 → 需求清单本身变了（补了 `#include <cstdint>` 之后，S6 就不再产出那条 gap 需求）→ 只能回第 1 关重扫。**A 档没有这个问题**，所以小回环只重跑本关。

> **分诊的粒度为什么是「每关一次」**：三种粒度都试过——每条一次（几十次调用，一半是「缺个包」）、全局一次（丢掉关与关的上下文，且不尊重原则三的顺序）、每关一次（8 次左右，每条 finding 都能拿到本关上下文）。**中间那个是对的。**

## 26. 「昂贵动作前置门」原则与两段预检细节

> 本节说明第 7 节那张图**为什么长这样**。图是最终形态，这里是依据。

### 26.1 为什么不能按「输入依赖」排

最初的版本按「**输入依赖**」排序：能算的先算，所以可达性排到了第 6（因为它的输入是第 3 关报出的缺失集）。

**这个原则是错的。** 正确的是：

> **按代价排序：在每个昂贵动作之前，先花秒级成本确认它能成功。**

按输入依赖排，得到「计算上最自然的顺序」；按代价排，得到「**最省时间的顺序**」——而省时间正是这个工具存在的理由（§1–§2）。

### 26.2 代价阶梯

同 §7.1 的表。这里只重复要点：**是三个小时级动作，不是两个**——`repo sync`、补拉缺失仓、`hb build`。最初只给了 `hb build` 一个门（就是那八关），**`repo sync` 一个都没有**，尽管它和 `hb build` 同为小时级。

### 26.3 两段预检接在哪

**第 -2 层接在「装 WSL / 装工具」之前，第 -1 层接在「`repo sync`」之前，八关接在「`hb build`」之前。** 完整形态见 §7.2。

### 26.4 三个入口

三个入口（`--stage env` / `fetch` / `tree`）及其运行位置见 §7.3。要点：**环境预检是唯一必须在 Windows 上跑的部分**——因为那时 WSL 还不存在。

### 26.5 第 6 关为什么还在 6 —— 以及原来给的理由是错的

原来的「可达性验证」一名两用，容易让人以为它是网络总检。拆开后是**三趟互不重叠的可达性检查**：

| 时机               | 名字                            | 探哪些端点                                      | 输入                      | 问的问题                                 |
| ------------------ | ------------------------------- | ----------------------------------------------- | ------------------------- | ---------------------------------------- |
| 装环境**前** | 环境预检（第 -2 层）            | WSL 分发源 / apt 镜像源 / 宿主代理              | 配置 + 常量知识           | 装环境要用的源，**通不通**         |
| sync**前**   | 获取预检（第 -1 层）            | manifest**声明了的** `<project remote>` | manifest                  | 这次 sync 要访问的端点，**通不通** |
| sync**后**   | **修复可达性**（第 6 关） | 源码**引用了但 manifest 没声明的**仓      | 第 3 关 + 第 5 关的缺失集 | 缺的这些仓，**补得上吗**           |

**三张目标清单的交集是空的**——一个查**软件源**（装环境要用的），一个查**声明了的仓**（sync 要拉的），一个查**没声明的仓**（sync 根本不知道要拉的）。
所以第 6 关省不掉：**`repo sync` 成功退出码 0，不代表树是完整的**——`repo` 的视野只有 manifest，看不见 `BUILD.gn` 里的 `deps`。

#### 那么为什么还在 6？

⚠️ **本节原先写的理由是「输入是第 3 关的缺失集」——那正是 §26.1 刚宣布为错误的「输入依赖」原则。结论对，理由错。**

真正的理由是**原则一（存在性）**：

> **第 6 关探的那个集合，在第 1 关跑完之前物理上不存在。**
>
> 「源码引用了哪些仓」要扫源码才知道。秒级探针在这里**没东西可探**。

这是**硬下界**，原则二（代价）管不了它——**当探针物理上没法更早跑时，代价原则失效。**

#### 第 6 关治的是什么病：repo 工具的能力边界

```
manifest.xml 里没有 third_party/asmjit
但 BUILD.gn 里写了 deps = ["//third_party/asmjit:asmjit"]
                    ↓
repo 的视野只有 manifest，看不到 BUILD.gn
                    ↓
repo sync 正常完成，退出码 0            ← 没有任何报错
                    ↓
hb build 跑了几小时后才发现 GN 加载不了    ← BUILD-026
```

#### 两处修订（本节原来没写对）

1. **输入漏了第 5 关**。原文只写「第 3 关的缺失集」，但**第 5 关也产出缺失集**（部件闭包 → 缺失集、使用集合 × 声明集合 → 缺口集）。按原文，`BUILD-014`/`BUILD-021`/`BUILD-025` 找到的缺失部件**没人查可达性**。
2. **它保护的动作没画进流水线图**。原文图是「第 8 关 → `hb build`」，中间缺了「**补拉缺失仓**」（小时级）。不画出来，第 6 关看起来就是个没有下游的检查。

另加一条落地要求：**第 6 关的结果要持久缓存**。vendor 闭源仓是**永久不存在**的，每跑一次探一次是浪费——第一次的结果存下来带时间戳即可。

### 26.6 第 -1 层预检具体查什么

门槛极低：`repo init` 只要几秒，产出 `.repo/manifests/*.xml`，里面就有全部 `<project remote=...>`。**不需要源码就能算出这次 sync 要访问哪些端点。**

| 检查                | 做法                                           | 对应               |
| ------------------- | ---------------------------------------------- | ------------------ |
| `repo` 命令在不在 | `command -v repo`                            | `NET-003` 的前置 |
| bootstrap 端点可达  | 探`storage.googleapis.com`                   | `NET-003`        |
| 每个 remote 的 DNS  | `getent hosts <host>`                        | `NET-001` 类     |
| 每个 remote 的连接  | `curl -I --max-time 10`                      | —                 |
| 每个 remote 的权限  | 返回码判读（401/403 单列一档）                 | `SYNC-004`       |
| **并发风险**  | `<project>` 数 × `sync-j` vs 端点限流历史 | `NET-004`（429） |

**最后一行值得注意**：`NET-004` 的 Gitee 429 是**可以在 sync 前预测的**——manifest 里有仓数，`<default sync-j>` 里有并发数，两者相乘就是压给端点的瞬时压力。这条只能算启发式，标 `warn` 不标 `block`。

**预检全部带 `--max-time`**——`SYNC-001` 的教训：检查器自己不能挂住。

### 26.7 这个原则不止适用于可达性

「昂贵动作前置门」是**通用编排原则**，不是网络专用的。按它把 61 条重排：

| 昂贵动作                       | 前置门                                          | 覆盖条目                                                          |
| ------------------------------ | ----------------------------------------------- | ----------------------------------------------------------------- |
| 装 WSL 发行版                  | 端点可达（第 -2 层）                            | `ENV-001`、`NET-002`                                          |
| apt 装工具                     | apt 源可达（第 -2 层）                          | `NET-001`                                                       |
| **装完之后 / sync 之前** | **基线工具存在性 + 环境身份（第 -1 层）** | `ENV-002/003/004/005/007/009/013`、`IMG-001/002`、`ENV-014` |
| `repo init`                  | repo bootstrap 端点（第 -1 层）                 | `NET-003`                                                       |
| **`repo sync`**        | manifest 端点全量探测 + 并发风险（第 -1 层）    | `NET-004`、`SYNC-004`                                         |
| **补拉缺失仓**           | 第 6 关修复可达性                               | `BUILD-026`、`BUILD-023`、`SYNC-004`                        |
| **`hb build`**         | 第 0–5 关（本地静态）                          | `SYNC-002/003/005`、`BUILD-023/024/026` 及其余全部            |

**第 3 行是本次新增的**，它解决了一个原来被误以为无解的问题。看下面。

#### 工具清单的洞，以及它怎么被填上

本节原来的版本记过一条自我批评：

> 保护 `apt` 的门要一份**工具清单**——清单从哪来？**从源码树的 S1 提取**。但那时还没有源码树……
> → 所以这一格的清单只能来自配置里的 `whitelist.yaml`，**不能来自扫描**。
> → **这正是 §10「未声明的约束只能靠白名单」的又一个落点。**

**推理是对的，但结论漏了一步。** 既然清单在配置里就有，那么**检查本身也不必等第 3 关**。

工具存在性应该**拆成两层**：

| 层                     | 清单来源                   | 在哪查             | 例子                                                                                       |
| ---------------------- | -------------------------- | ------------------ | ------------------------------------------------------------------------------------------ |
| **基线工具**     | `whitelist.yaml`（配置） | **第 -1 层** | `clang`、`gn`、`ninja`、`python3`、`timeout`、`mcopy`、`mkfs.vfat`、`repo` |
| **提取出的工具** | 第 1 关 S1 扫描            | 第 3 关            | 源码里调用的、非基线的（如产品特有的交叉编译器）                                           |

**两个好处**：

1. `command -v` 是**秒级**，能拦住「apt 装完了但某个基线工具其实没装上」——**不用等几小时的 sync**。这就是 `ENV-003`(python)、`ENV-013`(timeout)、`IMG-001`(mkfs.vfat)、`IMG-002`(mcopy) 该在的位置。
2. **R8 不再是「无解」**：基线清单就是它的来源；完整覆盖仍然靠第 3 关，两条腿不冲突。

#### 环境身份同理

`ENV-002`(Ubuntu 版本)、`ENV-004`(externally-managed)、`ENV-005`(Python 3.13) 三条，§10 说它们「**源码里没有任何一处声明，所以不可能被扫描器扫出来，只能靠白名单**」。

**但「扫不出来」不等于「查得晚」。** 恰恰相反——它们**不依赖源码树**，是全场最早能查的一类。原来放在第 4 关，是被「反正是白名单」这个性质连累了。

引擎位置：**第 -1 层的 `precheck/p_base.py`**。

> ⚠️ **`ENV-007` 是特例，它连第 -1 层都不够早。**
> 「Windows 商店 python stub」是 **Windows 侧**的现象。第 -1 层跑在 WSL 里，**PATH 里没有 Windows 的商店别名，查不到**。
> 它只能在**第 -2 层**——那是唯一在 Windows 侧的门。

## 27. 三原则与 61 条的落点

> **「六类归类」和「流水线分段」是什么关系？** 答案是：**正交**。
> 类别按「根因是什么」分，段按「需要什么才能查」分。本节把 61 条逐条放到段上。

### 27.1 位置公式

```
每道门都有一个区间：

    最早 ──────────────── 最晚
     ↑                      ↑
   原则一                 原则二
  (存在性，硬下界)      (代价，上界)

区间内的位置：原则三（依赖正确性）
```

| 原则                       | 一句话                                     | 违反的后果                                 |
| -------------------------- | ------------------------------------------ | ------------------------------------------ |
| **一 · 存在性**     | 一道门只能检查**此刻已经存在**的东西 | 门在跑，但没东西可查——**探针空转** |
| **二 · 代价**       | 在昂贵动作之前，先花秒级成本确认它能成功   | 花了几小时，才发现几秒就能查出的错         |
| **三 · 依赖正确性** | 前一步不通过时，后一步会产生**假报** | 报出一堆假的「身份错误」「缺部件」         |

**三条缺一条都定不下位置。** 第 6 关就是只有原则一能解释的例子（§26.5）。

### 27.4 覆盖不到的

后 17 条不是「还没实现」，是**方法上就覆盖不了**：

- **语义提取（5 条）**：判据在知识库里，不在源码模式里（§8）
- **运行期状态（5 条）**：依赖「此刻的机器状态」（§11）
- **结果判读（7 条）**：硬编检查会造假，只能读结果（§11）

**这三类的共同点：都不是「扫一遍源码」能回答的问题。** 承认它们的代价，比假装覆盖了要好——这就是 R2 和 R6 那两条「方法本身的边界，不是实现缺陷」的具体化。

# 下半 · 四层（竖着切）

## 29. 每一关内部：扫描 → 提取 → 验证 → 判读与修改

上半讲的是「竖着切成的几关」。但**每一关内部是个黑盒**——我们只知道「第 0–8 关做需求提取与验证」，不知道里面怎么走。

**四层就是把每一关切开看内部：**

```mermaid
flowchart LR
    A["L1 扫描<br/>源码树 + 配置<br/>↓<br/>文件清单"] --> B["L2 提取<br/>文件清单<br/>↓<br/>需求记录"]
    B --> C["L3 验证<br/>需求记录<br/>↓<br/>findings"]
    C --> D["L4 判读与修改<br/>findings<br/>↓<br/>报告 + 处置"]
```

| 层                      | 输入          | 输出                         | 干什么                                                                              |
| ----------------------- | ------------- | ---------------------------- | ----------------------------------------------------------------------------------- |
| **L1 扫描**       | 源码树 + 配置 | **文件清单**（带分类） | 遍历、排除、按后缀分类。机械动作                                                    |
| **L2 提取**       | 文件清单      | **需求记录**           | 按需求种类划分的若干任务                                                            |
| **L3 验证**       | 需求记录      | **findings**（带证据） | 按验证原语划分的若干任务                                                            |
| **L4 判读与修改** | findings      | **报告 + 处置决定**    | 定级、聚合、出口决定；**并把 findings 喂给 Agent 分诊，执行修复、回环、回滚** |

### L1–L3 只读，L4 是唯一会改东西的层

这条线把四层分成两半，也解释了一堆原来的设计决定：

| 层                      | 会不会改东西                                            |
| ----------------------- | ------------------------------------------------------- |
| L1 扫描                 | 只读路径（`readdir`）                                 |
| L2 提取                 | 只读文件内容                                            |
| L3 验证                 | 只读环境（`command -v` / `curl -I` 都不产生副作用） |
| **L4 判读与修改** | **唯一有副作用的层**——会装包、会改源码、会回滚  |

**这条线一画，修复段（§28）的那些要求就自动归位了**：为什么它必须能单独关（`--no-fix`）、为什么默认 dry-run、为什么只有它需要回滚——因为它全在唯一会改东西的那一层。

L4 内部两半，名字正好对上：

| 半边           | 动作                                                                        | 有副作用 |
| -------------- | --------------------------------------------------------------------------- | -------- |
| **判读** | 定级`block`/`warn`/`info` · 聚合（工具链 × 目标并排）· 出口决定    | ❌       |
| **修改** | **分诊（喂 AI，四选一）** · 执行 recipe / apply patch · 回环 + 回滚 | ✅       |

> **精度**：「分诊」是 AI，「出口决定」不是——`block` 清零没有是脚本判的。所以「喂 AI」只覆盖「修改」那一半。

**两条线不冲突，是同一件事的两个方向：**

|                         | 是什么                       | 回答什么                         |
| ----------------------- | ---------------------------- | -------------------------------- |
| **流水线**（§7） | **横着切**——切成几关 | 什么时候跑、跑在哪、保护哪个动作 |
| **四层**（§29）  | **竖着切**——每关内部 | 一个任务吃进什么、吐出什么       |

要注意：**两段预检没有 L2。**

| 段                   | L1                 | L2（提取）           | L3         | L4         |
| -------------------- | ------------------ | -------------------- | ---------- | ---------- |
| 第 -2 层             | 探测 Windows       | ❌ 无                | 对白名单   | 判读与修改 |
| 第 -1 层             | 读 manifest        | ❌ 无                | 对白名单   | 判读与修改 |
| **第 0–8 关** | **扫源码树** | ✅**七个任务** | 六个验证器 | 判读与修改 |

**因为「提取」的定义就是「从**源码文件**里读出声明」——预检没有源码，所以没有这一层。** 这也解释了 §7.4 那句「只有最后一段用到了那套提取器」。

### 29.1 L1 扫描层

#### 做什么

| 步 | 动作                                                      | 代价                         |
| -- | --------------------------------------------------------- | ---------------------------- |
| 1  | **遍历**：`readdir` 走全树，只记路径不读内容      | **秒级**（~18 万文件） |
| 2  | **排除**：扔掉不该看的目录                          | —                           |
| 3  | **分类**：按后缀 + 按路径给每个文件打 `kind` 标签 | —                           |
| 4  | **固化**：写出 `filelist.json`，后续关卡复用      | —                           |

**关键点：遍历 ≠ 解析。**

- **遍历**只 `readdir`，不打开文件——~184203 个文件，秒级
- **解析**才读内容——只有认得的那部分，~12930 个文件，分钟级

**这是全场唯一一次全树遍历。** 后面所有关卡都从 `filelist.json` 出发，不重复走树。

#### 排除哪些

| 目录           | 处理                              | 为什么                     |
| -------------- | --------------------------------- | -------------------------- |
| `.git/`      | 完全跳过                          | 不是源码                   |
| `.repo/`     | 跳过内容，**保留 manifest** | manifest 要读（S2）        |
| `out/`       | 跳过内容，**保留路径**      | `BUILD-010` 要判同名目录 |
| `prebuilts/` | 只建索引，不解析                  | `SYNC-005` 要判存在性    |

#### 分类表（**「1、文件分类」**）

| `kind`     | 匹配                               | 归谁用（L2 的哪个任务） |
| ------------ | ---------------------------------- | ----------------------- |
| `shell`    | `*.sh` / `*.bash` / 带 shebang | S1（工具）、K1（语法）  |
| `make`     | `Makefile` / `*.mk`            | S1、K1                  |
| `gn`       | `BUILD.gn` / `*.gni`           | S1（action）、S2、S5    |
| `product`  | `vendor/*/config.json`           | S3、S7                  |
| `bundle`   | `**/bundle.json`                 | S3                      |
| `manifest` | `.repo/manifests/*.xml`          | S2                      |
| `header`   | `*.h` / `*.hpp`                | S6（**声明侧**）  |
| `csrc`     | `*.c` / `*.cc` / `*.cpp`     | S6（**使用侧**）  |
| `ldscript` | `*.ld` / `*.lds`               | S5                      |
| `kconfig`  | `*_defconfig` / `Kconfig*`     | S7                      |
| `ninja`    | `out/**/*.ninja`                 | 第 7 关（半静态档）     |
| `other`    | 其余                               | **第 2 关的哨兵** |

**最后一行是第 2 关的意义**：如果有 `kind=other` 的文件里出现了一个提取器不认识的**新文件类型**，就说明规则缺了一类（§9）。

#### L1 的输出

```json
// filelist.json 的一条
{ "path": "build/scripts/build.sh", "kind": "shell", "size": 4213 }
```

### 29.2 L2 提取层（**「2、不同文件 → 不同识别」**）

L1 产出的分类清单，**分头喂给不同的提取任务**。每个任务只看自己认得的那几类文件。

```mermaid
flowchart LR
    F["filelist.json<br/>带 kind 标签"] --> S1["S1 工具"]
    F --> S2["S2 仓"]
    F --> S3["S3 部件"]
    F --> S4["S4 工具链"]
    F --> S5["S5 库与符号"]
    F --> S6["S6 头文件"]
    F --> S7["S7 配置与架构"]
    S1 --> R["requirements.json"]
    S2 --> R
    S3 --> R
    S4 --> R
    S5 --> R
    S6 --> R
    S7 --> R
    K["knowledge.yaml<br/>whitelist.yaml"] --> R
```

**「中央遍历，分散解析」**——树只走一次（L1），解析按任务分头做（L2）。

#### 任务表（**「3、不同任务明确定义输入输出」**）

| 任务                    | 输入（哪些`kind`）                              | 输出（需求记录）                | 例子                                      |
| ----------------------- | ------------------------------------------------- | ------------------------------- | ----------------------------------------- |
| **S1 工具需求**   | `shell` `make` `gn`                         | `kind=tool`                   | `mcopy` → `command -v mcopy`         |
| **S2 仓需求**     | `manifest` + `gn` 里的 `//path`             | `kind=repo`                   | `//third_party/asmjit` → 在不在        |
| **S3 部件需求**   | `product` + `bundle`                          | `kind=component`（含闭包）    | `drivers_tools` → 部件图里有吗         |
| **S4 工具链身份** | `shell` 里的编译器名 + `gn` 的 `target_cpu` | `kind=toolchain`              | `riscv32-unknown-elf-gcc` → 真身对不对 |
| **S5 库与符号**   | `gn` 的 `-lfoo`/`libs` + `ldscript`       | `kind=lib` / `kind=symbol`  | `-lnosys` → `libnosys.a` 在不在      |
| **S6 头文件**     | `csrc`（使用侧）+ `header`（声明侧）          | `kind=header` / `kind=gap`  | `uint32_t` 用了，`<cstdint>` 声明了吗 |
| **S7 配置与架构** | `kconfig` + `gn` 的 `target_cpu`            | `kind=config` / `kind=arch` | `x86_64` → Kbuild 的 `x86`           |
| **K1 语义知识库** | 上面全部产出 +`knowledge.yaml`                  | `kind=semantic`               | 脚本漏了`mcopy -o`                      |
| **K2 版本白名单** | 环境探测结果 +`whitelist.yaml`                  | `kind=version`                | Ubuntu 26.04 → 在支持列表里吗            |

**七个 S 任务是「从源码读出声明」；两个 K 任务是「拿经验去比对」**（§8）。

#### 「给定文件 → 识别需要哪些工具」怎么走

以 `build/scripts/build.sh` 为例：

```
① L1 扫到它          → kind=shell
② S1 分词            → 逐行取首词，滤掉 shell 关键字（if/for/cd/echo…）
③ 得到候选词         → [genconfig, ninja, python, mcopy, mformat, ...]
④ 滤掉包装器         → env / time 不算需求（见 L2 §19.3.4 的 SKIP_WRAPPER）
⑤ 产出需求记录        → {kind: tool, name: "mcopy", from: "build/scripts/build.sh:118"}
```

**「给定工具 → 识别版本」这一格，目前是空的。**

| 想查的                 | 现有任务                                                              | 结论                          |
| ---------------------- | --------------------------------------------------------------------- | ----------------------------- |
| 给定文件 → 要哪些工具 | **S1** ✅                                                       | 有                            |
| 给定工具 → 什么版本   | ❌**没有对应任务**（`v_identity` 只查身份三元素，不查版本号） | **建议并进 `p_base`** |

现在所有的**版本**检查（`ENV-002`/`ENV-005`/`ENV-014`）查的都是**环境**版本，不是**工具**版本。这是一个已知的设计缺口，不是遗漏。

### 29.3 L3 验证层

**输入**：需求记录 + 环境快照。**输出**：findings（带证据）。

| 验证器            | 验证原语           | 输入需求                    | 问的问题                       | 关卡 | 对应             |
| ----------------- | ------------------ | --------------------------- | ------------------------------ | ---- | ---------------- |
| `v_tree`        | **不变量**   | 哨兵 + 仓清单               | 树本身完整吗                   | 0    | `SYNC-002/003` |
| `v_coverage`    | **反向覆盖** | `filelist` 的 other       | 有没有没被任何提取器覆盖的文件 | 2    | 扫描器自检       |
| `v_exists`      | **存在性**   | `tool`/`repo`/`lib`… | 这个东西在不在                 | 3    | 六个子类         |
| `v_identity`    | **身份**     | `toolchain`               | 在的那个，是对的的那个吗       | 4    | §20.2           |
| `v_consistency` | **集合运算** | `component`/`arch`      | 差集是空吗                     | 5    | §20.3           |
| `v_reach`       | **可达性**   | 缺失集                      | 缺的这些，补得上吗             | 6    | §20.4           |

> **注意是六个，不是五个。** `v_coverage` 是第 2 关的哨兵，容易在数数时被漏掉（这份清单在旧稿里前后不一致过一次）。

**验证原语只有五种**：存在性 / 身份 / 集合运算 / 可达性 / 不变量。
需求有 **12 种** `kind`（[`schema/requirements.schema.json`](../schema/requirements.schema.json) 的 `enum`），验证器只有六个——**多对一**，因为同一个原语能验多种需求。

#### 一条需求怎么走到 finding

```
requirements.json:  {kind: tool, name: "mcopy", check: "CHK-EXISTS-CMD", severity: block}
                          ↓  check 字段决定派给谁
                     v_exists 执行 command -v mcopy
                          ↓
findings.json:      {req: "REQ-0042", verdict: "fail",
                     evidence: "command -v mcopy → 退出码 1",
                     severity: "block", declared_at: "build/scripts/build.sh:118"}
```

**`check` 字段是唯一的路由表。** 提取任务不认识验证器，验证器也不认识源码——中间靠 `requirements.json` 解耦（§15.3）。

### 29.4 L4 判读与修改层

**输入**：findings。**输出**：报告 + 处置决定。

**判读那半边**（无副作用），三个动作：

| 动作               | 做什么                                                                          |
| ------------------ | ------------------------------------------------------------------------------- |
| **定级**     | 每条 finding 落到`block` / `warn` / `info` 三档之一                       |
| **聚合**     | 把「工具链 × 目标」「仓库 × 可达性」这类并排成一节，否则人看不出关联          |
| **出口决定** | **不是 findings 清零，是 `block` 清零**；有「放弃」项则停，输出重建方案 |

**定级的依据**（不是拍脑袋）：

| 档        | 判据                               | 例子                            |
| --------- | ---------------------------------- | ------------------------------- |
| `block` | 这条不满足，**构建必然失败** | 工具不存在、仓缺失              |
| `warn`  | 需要人判，或**可能是假阳性** | S1 扫出来的疑似工具名、并发预测 |
| `info`  | 只是提示，不影响构建               | `ENV-014`（Node 14）          |

**定级放在 L4 而不是提取时**，因为「严不严重」要看**验证的结果**，不看需求本身。

**修改那半边**（有副作用），四个动作与两条回环：

| 步 | 动作                                                                                            |
| -- | ----------------------------------------------------------------------------------------------- |
| ① | **分诊**：本关 findings + `knowledge.yaml` + 本关上下文 → **一次 Agent**         |
| ② | Agent 四选一（受档位围栏）：`apply_recipe` / `propose_patch` / `escalate` / `abandon`   |
| ③ | 脚本执行 recipe，或人审后 apply patch（默认 dry-run）                                           |
| ④ | **回环**：A 档改的是环境 → 小回环（只重跑本关）；B 档改了源码 → 大回环（回第 1 关重扫） |

四条收敛判据兜底：findings 严格变小 · 不允许多出新 finding · 单条 ≤3 次 · 整轮 ≤5 轮。任一条不满足就回滚本轮全部改动，转「放弃 + 重建方案」。

**每关跑完都做一次 L4**（就是 §7.2.1 的那个分诊）：findings 交给一次 Agent，四选一动作，执行、重验、收敛。

> 修复段的完整设计（四档定义、根本性判据、Agent 的围栏、`fix_recipe` 与自学习回路）见 [`06-修复段.md`](06-修复段.md)。

**读法**：

- **L1 只在前两关各跑一次**（第 0 关全树；第 -1 层只读 manifest）——第 1 / 2 关**复用**第 0 关的 `filelist.json`，不再走树
- **L2 只在第 1 关**——这是全场唯一一次「从源码读声明」
- **L3 每关一个验证器**——第 0 关和 -1/-2 层是特化过的
- **L4 每关都有**——但**只有第 8 关做出口决定**
