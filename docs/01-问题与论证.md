## 1. 问题：冷启动

已有的 61 条检查全部是**从已知失败反推**出来的。这带来一个循环依赖：

> 要跑检查，得先知道「这个环境会遇到哪些问题」；
> 要知道会遇到哪些问题，得先编译过；
> 可是编译正是我们想避免的（反复编译成本高）。

换一个全新的目标架构时，这个问题最尖锐：**你不知道需要哪些工具、哪些库、哪些配置，因为从来没人在这上面编过。**

所以「再补几条检查」是走不通的——补的是特例，换环境就失效。

---

## 2. 破题：不从「失败」生成检查，从「声明」生成检查

关键判断：

> **构建失败，永远是「某个声明的要求没有被满足」。**
> **所以不该枚举失败，该枚举声明。**

为什么这能解决冷启动：

- **失败是样本**——你只见过发生过的那几次
- **声明是全空间**——源码树里每一个命令调用、每一条路径引用、每一个 `#include`，都是一份需求声明
- **声明是静态存在的**——编译只是去**验证**它们，不是去**产生**它们

**所以：只要源码同步完了，就可以生成检查清单。不需要编译过。**

---

## 3. 三类提取（缺一不可）

「从声明生成检查」只说了一半。完整的提取有三类：

| 类型               | 从什么提取         | 生成什么检查             | 例子                                      |
| ------------------ | ------------------ | ------------------------ | ----------------------------------------- |
| **需求提取** | 声明「我需要 X」   | X 存在吗                 | 脚本调用`mcopy` → `command -v mcopy` |
| **缺口提取** | 使用「我用了 X」   | X 被声明了吗             | 用`uint32_t` → 有没有 `<cstdint>`    |
| **语义提取** | 写法「我这么用了」 | 这个写法在当前环境成立吗 | `mcopy` 没带 `-o` → 覆盖会失败       |

前两类**完全能从源码树推出**；第三类不能，见第 8 节。

---

## 4. 声明的七个来源

把源码树当成一个「需求数据库」，它有七张表。

| #  | 声明来源                                                                         | 声明了什么需求                         | 提取方式                                      |
| -- | -------------------------------------------------------------------------------- | -------------------------------------- | --------------------------------------------- |
| S1 | 构建脚本里的命令调用（`.sh` / `Makefile` / GN `action` / `subprocess`）  | 需要哪些**宿主工具**             | 分词后取每行首词，滤掉 shell 关键字与内建命令 |
| S2 | `manifest.xml` 的 `<project>` + 源码里的路径引用                             | 需要哪些**源码仓**               | 读 XML + 扫`//path` 形式引用                |
| S3 | 产品`config.json` + 各部件 `bundle.json` 的 `deps`                         | 需要哪些**部件**（含传递闭包）   | 迭代求闭包                                    |
| S4 | 脚本里的编译器名（`$CC`、`aarch64-linux-gnu-gcc`…）+ `target_cpu` / board | 需要哪个**工具链**、什么目标架构 | 扫变量赋值与命令名 + 读配置字段               |
| S5 | `BUILD.gn` 的 `-lfoo` / `libs` + `.ld` 的 `ENTRY()` 与符号引用         | 需要哪些**库和符号**             | 扫链接参数 + 解析链接脚本                     |
| S6 | 源码的`#include <x.h>` / `#include "x.h"`                                    | 需要哪些**头文件**               | 扫 include 指令                               |
| S7 | 内核`defconfig` 名 / GN 的 `target_cpu`                                      | 需要哪些**配置文件**、架构名映射 | 读配置字段                                    |

**这七张表就是「全面」的边界。** 不是「我知道会遇到哪些问题」，而是「我知道需求一共有几类」。

### 命名约定（全文四套前缀，别混）

| 前缀                           | 全称                | 是什么                                                                             | 出现位置                                         | 例子                             |
| ------------------------------ | ------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------ | -------------------------------- |
| `S1`–`S7`                 | **Source**    | 声明的**七个来源**，同时也是**七个提取器**                             | §4、§5、§19、`extractors/s*.py`             | `S1-tool` = 工具需求提取       |
| `K1`–`K2`                 | **Knowledge** | 语义**知识库规则**（没有声明来源的那一类）；每条可带 `fix_recipe` 驱动修复 | §8、§9、§21、§28.6、`rules/knowledge.yaml` | `K1-IMG-005` = mcopy 缺 `-o` |
| `CHK-xxx`                    | **Check**     | **验证规则 ID**，写进 `requirements.json` 的 `check` 字段                | §17、§19、§20                                 | `CHK-EXISTS-CMD`               |
| `R1`–`R9`                 | **Risk**      | **实现风险**编号，只在本设计和实现方案里用                                   | §24、实现方案 §11                              | `R1` = S1 假阳性               |
| `ENV-` `BUILD-` `IMG-`… | —                  | **61 条问题的原始编号**，来自六类重新归类文件，**不是本文生成的**      | 全文                                             | `ENV-013` = `timeout` 缺失   |

> ⚠️ 早先的草稿里，验证规则用过 `R-` 前缀（`R-EXISTS-CMD`），**与风险编号 `R1`–`R9` 撞名**。
> 现已统一改为 `CHK-`——既避免混淆，也和 JSON 里的字段名 `check` 对上。

## 5. 关键：提取规则是环境无关的

这是整套方法能自动化的根本原因。规则**不随目标环境变化**：

| 声明形态         | 一律生成这种检查 | 判据                                      |
| ---------------- | ---------------- | ----------------------------------------- |
| 一个命令名       | 存在性           | `command -v`                            |
| 一个路径         | 存在性           | `test -f` / `test -d`                 |
| 一个部件名       | 可解析性         | 查部件图                                  |
| 一个`-lX`      | 库存在性         | `test -f libX.a`                        |
| 一个`#include` | 头文件可达性     | 搜索路径中能找到                          |
| 一个架构名       | 工具链身份       | `-dumpmachine` + `-E -v`              |
| 一个网络端点     | 可达性           | `getent hosts` + `curl -I --max-time` |

**换一个全新架构，不需要改规则，只是清单内容变了。**

这就是「不知道需要哪些检查」的答案：**不需要知道检查，只需要知道「怎么从声明推出检查」。规则只有七条。**

### 提取器比问题少一个量级

一个提取器就能覆盖多条问题。例如 S1（工具需求提取）：

> 扫脚本首词 → 逐个 `command -v` → 一次覆盖
> `ENV-003`(python)、`ENV-009`(qemu/ninja/node)、`ENV-013`(timeout)、
> `IMG-001`(mkfs.vfat)、`IMG-002`(mcopy)、`BUILD-001`(genconfig)

**这六条不是六个问题，是一个提取器的六次命中。**

## 6. 需求清单的格式

提取器的产出不是「问题清单」，是「需求清单」。每条记录必须自带出处，否则无法定位修复。

```json
{
  "kind": "tool",
  "name": "mcopy",
  "declared_at": "device/qemu/arm_virt/mkimage.sh:42",
  "declared_as": "mcopy -i $IMG rootfs/* ::",
  "extractor": "S1-tool",
  "check": "CHK-EXISTS-CMD",
  "verify_cmd": "command -v mcopy"
}
```

字段说明：

| 字段            | 作用                                                                |
| --------------- | ------------------------------------------------------------------- |
| `kind`        | 需求种类（tool / repo / part / lib / header / arch / config）       |
| `declared_at` | **出处**：哪个文件哪一行。这是报告里「缺什么 + 出自哪」的来源 |
| `declared_as` | 原始写法。语义提取器需要它做模式匹配                                |
| `extractor`   | 哪条提取规则产生的，便于统计各提取器的命中量                        |
| `check`       | 挂哪条验证规则                                                      |
| `verify_cmd`  | 实际执行的验证命令                                                  |

**报告要输出「缺什么 + 出自哪一行 + 怎么补」，不是布尔值。** 这是从 61 条逐条检查里继承下来的原则。

## 8. 语义提取：唯一不能从源码推出的那一类

有一批规则**不在源码里，只在经验里**：

| 条目          | 规则                                    | 为什么源码里没有 |
| ------------- | --------------------------------------- | ---------------- |
| `IMG-005`   | `mcopy` 覆盖要带 `-o`               | 工具用法知识     |
| `IMG-004`   | `mformat` 要写 `::` 而不是 `:`    | 工具用法知识     |
| `BUILD-004` | `#!/bin/sh` 的脚本不能用 `pushd`    | 语言知识         |
| `BUILD-005` | `#!/bin/sh` 的脚本不能用 `shopt`    | 语言知识         |
| `BUILD-008` | 用`uint32_t` 要 include `<cstdint>` | 标准库知识       |
| `BUILD-009` | `cp` 到某目录前要先 `mkdir -p`      | shell 行为知识   |

这些**不可能从目标源码里扫出来**，只能来自一个「工具语义规则库」。

**而 61 条问题，就是这个库的 v1。**

所以流水线实际有两个输入：

```
源码树  ──→  提取器（环境无关的规则）  ──┐
                                        ├──→ 需求清单 ──→ 验证器 ──→ 报告
知识库  ──→  语义匹配器（历史经验）    ──┘
（61 条 → 规则化）
```

## 9. 完备性验收实验（可证伪）

有了上面的架构，「这套方法全面吗」变成一个**能做的实验**：

> **实验**：只用七条提取规则（**不看** 61 条），从源码树生成需求清单；
> 然后问：**61 条问题涉及的声明，有多少条被清单覆盖到了？**

- 覆盖到的 → 提取器有效
- **覆盖不到的 → 说明扫描规则缺了一类，补规则，而不是补特例**

**补规则 vs 补特例，是这套方法能不能推广的分水岭。**
如果每遇到一个新问题就要加一条特例检查，它就退化成一份 checklist，换环境即失效。
如果每次都能归结为「缺了一类声明」，那规则集是收敛的。

## 10. 冷启动的真实边界

上面这套听起来很全，但有一个**结构性缺口**，必须说清楚：

| 需求类型                                          | 有声明来源吗             | 怎么检查                                        |
| ------------------------------------------------- | ------------------------ | ----------------------------------------------- |
| 工具 / 仓 / 部件 / 库 / 头文件                    | **有**（在源码里） | 提取声明 → 验证 ✅                             |
| **版本约束**（OS / Python / Node / 编译器） | **常常没有**       | 只能靠**白名单** ⚠️                     |
| **架构兼容性**                              | 部分有（`target_cpu`） | 有声明的能验，没声明的靠**已知矩阵** ⚠️ |

**版本约束和架构约束，往往不写在任何地方**——它们只存在于「实际环境」里。

这正是 `ENV-002`（Ubuntu 版本）、`ENV-004`（externally-managed）、`ENV-005`（Python 3.13）、`ENV-007`（商店 stub）的特征：**源码里没有任何一处声明「我需要 Python < 3.13」**。所以它们**不可能被扫描器扫出来**，只能靠一张已知兼容性白名单。

**这顺带解释了既有的分类：工具能归 A1（可被声明推导），版本只能归 A2（靠外部知识）。** 这不是人为划分，是这两类问题的**可推导性**根本不同。

**诚实的结论：这套流水线能覆盖「所有可声明的需求」，覆盖不了「未声明的隐含约束」。** 后者必须人工维护白名单。

| 情况                                | 条目                                                                                                                                                                             | 说明                                 |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |

## 12. 两种运行模式

| 模式             | 输入                                  | 覆盖                     | 适用           |
| ---------------- | ------------------------------------- | ------------------------ | -------------- |
| **冷启动** | 源码树 + 七条提取规则 + 语义知识库 v1 | 可声明的需求（约 60%）   | 新架构第一次跑 |
| **增量**   | 上面全部 +**历史失败库**        | 加上「未声明的隐含约束」 | 跑过几轮之后   |

**每次真的失败后，把新发现的约束写回知识库**——但它**不是运行时的依赖**，是知识库的成长。所以整套方法**仍然不需要「先编译一次」**，只是编译过之后会变得更全。

这就是冷启动与「越用越准」的平衡点：**冷启动可用，增量变全。**

## 14. 一句话总结

> 不要问「这个环境会遇到哪些问题」（答不出来），
> 要问「这棵树声明了哪些需求」（扫得出来）。
>
> **规则只有七条，清单由扫描生成。61 条问题是验收集和知识库，不是检查的输入。**
