# S3 部件提取程序使用说明

适用版本：0.3.0

说明日期：2026 年 10 月 30 日

S3 从源码配置中提取部件定义、产品选择、依赖关系和构建目标，整理成带有来源位置的 JSON 清单。本说明按“先运行，再读结果”的顺序介绍当前程序。

当前默认入口只运行 S3。输入已按团队的文件清单规范实现；输出是本项目自行设计的精简格式，尚未完成下游联调。使用结果前，请注意第 8 节列出的功能边界和两个已知问题。

## 1 程序解决什么问题

同一个部件的信息可能分散在几个文件中：

| 原文件 | S3 关注的内容 |
| --- | --- |
| `bundle.json` | 部件名称、所属子系统、依赖、特性和构建目标声明 |
| `ohos.build` | 部件定义及其 `module_list` 等声明 |
| `productdefine` 下的相关 JSON | 部件选择、基线配置、继承引用 |
| `vendor/*/*/config.json` | 产品配置中的部件选择及选项 |
| 分给 S3 的 `BUILD.gn` | `lite_subsystem` 或 `lite_subsystem_test` 中的目标列表 |

程序只处理输入清单中明确分给 S3 的文件；文件名符合上表，也不会自动绕过清单去读取。

流程是：

```text
源码根目录 + filelists.json
            ↓
      S3 读取并提取
            ↓
requirements.json + diagnostics.json
```

### 部件和构建目标的区别

部件是功能组织单位，构建目标是具体的构建任务。一个部件可以关联多个目标。

真实的 `c_utils` 样例中：

- `c_utils` 是部件名，所属子系统是 `commonlibrary`。
- `hilog`、`rust_cxx` 是它声明依赖的部件。
- `utils`、`utilsbase`、`utils_rust` 是它声明的构建目标。

`commonlibrary:c_utils` 表示“子系统:部件”。而 `//commonlibrary/c_utils/base:utils` 是 GN 目标标签：冒号前定位源码根下的目录，冒号后是目标名。两种名称不能混用。

GN 是构建配置工具，`BUILD.gn` 是它的配置文件。当前 S3 只读取相关声明，不运行 GN 或编译器。

## 2 先运行附带样例

需要 Python 3.9 或更高版本。提取器运行时只使用 Python 标准库。

在本分支的仓库根目录执行：

```sh
python3 -m src.l2_extract \
  --root examples/s3/source \
  --filelists examples/s3/filelists.json \
  --output out/s3-demo
```

服务器上如已有 L1 的 `filelists.json`，将 `--filelists` 换成它的路径，并将 `--root` 指向生成该清单时使用的源码根目录。

附带样例是人工构造的小型源码目录，包含 JSON 和 GN 声明。当前运行结果为：

```text
S3: 13 records; extraction complete; 0 diagnostics
```

程序还会打印两个输出文件的绝对路径。该样例的路由表包含 8 个文件，其中 7 个属于 S3，另外 1 个只属于 S1，因此诊断中的 `files` 是 7。

### 命令参数

| 参数 | 是否必填 | 作用 |
| --- | --- | --- |
| `--root` | 是 | 实际源码根目录 |
| `--filelists` | 是 | 输入清单文件的路径 |
| `--output` | 否 | 输出目录，默认是当前运行目录下的 `out/s3` |
| `--evidence` | 否 | 加上后额外写出详细证据文件 |

`--output` 指定的是目录，不是 JSON 文件名。它必须位于被检查的源码根目录之外。默认两个输出文件名称固定，再次运行到同一个输出目录会替换同名文件。

查看参数帮助：

```sh
python3 -m src.l2_extract --help
```

## 3 输入文件怎么读

实际输入文件叫 `filelists.json`。它的顶层是一个数组，每个对象描述一个文件：

```json
[
  {
    "path": "base/hiviewdfx/hilog/bundle.json",
    "classes": ["S3", "S6"]
  },
  {
    "path": "base/hiviewdfx/hilog/BUILD.gn",
    "classes": ["S1", "S4", "S5", "S7"]
  }
]
```

逐项读：

| 字段 | 含义 | 在这个例子中 |
| --- | --- | --- |
| `path` | 相对源码根的文件路径 | 定位到具体的 `bundle.json` 或 `BUILD.gn` |
| `classes` | 应该处理该文件的提取器类别 | 第一条交给 S3 和 S6，第二条没有分给 S3 |

S3 会打开第一条对应的文件，跳过第二条。不是所有 `BUILD.gn` 都归 S3。

清单中没有文件内容。程序要结合 `--root` 才能打开源码，例如：

```text
源码根目录：/srv/openharmony
相对路径：base/hiviewdfx/hilog/bundle.json
实际文件：/srv/openharmony/base/hiviewdfx/hilog/bundle.json
```

### 文件清单和格式说明的区别

| 文件 | 用途 |
| --- | --- |
| `filelists.schema.json` | 规定清单允许哪些字段、字段类型及取值，附有示例 |
| `filelists.json` | 上游扫描后得到的实际文件列表，是程序需要读取的输入 |

`filelists.schema.json` 中的 `examples` 是示例集合；其中第一个完整示例，即 `examples[0]`，才是一份文件清单。不要把整份 Schema 或外层 `examples` 数组直接当成输入。

### 输入必须满足的规则

- 每条只能有 `path` 和 `classes`，同一个路径只能出现一次。
- `path` 使用正斜杠和相对路径，不包含 `.`、`..` 路径段，不以斜杠结尾。
- `classes` 非空、不重复，并按 `S1,S3,S4,S5,S6,S7` 排序。
- S2 已移除；清单不携带 `root`、`kind`、`meta`、`stats` 等字段。
- 整个清单可以是空数组 `[]`。被分给某个提取器，不代表一定能从该文件中提取到声明。

程序先检查整份路由表的格式，再读取含 S3 类别的文件。规范见 [输入 Schema](../schema/filelists.schema.json)。

## 4 输出文件是什么

默认生成两个文件，显式加 `--evidence` 时生成第三个：

| 文件 | 内容 | 通常由谁使用 |
| --- | --- | --- |
| `requirements.json` | 精简的部件声明和关系记录 | 查看结果的人、后续验证模块 |
| `diagnostics.json` | 本次处理数量、完成状态和问题 | 运行程序的人、调用程序的代码 |
| `evidence.json` | 原文、哈希、精确位置及内部关联信息 | 排查提取问题时使用 |

`requirements.json` 是数组，每条至少有三个字段：

| 字段 | 含义 |
| --- | --- |
| `kind` | 这是一条什么类型的记录 |
| `name` | 这条记录的主体或关系对象，含义随 `kind` 改变 |
| `at` | 声明所在的文件路径和行号，行号从 1 开始 |

输出按来源文件和行号排序。同一位置的 GN 赋值操作保留先后次序，不应随意重排。

## 5 用 c_utils 带读一次完整输出

这一节使用项目保存的 OpenHarmony 6.0 真实 `bundle.json`。归档目录叫 `commonlibrary_c_utils`，所以 `at` 中使用这个名字；文件内声明的 GN 标签仍保留原始源码路径 `commonlibrary/c_utils`。

输入样例已保存为 [c_utils.filelists.json](../examples/s3/c_utils.filelists.json)：

```json
[
  {
    "path": "commonlibrary_c_utils/bundle.json",
    "classes": ["S3", "S6"]
  }
]
```

在仓库根目录执行：

```sh
python3 -m src.l2_extract \
  --root examples/s2_s3_sources/OpenHarmony-v6.0-Release \
  --filelists examples/s3/c_utils.filelists.json \
  --output out/s3-c-utils
```

这次只读取一个 `bundle.json`，输出 5 条记录。下面是完整内容，仅调整了排版：

```json
[
  {
    "kind": "component",
    "name": "commonlibrary:c_utils",
    "at": "commonlibrary_c_utils/bundle.json:15",
    "features": [
      "c_utils_feature_coverage",
      "c_utils_debug_refbase",
      "c_utils_track_all",
      "c_utils_print_track_at_once",
      "c_utils_debug_log_enabled",
      "c_utils_feature_intsan",
      "c_utils_parcel_object_check",
      "c_utils_feature_enable_pgo",
      "c_utils_feature_pgo_path"
    ],
    "adapted_system_type": ["standard"]
  },
  {
    "kind": "requires",
    "name": "hilog",
    "at": "commonlibrary_c_utils/bundle.json:32",
    "from": "commonlibrary:c_utils"
  },
  {
    "kind": "requires",
    "name": "rust_cxx",
    "at": "commonlibrary_c_utils/bundle.json:33",
    "from": "commonlibrary:c_utils"
  },
  {
    "kind": "requires",
    "name": "bounds_checking_function",
    "at": "commonlibrary_c_utils/bundle.json:36",
    "from": "commonlibrary:c_utils",
    "category": "third_party"
  },
  {
    "kind": "build_targets",
    "name": "commonlibrary:c_utils",
    "at": "commonlibrary_c_utils/bundle.json:40",
    "field": "sub_component",
    "targets": [
      "//commonlibrary/c_utils/base:utils",
      "//commonlibrary/c_utils/base:utilsbase",
      "//commonlibrary/c_utils/base:utils_rust"
    ]
  }
]
```

### 第一条是部件定义

`kind: "component"` 表示定义了一个部件。`name: "commonlibrary:c_utils"` 表示部件叫 `c_utils`，归属 `commonlibrary` 子系统。

`features` 列出原文件声明的特性名称，不表示这些特性已经开启。`adapted_system_type: ["standard"]` 保留该部件声明的适用系统类型。

`at` 中的第 15 行定位到 `component` 对象的起始位置；它不一定就是 `name` 字段所在行。

### 第二至四条是依赖关系

以第二条为例：

- `kind: "requires"`：这是一条依赖。
- `name: "hilog"`：被依赖的对象是 `hilog`。
- `from: "commonlibrary:c_utils"`：发起依赖的是 `c_utils`。
- `at: "...bundle.json:32"`：依赖声明位于第 32 行。

连起来就是：**c_utils 依赖 hilog，依据是该文件的第 32 行。**

第三条用相同方式记录对 `rust_cxx` 的依赖。第四条增加 `category: "third_party"`，表示这个依赖来自原文件的 `deps.third_party` 分类。

这些记录保留声明，不代表已经找到或验证了依赖对象。

### 第五条是构建目标列表

`kind: "build_targets"` 表示构建目标声明。此时 `name` 是拥有这些目标的部件，`field: "sub_component"` 表示列表来自原文件的 `component.build.sub_component`。

`targets` 中的三个标签按原文保存。例如：

```text
//commonlibrary/c_utils/base:utils
```

`//` 表示从源码根开始定位，`commonlibrary/c_utils/base` 是目录，`utils` 是该目录 `BUILD.gn` 中的目标名。标签不是编译产物的文件路径，也不是部件名。

这条列表直接从 `bundle.json` 取得。当前输出不因出现这些标签就继续打开对应 `BUILD.gn`，也不据此判断目标是静态库还是动态库。

## 6 九种记录类型和字段含义

### kind 的全部取值

`kind` 后面的值由程序规定。`name` 中的实际名称或路径来自源码，不能预先列出固定全集。

| kind | 含义 | name 放什么 | 关键附加字段 |
| --- | --- | --- | --- |
| `component` | 部件定义 | 部件身份，通常为“子系统:部件” | 有声明时保留 `features`、`adapted_system_type`、`adapted_kernel` |
| `requires` | 部件直接依赖 | 被依赖对象的原始名称 | `from`；第三方依赖另有 `category` |
| `selects` | 配置中的部件选择 | 被选择的部件身份 | `from` 为配置路径；非空选项放在 `options` |
| `inherits` | 配置继承引用 | 被引用配置的路径 | `from` 为当前配置路径 |
| `system_component` | 配置中同名字段的引用 | 被引用文件的路径 | `from` 为当前配置路径 |
| `build_targets` | JSON 中的构建目标声明 | 所属部件身份 | `field`、`targets` |
| `conditional_requires` | 内核或板卡条件依赖 | 声明条件依赖的部件身份 | `category`、`value`、`symbolic` |
| `subsystem` | GN 子系统声明 | 子系统名称 | `template`；必要时还有 `when`、`symbolic` |
| `subsystem_components` | GN 子系统目标列表的一次赋值 | 所属子系统名称 | `op`；以及 `targets` 或 `expression`，必要时还有 `when`、`symbolic` |

缺少子系统身份时，部件名称可能保留为未限定名称，同时产生诊断；不能假设所有 `name` 都带冒号。`requires.name` 本来就保留依赖的原始写法，例如 `hilog`。

`selects` 记录的是配置声明。如果 `options` 包含 `is_exclude` 等选项，后续消费者必须一起理解，不能直接把每条记录都当成实际启用的部件。

### 附加字段逐项解释

| 字段 | 当前可能出现的值或形式 | 怎么理解 |
| --- | --- | --- |
| `from` | 部件身份或配置路径 | 依赖、选择、引用关系由谁发起 |
| `category` | `third_party`、`kernel_special`、`board_special` | 依赖的分类，具体含义取决于记录类型 |
| `field` | `sub_component`、`modules`、`group_type`、`module_list`、`targets` | JSON 源文件中承载构建目标信息的字段 |
| `targets` | GN 字符串列表，或 JSON 构建字段的原始值 | GN 列表可直接读取各标签；JSON 值需结合 `field` 理解，不保证总是扁平字符串数组 |
| `options` | 对象 | 部件选择条目的附加选项，如特性赋值、排除标记 |
| `features` | 数组 | 部件定义声明的特性名称；与选择条目 `options.features` 的赋值含义不同 |
| `adapted_system_type` | 数组，例如 `["standard"]` | 部件声明适用的系统类型 |
| `adapted_kernel` | 数组，值取自源码 | 部件声明适用的内核 |
| `template` | `lite_subsystem` 或 `lite_subsystem_test` | GN 子系统使用的模板名 |
| `op` | `=`、`+=`、`-=` | 设置列表、添加列表元素、移除列表元素 |
| `when` | 条件字符串数组 | 声明所在的条件或循环上下文，程序未选择生效分支 |
| `expression` | 原始表达式字符串 | 无法直接解释为纯字符串列表时保留完整表达式 |
| `symbolic` | `true` | 包含未求值的名称、变量或条件依赖等内容 |
| `value` | 条件依赖的原始内容 | 与 `conditional_requires.category` 配合阅读 |

只有需要时才输出附加字段，不会给每条记录补齐一堆空值。没有 `symbolic` 也不代表声明无条件生效，还要查看 `when`。

当前精简输出的结构定义见 [输出 Schema](../schema/requirements.s3.schema.json)。

## 7 GN 条件记录怎么读

下面是一段用于讲解的人工样例，文件路径设为 `build/lite/config/subsystem/demo/BUILD.gn`：

```gn
lite_subsystem("demo") {
  subsystem_components = [ "//ipc:ipc" ]
  if (enable_hilog) {
    subsystem_components += [ "//hilog:hilog" ]
  }
}
```

程序产生三条记录：

```json
[
  {
    "kind": "subsystem",
    "name": "demo",
    "at": "build/lite/config/subsystem/demo/BUILD.gn:1",
    "template": "lite_subsystem"
  },
  {
    "kind": "subsystem_components",
    "name": "demo",
    "at": "build/lite/config/subsystem/demo/BUILD.gn:2",
    "op": "=",
    "targets": ["//ipc:ipc"]
  },
  {
    "kind": "subsystem_components",
    "name": "demo",
    "at": "build/lite/config/subsystem/demo/BUILD.gn:4",
    "op": "+=",
    "targets": ["//hilog:hilog"],
    "when": ["enable_hilog"]
  }
]
```

第一条声明子系统 `demo`；第二条记录列表的初始赋值；第三条记录“在 `enable_hilog` 条件下添加 `//hilog:hilog`”。

程序没有计算 `enable_hilog` 的值，所以第三条带有 `when`，诊断包含 `GN_CONDITIONAL`，整体状态是部分完成。不能直接将两条目标列表合并成“必定启用 ipc 和 hilog”。

遇到列表变量或拼接，例如 `common_components + ["//extra"]`，程序保存整个 `expression` 并标记 `symbolic: true`。遇到包含变量插值的字符串列表，会保留 `targets` 的原文并标记 `symbolic`。程序不自动读取导入文件来求这些变量的值。

## 8 诊断信息和当前限制

### diagnostics.json 的字段

c_utils 样例的实际诊断为：

```json
{
  "complete": true,
  "files": 1,
  "records": 5,
  "messages": []
}
```

| 字段 | 含义 |
| --- | --- |
| `complete` | 当前实现对本次提取给出的完成状态，需结合下面的已知问题使用 |
| `files` | 输入清单中分配给 S3 的文件数，包括读取失败的文件 |
| `records` | 输出的记录数，不是部件数量；一个部件可能产生多条记录 |
| `messages` | 问题列表，通常包含 `code`、`message` 和可定位时的 `at` |

终端退出码供脚本判断结果：

| 退出码 | 含义 | 输出情况 |
| --- | --- | --- |
| `0` | 程序报告提取完成 | 已写出需求和诊断 |
| `1` | 程序报告部分完成，如条件或变量待解析、源文件读取失败 | 仍写出可用的部分结果和诊断 |
| `2` | 参数、输入清单或输出操作错误 | 不应使用可能残留的旧输出冒充本次结果 |

`complete: true` 只涉及本次输入和实现支持范围，不表示源码树完整、依赖满足、目标存在或构建成功。

### 常见问题怎么处理

| 现象 | 先检查什么 |
| --- | --- |
| 提示输入必须是数组 | 是否误传了 `filelists.schema.json`，或用了旧 `meta/files/kind` 格式 |
| 提示类别不合法 | 是否仍包含 S2，类别是否重复或顺序错误 |
| `REFERENCE_MISSING` | `--root` 与相对路径拼接后，文件是否实际存在 |
| `REFERENCE_OUT_OF_SCOPE` | 路径或符号链接是否指到了源码根之外 |
| `GN_SYMBOLIC`、`GN_CONDITIONAL` | 结果中是否有 `symbolic`、`expression`、`when`；这些内容还未求值 |
| `GN_UNSUPPORTED_SYNTAX` | 查看对应源码；可能是未支持的 GN 写法，也可能是语法损坏 |
| `INVALID_STRUCTURE` | 原 JSON 字段的类型或结构是否正确 |
| 输出目录被拒绝 | 是否把输出目录放在了 `--root` 内部 |

### 当前版本的两个已知问题

以下问题尚未修复，属于实际实现缺陷：

1. **正常空结果可能被标为不完整。** 某个合法 GN 文件没有 S3 子系统声明时，当前会生成 `GN_NO_SUBSYSTEM` 并令 `complete` 为 `false`；部分无相关结构的 JSON 也会生成 `S3_UNRECOGNIZED`。上游路由规范允许提取结果为空，因此不能仅凭这种提示认定源码有错。
2. **空的错误字段可能被忽略。** 产品配置若写成 `{"parts": []}`，当前可能返回空结果且 `complete: true`；`parts` 应为对象，这种类型错误本应被报告。

### 功能边界

- 默认入口只提取声明，不展开产品继承后计算最终生效部件，也不递归计算完整依赖闭包。
- GN 支持子系统声明的结构读取，不是完整 GN 解释器；变量、分支和循环不执行求值。
- c_utils 中的 `inner_kits` 头文件列表和 `build.test` 测试目标，目前不进入精简主输出。
- 主输出不携带完整原文和哈希。需要排查来源时，可加 `--evidence`；哈希是文件内容的指纹，用于比较文件内容是否变化，下游日常读取主输出不需要它。
- 当前完成的是离线样例和代码测试；新接口尚未完成完整源码树验证及团队下游联调。

## 9 如何交给下游

主数据文件是 `requirements.json`；应同时交付 `diagnostics.json`，让下游识别部分结果和待处理项。源码根目录、目标产品等运行上下文需要由调用方另外传递，不能从当前主输出中猜测。

下游读取时，应先按 `kind` 分支，再解释 `name` 及附加字段。例如 `requires.name` 是被依赖对象，`build_targets.name` 是拥有目标的部件；将两者直接合并成一个“部件名称列表”会丢失关系。

团队已冻结的是 `filelists.json` 输入。当前精简输出与旧 `requirements.schema.json` 的外层和字段不同，不能直接当成旧格式送给旧读取器。应按当前 [S3 输出 Schema](../schema/requirements.s3.schema.json) 与验证模块约定交接方式。

需要在 Python 中调用时：

```python
import json
from pathlib import Path
from src.l2_extract.s3_pipeline import extract_s3

filelists = json.loads(Path("examples/s3/filelists.json").read_text(encoding="utf-8"))
requirements, diagnostics, evidence = extract_s3("examples/s3/source", filelists)
```

该函数返回三个 Python 对象，不自动写文件；命令行入口负责保存输出。
