### 32.0.1 三个问题

对每个对象，本文按同一模板回答：

| 问题                | 落点                                                                   |
| ------------------- | ---------------------------------------------------------------------- |

### 32.0.2 识别强度分级

本文把“认出一个文件”的判据按可靠性排序：

| 强度 | 判据                      | 例子                                                                                        | 误判风险                 |
| ---- | ------------------------- | ------------------------------------------------------------------------------------------- | ------------------------ |
| A    | **精确文件名**      | `bundle.json`、`ohos.build`、`Makefile`、`Kconfig` | 极低                     |
| B    | **路径 + 后缀**     | `vendor/*/*/config.json`、`arch/<arch>/configs/*_defconfig`  | 低                       |
| C    | **后缀 + 内容签名** | `.json` 里出现 `component.deps.components`；`BUILD.gn` 里出现 `toolchain(`            | 中                       |
| D    | **仅后缀**          | `.c`、`.cpp`、`.ld`、`.sh`                                                          | 中（同类文件多用途）     |
| E    | **仅 shebang**      | 无后缀 shell 脚本                                                                           | 高（也可能被当数据文件） |

一个对象往往同时有多个载体，且不同载体强度不同。**路由应优先走 A/B，C 只作兜底和校验，D/E 只用于“文件形态”这一层。**

### 32.0.3 证据核验方式

本文每条结论都绑定一个证据编号 `[E..]`，索引见 §32.11。核验方式分四档：

| 标记               | 含义                                                |
| ------------------ | --------------------------------------------------- |
| **本地克隆** | 源码树已完整克隆到 `_ohos_probe/`，逐文件读取；最强 |
| **抓取正文** | 用 `raw` URL 取到文件正文并核对                   |
| **仅 200**   | 只确认路径存在，未逐行核对正文                      |
| **官方文档** | 用于语义/格式说明，不用于证明某版本的实际目录布局   |

> 说明：本会话中 `source.android.com`、`docs.kernel.org`、`cmake.org`、`sourceware.org` 等文档站多次返回 `000`，因此这些只作**语义定位**，不作为布局证据；布局证据一律用可抓取的源码文件。

### 32.0.4 结论摘要

1. **后缀单独只对 4 类载体够用**：C/C++ 源文件（`.c/.cc/.cpp/.h/.hpp`）、链接脚本（`.ld/.lds`）、符号版本脚本（`.map`）、内核 defconfig（`*_defconfig`）。其余对象都必须叠加文件名或路径。
2. **`.json` 是最危险的后缀**：它几乎不携带对象语义。OHOS 里 `.json` 至少承载 6 种不同 schema（bundle、product、productdefine、inherit、device、platform）。XML 的 manifest 用途已随 S2 移除，本文不再覆盖。
3. **OHOS 的组件声明载体经历了 4 次换代**：1.0 `product/*.json` + `platform/*/platform.json`；2.2 `ohos.build` + `productdefine parts`；3.0 `bundle.json`（deps 为空）+ `ohos.build` 并存；3.1+ `bundle.json`（deps 有值）。**任何只认 `bundle.json` 的实现，在 2.2/3.0 会漏掉大半组件。**
4. **1.0 的组件依赖是完整的，2.2/3.0 反而丢了**：`platform.json` 有 `deps.components`；2.2/3.0 的 `ohos.build` 没有；3.1+ 的 `bundle.json` 才重新有。传递闭包能力是**非单调**的，验证器必须按版本降级。
5. **`target_cpu` 不是通用字段**：标准系统产品配置有，mini 系统配置即使到 7.0 也没有。lite 侧必须从 `config.gni` 的 `board_cpu/board_arch` 取。
6. **一个源码目录可以有多个组件**：3.2 的 `hiviewdfx_hilog` 目录里有 4 个 `bundle.json`，对应 4 个 `component.name`；按“目录根一个 bundle”解析会漏 3 个。
7. **跨 OS 同构的是“概念”，不是“文件名”**：组件、工具链、链接、配置各有一套；L1 需要“OS 画像”这一层，否则一套后缀规则无法同时覆盖。

## 32.2 S1 · 工具（tool）

### 32.2.1 对象定义

**S1 的对象是“构建/生成过程中会被调用的外部命令”**：shell 命令、Make recipe 里的命令、GN `action` 里 `script` 指向的解释器、Python 脚本里的 `subprocess`、以及 Python 包声明的运行时依赖。它不判断命令“能不能跑”，只提取“需要它”。

### 32.2.2 载体表

| 载体                                                      | 识别方式                         | 后缀单独够？                                          | 强度 | 证据       |
| --------------------------------------------------------- | -------------------------------- | ----------------------------------------------------- | ---- | ---------- |
| `*.sh` / `*.bash`                                     | 后缀                             | ✅ 够（但要知道是宿主脚本还是目标脚本）               | D    | [E29][E30] |
| 无后缀脚本                                                | 首行 `#!`                      | ❌ 只看后缀会漏                                       | E    | —         |
| `Makefile` / `makefile` / `GNUmakefile`             | 精确文件名                       | ✅ 文件名够                                           | A    | [E35]      |
| `*.mk`                                                  | 后缀                             | ⚠️ 可能是构建脚本，也可能是数据                     | D    | [E36]      |
| `BUILD.gn` / `*.gni` 的 `action`/`action_foreach` | 文件名 + 内容 `script = "..."` | ❌ 后缀只说明是 GN，不说明是工具                      | C    | [E31]      |

### 32.2.3 识别规则

S1 的识别分两步，**先定文件形态，再定“哪一段是工具调用”**：

```text
# 第一步：文件形态（L1，可不读正文）
if name in {"Makefile","makefile","GNUmakefile"} or suffix == ".mk": form = make
elif name == "BUILD.gn" or suffix == ".gni":                          form = gn
elif suffix in {".sh",".bash"}:                                       form = shell
elif suffix == ".py":                                                 form = python
elif name in {"setup.py","pyproject.toml","requirements.txt"}:        form = pydep
elif name == "CMakeLists.txt" or suffix == ".cmake":                  form = cmake
elif suffix in {".bb",".bbappend"}:                                   form = bitbake
elif name == "SConscript":                                            form = scons
elif suffix == "" and head2(path).startswith("#!"):                   form = shell
else:                                                                 form = other

# 第二步：内容切片（L2）
shell   -> 逐行取命令位置首词；滤内建/关键字；拆 sudo/timeout；env/time 降置信度
make    -> 只取以 TAB 开头的 recipe 行；变量赋值单独处理（LDFLAGS 归 S5）
gn      -> 只取 action/action_foreach 块里的 script= 与 args=
python  -> AST 取 subprocess.*/os.system/os.exec*/shutil.which/distutils.spawn.find_executable
pydep   -> setup.py 的 install_requires/python_requires；requirements.txt 的包名
cmake   -> add_custom_command/add_custom_target 的 COMMAND
bitbake -> do_compile/do_install/do_configure 里的命令
scons   -> DefineGroup/SConscript 的环境与工具
```

### 32.2.5 跨 OS 对照

| OS                       | 工具声明载体                                                                                               | 识别要点                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **AOSP**           | `Android.bp` 的 `genrule { cmd: ... }`；`Android.mk`；`build/soong` 的 Go 代码 | `genrule` 是内容签名；`Android.mk` 是文件名 |
| **Linux**          | `Makefile`/`Kbuild`/`scripts/*.sh`/`scripts/*.py`                                                  | `Makefile` 精确名；`scripts/` 路径          |
| **Zephyr**         | `CMakeLists.txt` 的 `add_custom_command`/`add_custom_target`；`scripts/*.py`；`west` 命令        | CMake 文件名 + 内容命令                         |
| **Buildroot**      | `package/*/*.mk` 的 `$(HOST_DIR)/bin/...`；`Makefile`；`support/scripts/*.py`                      | `.mk` + 路径 `package/`                     |
| **Yocto**          | `*.bb` 的 `do_compile`/`do_install`；`python do_...`；`bitbake` 本身                             | `.bb` 后缀 + 任务函数名                       |
| **RT-Thread**      | `SConscript` 的 `DefineGroup`；`rtconfig.py`；`building.py`                                        | `SConscript` 精确名                           |
| **NuttX / U-Boot** | `Makefile`/`Kbuild`/`scripts/*.sh`；U-Boot 的 `tools/`                                             | `Makefile` 精确名                             |

**结论**：S1 的后缀规则只能覆盖 `.sh/.py/.bb`；`Makefile`、`SConscript`、`CMakeLists.txt` 靠精确文件名；GN `action`、CMake `add_custom_command`、BitBake 任务函数靠内容签名。跨 OS 复用时要加一层“OS 画像”，否则会把 `SConscript` 当普通文本、把 `Android.bp` 当 JSON 之类的误判。

### 32.2.6 误判与漏判

| 风险                | 例子                                 | 处置                                                            |
| ------------------- | ------------------------------------ | --------------------------------------------------------------- |
| 把数据当脚本        | `.sh` 里其实是模板/测试数据        | 只在“有 shebang 或位于构建脚本目录”时提升置信度               |
| 把 shell 内建当工具 | `cd`、`echo`、`export`         | 黑名单 + 分词器识别                                             |
| 把包装器当工具      | `sudo make`、`timeout 10 make`   | 拆包装器；`env`/`time` 不算需求（见 07 的 C14 裁决）        |
| 变量展开取不到      | `$CC`、`${CROSS_COMPILE}gcc`     | 记为 `low`，同时交给 S4 解析变量定义                          |
| Python 依赖漏掉     | `setup.py` 的 `install_requires` | 必须单独扫 `setup.py`/`pyproject.toml`/`requirements.txt` |
| 只在注释里出现      | `# run make`                       | 去掉注释后再分词                                                |

## 32.4 S3 · 部件（component）

### 32.4.1 对象定义

**S3 的对象是“产品由哪些部件组成、部件依赖哪些部件、部件对外暴露哪些头文件和构建目标”**。它是 S1、S3–S7 里载体最复杂、版本差异最大的一个。

| 3.1  | `<dir>/bundle.json`                                         | 精确文件名                                               | ✅       | `deps.components` **有值**                                | [E19]      |
| 3.2  | `<dir>/bundle.json`，可多个                                 | 精确文件名 + `component.name`                          | ✅       | `deps.components` + `build.sub_component`                     | [E19][E20] |
| 3.2+ | `productdefine/common/products/*.json`                       | 路径 + `.json`                                         | ❌       | `target_cpu` + `inherit` + `subsystems[].components[]`      | [E21]      |
| 3.2+ | `productdefine/common/inherit/*.json`                        | 路径 + `.json`                                         | ❌       | 与 products **同 schema**，只能靠路径区分                   | [E23]      |
| 6.1  | `<dir>/bundle.json`                                         | 精确文件名                                               | ✅       | `deps.components` + `build.inner_kits[].header`               | [E22]      |
| 6.1  | `build/lite/config/subsystem/*/BUILD.gn`                     | 路径 + `lite_subsystem(...)`                           | ❌       | `subsystem_components = [...]`                                  | [E26]      |
| 6.1  | `device/<...>/<board>/<kernel>/ohos.build`                   | 精确文件名                                               | ✅       | `subsystem` + `parts` + `module_list`                       | [E25]      |

> **注意**：`bundle.json` 在 3.0/3.1 是**目录根一个**；3.2 的 `hiviewdfx_hilog` 有 4 个；4.0+ 又回到目录根一个。**必须扫描所有 `bundle.json`，按 `component.name` 建索引，不能假设“一目录一组件”。**

### 32.4.3 六种 schema，长得像但不是一个东西

| schema             | 典型文件                                 | 顶层键                          | 组件键                          | 依赖键                                     | 说明                                                      |
| ------------------ | ---------------------------------------- | ------------------------------- | ------------------------------- | ------------------------------------------ | --------------------------------------------------------- |
| A · 1.0 产品      | `build/lite/product/*.json`            | `subsystem`（**单数**） | `component`（**单数**） | 无                                         | `name` + `dir`（GN label）+ `features`              |
| B · 1.0 平台      | `build/lite/platform/*/platform.json`  | `subsystems`                  | `components`                  | `deps.components` / `deps.third_party` | `component` + `targets` + `optional`                |
| C · 2.2 部件      | `<dir>/ohos.build`                    | `subsystem` + `parts`       | `parts` map                   | 无（只有 `inner_kits`）                  | `module_list` + `variants`                            |
| D · 2.2–3.1 产品 | `productdefine/common/products/*.json` | `parts` map                   | 键 `subsystem:part`           | 无                                         | 无 `target_cpu`                                         |
| E · 2.2+ 厂商产品 | `vendor/*/*/config.json`               | `subsystems`                  | `components`                  | 无                                         | 标准产品有 `target_cpu`，mini 没有                      |
| F · 3.0+ 部件     | `<dir>/bundle.json`                   | `component`                   | `component.name`              | `deps.components`                        | 3.0 空，3.1+ 有值；`build.sub_component`/`inner_kits` |

**这六种 schema 的区分不能靠 `.json` 后缀，甚至不能只靠顶层键**：E 和 F 都有 `components`/`deps`，但一个在 `subsystems[]` 下、一个在 `component` 下；D 和 A 都有“产品”语义，但一个用 `parts`、一个用 `subsystem/component`。**路径 + 文件名是第一判据，内容签名是第二判据。**

### 32.4.7 productdefine 的子路径分类

`productdefine/common` 不是一个“产品目录”，而是五类文件的混合：

| 子路径                  | 语义                                           | 能否当产品种子？    | 证据       |
| ----------------------- | ---------------------------------------------- | ------------------- | ---------- |
| `products/*.json`     | 产品形态（system-arm64-default 等）            | ✅ 是               | [E21][E23] |
| `products/_*.json`    | 共享部件片段（如 `_ohos_common_parts.json`） | ❌ 不是产品         | [E27][E28] |
| `inherit/*.json`      | 可继承的部件模板（rich/headless/phone/...）    | ❌ 不是产品，是片段 | [E23][E24] |
| `base/*.json`         | 最小系统部件集合（mini/small/standard）        | ❌ 不是产品，是片段 | [E23]      |
| `device/*.json`       | 指令集/设备信息（3.0/3.1 有；6.1 本地树没有）  | ❌ 不是产品         | [E27]      |
| `bundle.json`（目录根） | `productdefine_common` 自身的组件声明        | ❌ 不是产品         | [E27]      |

**关键**：`products/`、`inherit/`、`base/` 的 JSON **schema 完全相同**（都是 `subsystems[].components[]`）。**只靠内容无法区分“产品”和“片段”，必须靠路径。** 这是“后缀不够、路径必须”的最强例证。

6.1 README 明确写了合并顺序（[E24]）：

```text
1. 先加载 inherit 中的部件列表；
2. 加载 subsystems 中的部件列表；
3. （设备/形态配置按 target_cpu/type 继续合并）
```

  "subsystem": "device_arm_virt",
  "parts": {

这是 4.0/6.1 仍然存在的**设备级组件声明**。S3 如果只扫目录根 `bundle.json`，会漏掉板级 chipset 组件。

### 32.4.9 跨 OS 对照

| OS                       | 组件/包声明载体                                                                                                  | 识别要点                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **AOSP**           | `Android.bp` 的 `cc_library`/`cc_binary`/`filegroup`；`PRODUCT_PACKAGES +=`（`target/product/*.mk`） | `Android.bp` 精确名 + 内容模块类型；`PRODUCT_PACKAGES` 内容签名 [E61][E62] |
| **Buildroot**      | `package/<pkg>/Config.in` + `<pkg>.mk`；`BR2_PACKAGE_*`                                                    | 路径 `package/*/` + 文件名 [E67]                                             |
| **Yocto**          | `meta-*/recipes-*/**/*.bb`；`IMAGE_INSTALL`                                                                  | `.bb` 后缀 + 路径 `recipes-` [E69]                                         |
| **Zephyr**         | 无中央组件清单；`west.yml` 项目 + CMake target + `prj.conf` 的 `CONFIG_*`                                  | 概念弱同构 [E64][E65]                                                          |
| **RT-Thread**      | `SConscript` 的 `DefineGroup`；`Kconfig` 的 `config`                                                     | `SConscript` 精确名 + 内容 [E71]                                             |
| **NuttX / U-Boot** | `Kconfig` 的 `config`；`Makefile` 的对象列表                                                               | `Kconfig` 精确名 + 内容 [E78]                                                |

**结论**：S3 是“概念同构、载体完全不同”的典型。OHOS 内部又有 6 种 schema。**S3 的 `kind=component` 必须配 `carrier` 子字段**（`bundle`/`ohosbuild`/`productdefine.products`/`productdefine.inherit`/`productdefine.base`/`vendor.config`/`platform.json`/`lite_subsystem`/`device.ohosbuild`），否则提取器无法知道该按哪套 schema 解析。

## 32.5 S4 · 工具链（toolchain）

### 32.5.1 对象定义

**S4 的对象是“目标架构 + 编译器/链接器/归档器 + 它们的路径与前缀”**。它既包括“用什么工具”（`clang`、`aarch64-linux-ohos-gcc`），也包括“为哪个架构”（`arm`、`arm64`、`riscv64`、`loongarch64`）。

### 32.5.2 载体表

| 载体                                                                                  | 识别方式                                                                            | 后缀够？  | 强度 | 证据       |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | --------- | ---- | ---------- |
| product JSON 的 `target_cpu`                                                        | 内容键 + 路径 `vendor/*/*/config.json` / `productdefine/common/products/*.json` | ❌        | B+C  | [E21][E44] |
| product JSON 的 `board` / `device_company` / `kernel_type` / `kernel_version` | 内容键 + 路径                                                                       | ❌        | B+C  | [E16]      |
| `config.gni` 的 `board_cpu` / `board_arch` / `board_toolchain*`               | 文件名 `config.gni` + 路径 `device/...` + 内容键                                | ❌        | B+C  | [E39]      |
| 1.0 `build/lite/config/boards/*.gni` 的 `board_arch` / `board_cpu`              | 路径 + 内容键                                                                       | ❌        | B+C  | [E38]      |
| GN `toolchain("...") { cc= cxx= ar= ld= }`                                          | `.gn/.gni` + 内容签名                                                             | ❌        | C    | [E42][E43] |
| `build/toolchain/ohos/ohos_toolchain.gni` 的 `abi_target`                         | 路径 + 内容键                                                                       | ❌        | B+C  | [E41]      |
| `build/ohos_var.gni` 的 `target_platform_triple`                                  | 路径 + 内容键                                                                       | ❌        | B+C  | [E40]      |
| shell `CC=` / `CXX=` / `CROSS_COMPILE=`                                         | `.sh/.mk` + 内容                                                                  | ❌        | C    | [E29]      |
| CMake `CMAKE_C_COMPILER` / `CMAKE_TOOLCHAIN_FILE`                                 | `CMakeLists.txt`/`*.cmake` + 内容                                               | ❌        | C    | [E75]      |
| `rtconfig.py` 的 `CROSS_TOOL` / `PREFIX` / `EXEC_PATH`                        | 精确文件名 + 内容                                                                   | ✅ 文件名 | A+C  | [E71]      |
| Buildroot `BR2_TOOLCHAIN_*`                                                         | `*_defconfig`/`.config` + 内容                                                  | ❌        | C    | [E66]      |
| Yocto `MACHINE` / `TUNE_*` / `TARGET_PREFIX`                                    | `conf/machine/*.conf` + 内容                                                      | ❌        | B+C  | [E68]      |

### 32.5.3 识别规则

```text
# 标准系统：product JSON
if path matches vendor/*/*/config.json or productdefine/common/products/*.json:
    if "target_cpu" in json: emit(arch = target_cpu, source = path)
    if "board" in json:      emit(board = board, source = path)
    if "kernel_type" in json:emit(kernel = kernel_type, source = path)

# Lite 系统：board config.gni
if name == "config.gni" and "board_cpu" in text:
    emit(cpu = board_cpu, arch = board_arch,
         toolchain = board_toolchain,
         prefix = board_toolchain_prefix,
         path = board_toolchain_path,
         type = board_toolchain_type)

# GN toolchain 定义
if suffix in {".gn",".gni"} and re.search(r'toolchain\s*\(', text):
    emit(cc/cxx/ar/ld from assignments; abi_target if present)

# shell / Make
if form in {shell, make} and re.search(r'\b(CC|CXX|CROSS_COMPILE)\s*=', text):
    emit(compiler vars; confidence medium; cross-check with S1)
```

### 32.5.4 OHOS 版本矩阵

| 版本 | 标准系统                                                                                           | Lite 系统                                                                                                                | 备注                           |
| ---- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| 1.0  | `product/*.json` 的 `compiler: "clang"`；`board`/`kernel`                                  | `config/boards/*.gni` 的 `board_arch`/`board_cpu`                                                                  | 没有 `target_cpu` [E11][E38] |
| 2.2  | vendor `config.json` 有 `board`/`kernel_type`，**没有 `target_cpu`**                 | `device/.../config.gni` 的 `board_cpu`/`board_arch`/`board_toolchain*`；`build_lite/toolchain/{clang,gcc}.gni` | [E16][E39][E42]                |
| 3.0  | 同上，`target_cpu` 仍缺                                                                          | 同上                                                                                                                     | [E16]                          |
| 3.1  | productdefine 仍是 `parts`，**没有 `target_cpu`**；`bundle.json` 的 deps 已有值        | 同上                                                                                                                     | [E19][E79]                     |
| 3.2  | `productdefine`/`vendor` 标准产品有 `target_cpu`（3.2 vendor 已核对）                        | 同上                                                                                                                     | [E21][E80]                     |
| 4.0  | 标准产品有 `target_cpu`；mini 仍无                                                               | 同上                                                                                                                     | [E44]                          |
| 6.1  | `target_platform_triple`：arm/arm64/x86_64；`abi_target`：arm/arm64/riscv64/x86_64/loongarch64 | `config.gni` 字段稳定                                                                                                  | [E40][E41][E39]                |
| 7.0  | 未单独核对；预计与 6.1 同                                                                          | 同上                                                                                                                     | —                              |

**关键结论**：

1. **`target_cpu` 只覆盖标准系统**。mini 产品从 2.2 到 7.0 都没有；S4 必须能从 `config.gni` 的 `board_cpu`/`board_arch` 取。
2. **`target_cpu` 的值是 OS 内部名**（`arm`/`arm64`/`riscv64`/`x86_64`/`loongarch64`），不是 GNU triple；triple 由 `ohos_var.gni` 和 `ohos_toolchain.gni` 映射。
3. **`target_platform_triple` 只列了 3 种**（arm/arm64/x86_64），riscv64/loongarch64 在 `abi_target` 里；不要假设一个变量覆盖全部架构。
4. **1.0 的 `board_arch` 是 `armv7-a`、`rv32imc` 这类微架构名**，不是 `arm`；S4/S7 的 arch 归一化需要映射表。

### 32.5.5 跨 OS 对照

| OS                       | 工具链声明                                                          | 架构声明                                |
| ------------------------ | ------------------------------------------------------------------- | --------------------------------------- |
| **AOSP**           | `BoardConfig.mk` 的 `TARGET_*`；`Android.bp` 的 `toolchain` | `TARGET_ARCH`/`TARGET_ARCH_VARIANT` |
| **Linux**          | Makefile 的 `CROSS_COMPILE`/`CC`                                | `ARCH=`；`arch/<arch>/`             |
| **Zephyr**         | `ZEPHYR_TOOLCHAIN_VARIANT`；`west` 的 toolchain 配置            | board 名 + `CONFIG_*`                 |
| **Buildroot**      | `BR2_TOOLCHAIN_*`；`BR2_aarch64=y`                              | `BR2_<arch>`                          |
| **Yocto**          | `TUNE_*`/`TARGET_PREFIX`/`PREFERRED_PROVIDER_virtual/*`       | `MACHINE` + tune include              |
| **RT-Thread**      | `rtconfig.py` 的 `CROSS_TOOL`/`PREFIX`/`EXEC_PATH`          | `ARCH`/`CPU`                        |
| **NuttX / U-Boot** | `CROSS_COMPILE`/`CC`                                            | `ARCH`/`CONFIG_*`                   |

**结论**：S4 没有“统一后缀”。唯一稳定的判据是**键名**（`target_cpu`、`board_cpu`、`CROSS_COMPILE`、`TUNE_*`）和**路径**（`config.gni`、`BoardConfig.mk`、`conf/machine/*.conf`）。跨 OS 需要键名映射表，不是一个后缀规则能解决的。

## 32.6 S5 · 库与符号（lib + symbol）

### 32.6.1 对象定义

**S5 的对象是“链接时需要哪些库、链接脚本把哪些段/符号放到哪里、共享库导出哪些符号”**。它包含三类声明：

1. **链接需求**：`-lfoo`、`libs = [...]`、`LDLIBS`、`LITEOS_BASELIB`。
2. **链接布局**：`.ld/.lds` 的 `ENTRY`、`MEMORY`、`SECTIONS`、符号赋值。
3. **符号导出**：`.map` 版本脚本的 `global`/`local`。

### 32.6.2 载体表

| 载体                                                                  | 识别方式                              | 后缀够？      | 强度 | 证据       |
| --------------------------------------------------------------------- | ------------------------------------- | ------------- | ---- | ---------- |
| `BUILD.gn` 的 `libs = [...]` / `ldflags = [...]` / `-l${...}` | 文件名 + 内容                         | ❌            | C    | [E44]      |
| `*.mk`/`Makefile` 的 `LDFLAGS`/`LDLIBS`/`LITEOS_BASELIB`    | 文件名/后缀 + 内容                    | ⚠️ 文件级够 | C    | [E36]      |
| `config.gni` 的 `board_ld_flags`                                  | 文件名 + 路径 + 内容                  | ❌            | C    | [E39]      |
| `*.ld` / `*.lds`                                                  | 后缀                                  | ✅ 够         | D    | [E45][E76] |
| `*.map` 版本脚本                                                    | 后缀 + `{ global:` / `extern "C"` | ✅ 够         | D+C  | [E46]      |
| `BUILD.gn` 的 `version_script = "..."`                            | 文件名 + 内容                         | ❌            | C    | [E47]      |
| product/vendor JSON 的 `force_link_libs`                            | 路径 + 内容                           | ❌            | B+C  | [E44]      |
| `Android.bp` 的 `shared_libs`/`static_libs`/`ldflags`         | 精确名 + 内容                         | ✅ 文件级     | A+C  | [E62]      |
| CMake `target_link_libraries`                                       | 精确名 + 内容                         | ❌            | C    | [E75]      |
| `rtconfig.py` 的 `LIBS`/`LINKFLAGS`                             | 精确名 + 内容                         | ✅ 文件级     | A+C  | [E71]      |

### 32.6.3 识别规则

```text
# 链接需求
if form == gn and re.search(r'\b(libs|ldflags)\s*(\+?=)', text):
    extract list literals; for "-l${var}" emit symbolic requirement (var -> S3/S4)
if form == make and re.search(r'\b(LDFLAGS|LDLIBS|LITEOS_BASELIB)\b', text):
    extract "-lfoo"/"-Lpath"
if name == "config.gni" and "board_ld_flags" in text: emit(flags)

# 链接脚本
if suffix in {".ld",".lds"} and re.search(r'\b(ENTRY|SECTIONS|MEMORY|OUTPUT_ARCH)\s*\(', text):
    emit(sections, entry, memory regions, symbol definitions)

# 符号版本脚本
if suffix == ".map" and re.search(r'\{\s*global\s*:', text):
    emit(exported symbols from extern "C"/"extern "C++" blocks; local)
```

## 32.7 S6 · 头文件缺口（header gap）

### 32.7.1 对象定义

**S6 的对象是“某个翻译单元使用了某个类型/符号，但没有（直接或传递地）声明它”**。它是“使用 × 声明”的差集，不是“文件是否存在”。

### 32.7.2 载体表

| 载体                                                         | 识别方式      | 后缀够？            | 强度 | 证据       |
| ------------------------------------------------------------ | ------------- | ------------------- | ---- | ---------- |
| `.c` / `.cc` / `.cpp` / `.cxx`                       | 后缀          | ✅ 文件级够         | D    | [E49]      |
| `.h` / `.hpp` / `.hxx` / `.hh`                       | 后缀          | ✅ 文件级够         | D    | [E52]      |
| `.inc` / `.ipp` / `.tcc`                               | 后缀          | ⚠️ 可能被 include | D    | —         |
| `#include <...>` / `#include "..."`                      | 内容          | —                  | C    | [E49]      |
| 类型使用（`uint32_t`/`size_t`/`pthread_t`/...）        | 内容          | —                  | C    | [E49]      |
| `bundle.json` 的 `build.inner_kits[].header`             | 精确名 + 内容 | ✅ 文件级           | A+C  | [E22][E50] |
| 2.2 `ohos.build` 的 `inner_kits[].header`                | 精确名 + 内容 | ✅ 文件级           | A+C  | [E14][E51] |
| `BUILD.gn` 的 `include_dirs`/`public_configs`/`deps` | 文件名 + 内容 | ❌                  | C    | [E47]      |
| `compile_commands.json`                                    | 精确名        | ✅ 文件级（生成物） | A    | —         |

### 32.7.3 识别规则

```text
# 文件级：后缀直接路由到 S6
if suffix in {".c",".cc",".cpp",".cxx"}: role = source
if suffix in {".h",".hpp",".hxx",".hh"}: role = header

# 内容级：使用 × 声明
for each source/header:
    includes = parse_include_directives(text)       # 保留条件编译上下文
    used     = parse_type_identifiers(text)         # uint32_t, size_t, ...
    declared = resolve_headers(includes, include_dirs)  # 至少 1–2 层
    gaps     = used - declared
    # 只有 gaps 非空且不在条件编译的“非目标平台”分支里，才报
```

### 32.7.4 真实样例：条件编译是最大误报源

`hiviewdfx_hilog/frameworks/libhilog/hilog_printf.cpp`（[E49]）：

```cpp
#include <cerrno>
#include <cstdarg>
#include <cstdio>
#include <ctime>
#include <fstream>
#include <iostream>
#include <mutex>
#include <securec.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <sys/types.h>

#ifdef __LINUX__
#include <atomic>
#endif

#ifndef __WINDOWS__
#include <sys/syscall.h>
#include <sys/types.h>
#else
#include <windows.h>
#include <memory.h>
#endif
#include <unistd.h>

#include "log_timestamp.h"
#include "hilog_trace.h"
#include "hilog_inner.h"
#include "hilog/log.h"
...
```

同一个文件里还有：

```cpp
static uint32_t processQuota = 0;                 // line 148
uint32_t sumLen = (uint32_t)atomic_load(&gSumLen); // line 167
header.tv_sec = static_cast<uint32_t>(ts.tv_sec); // line 291
```

**三个事实**：

1. `<windows.h>` / `<memory.h>` 在 `#ifndef __WINDOWS__` 的 `#else` 分支里，目标平台是 OHOS 时**不应计入**。朴素扫描会把它们当缺失头。
2. `uint32_t` 在本文件没有直接 `#include <cstdint>`，但它通过 `hilog_common.h` 等传递获得；如果 S6 只查“直接 include”，会报大量假缺口。
3. `#if not (defined(__WINDOWS__) || defined(__MAC__) || defined(__LINUX__))` 这种写法要求解析器理解 C 预处理器表达式，不能只做字符串匹配。

**S6 的判据必须写清楚**（建议）：

> 报“缺口”的最低条件：类型在目标平台可达的代码分支中被使用；该文件的直接 include 链（深度 ≤ 2）中没有任何头文件声明该类型；且该类型不是编译器内建/语言关键字。

否则 S6 的误报率会高到不可用。

### 32.7.5 跨 OS

S6 是**最跨 OS 同构**的对象：C/C++ 源文件、`#include`、类型使用在所有 OS 上都一样。差异只在：

- OHOS 6.1+ 引入 Rust（`.rs`）和 ArkTS（`.ets`），当前 S6 不覆盖；
- 不同 OS 的 `include_dirs` 来源不同（GN/Make/CMake/SConscript）；
- 系统头文件集合不同（musl vs glibc vs newlib vs Zephyr libc）。

**结论**：S6 的文件识别可以只靠后缀；**对象识别必须读内容，且必须带条件编译模型**。

## 32.8 S7 · 配置与架构（config + arch）

### 32.8.1 对象定义

**S7 的对象是“构建时选择哪套内核/系统配置、目标是什么架构、配置项的值是什么”**。它既包括“选了哪个 defconfig”，也包括“defconfig 里的 `CONFIG_*` 值”和“架构目录”。

### 32.8.3 OHOS 的 4 层 defconfig 布局

`kernel_linux_config@6.1` 里有 **34 个** `*_defconfig`，分属 4 种布局（[E53]）：

| 布局                                       | 路径                                                                                                   | 语义                    | 选择变量                         |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ | ----------------------- | -------------------------------- |
| **base**                             | `linux-5.10/base_defconfig`                                                                          | 必选/安全红线，不可覆盖 | 固定加载                         |
| **type**                             | `linux-5.10/type/{small,standard}_defconfig`                                                         | 系统形态                | `build_type`                   |
| **chip**                             | `linux-5.10/<chip>/arch/<arch>_defconfig`（qemu/hispark_taurus/imx8mm/rk3568/unionpi_tiger/yangfan） | 芯片平台                | `target_cpu`                   |
| **arch/configs（扁平）**             | `linux-5.10/arch/{arm,arm64,riscv,x86,loongarch}/configs/<device>_<type>_defconfig`                  | 开发板完整配置          | `DEVICE_NAME` + `BUILD_TYPE` |
| **product**（README 有，树里未全见） | `<...>/product/<type>_defconfig`                                                                     | 产品类型                | `device_type`                  |

6.1 README 明确写了 5 层（base → type → form → chip → product）和选择变量（[E54]）：

```text
1. base：必选，不可覆盖
2. type：必选，由 build_type 选择
3. form：可选，由 build_variant 选择
4. chip：必选，由 target_cpu 选择
5. product：可选，由 device_type 选择
```

**但实际构建脚本 `kernel.mk` 用的是扁平布局**（[E55]）：

```make
KERNEL_CONFIG_PATH := $(OHOS_BUILD_HOME)/kernel/linux/config/${KERNEL_VERSION}
DEFCONFIG_FILE := $(DEVICE_NAME)_$(BUILD_TYPE)_defconfig
...
cp -rf $(KERNEL_CONFIG_PATH)/. $(KERNEL_SRC_TMP_PATH)/
$(KERNEL_MAKE) -C $(KERNEL_SRC_TMP_PATH) ARCH=$(KERNEL_ARCH) $(KERNEL_CROSS_COMPILE) $(DEFCONFIG_FILE)
```

也就是说：**README 描述的是“分层组合模型”，`kernel.mk` 直接调用的是“扁平完整 defconfig”**。两者在 6.1 同时存在。S7 不能假设“所有 `*_defconfig` 都是完整产品配置”，也不能假设“README 的层一定被当前构建使用”。

**内核版本与架构目录**（[E53]）：

| 内核版本       | 存在的布局                                                                        | 架构目录       |
| -------------- | --------------------------------------------------------------------------------- | -------------- |
| `linux-4.19` | `arch/arm/configs/*_defconfig`                                                  | `arch/arm`   |
| `linux-5.10` | `arch/{arm,arm64,riscv,x86,loongarch}/configs/` + 分层目录 + `base_defconfig` | 5 种           |
| `linux-6.6`  | `arch/arm64/configs/*_defconfig` + 分层目录 + `base_defconfig`                | `arch/arm64` |

**路径陷阱**：`kernel_linux_config` 在源码树里的位置是 `kernel/linux/config`。扫描器按树内路径识别，不要按目录名找；直接按 `kernel/linux/config/` 前缀匹配即可。

### 32.8.4 defconfig 内容签名

`arch/arm/configs/qemu-arm-linux_standard_defconfig` 开头（[E56]）：

```text
#
# Automatically generated file; DO NOT EDIT.
# Linux/arm 5.10.79 Kernel Configuration
#
```

`type/standard_defconfig` 开头（[E57]）：

```text
CONFIG_IRQ_WORK=y
CONFIG_BUILDTIME_TABLE_SORT=y
```

**结论**：不能只靠 `# Automatically generated` 判断 defconfig；`type/*` 可能直接以 `CONFIG_*` 开头。**内容签名应是“存在 `CONFIG_*` 行”，不是“存在自动生成头”。**

### 32.8.5 跨 OS 对照

| OS                  | 配置载体                                                      | 识别                           |
| ------------------- | ------------------------------------------------------------- | ------------------------------ |
| **Linux**     | `arch/<arch>/configs/defconfig`；`Kconfig`                | 路径 + 文件名 [E70][E78]       |
| **Zephyr**    | `boards/<...>/<board>_defconfig`；`prj.conf`；`Kconfig` | 文件名/路径 [E64][E65]         |
| **Buildroot** | `configs/*_defconfig`；`BR2_*`                            | 路径 `configs/` + 后缀 [E66] |
| **NuttX**     | `boards/<arch>/<chip>/<board>/configs/<cfg>/defconfig`      | 路径 [E72]                     |
| **U-Boot**    | `configs/*_defconfig`                                       | 路径 + 后缀 [E73]              |
| **AOSP**      | `BoardConfig.mk`；`PRODUCT_*`                             | 精确文件名                     |
| **Yocto**     | `meta/conf/machine/*.conf`；`TUNE_*`                      | 路径 + 后缀 [E68]              |
| **RT-Thread** | `rtconfig.h`/`rtconfig.py`；`Kconfig`                   | 精确文件名 [E71]               |

**结论**：`*_defconfig` 是跨 OS 最通用的后缀，但**“同名不同层”**（base/type/chip/board/product）必须靠路径区分；`Kconfig` 是 schema，不是值；`target_cpu` 是 OHOS 特有字段，不能当作跨 OS 通用键。

## 32.9 路由：从文件到 kind 到提取器

### 32.9.1 两阶段分类

研究结果表明，L1 的 `classify()` 如果只输出 12 个语义 `kind`，会丢失“这个 `.json` 到底是 bundle 还是 productdefine”这一层信息。建议改成**两阶段**：

```text
Stage A · 文件形态（lexical）
  suffix + exact name + shebang -> lex_kind
  例：json / gn / make / shell / python / c / header / ld / map / defconfig / kconfig

Stage B · 对象语义（semantic）
  path pattern + exact name + (optional) content signature -> (kind, carrier)
  例：(component, bundle) / (component, productdefine.products) /
      (config, defconfig.type) / (arch, board.gni)
```

**Stage A 不读内容**（shebang 只读首行），**Stage B 以路径/文件名为主要判据**；只有非标准布局才读内容签名。这样既符合 07 里“L1 纯函数、只按后缀与路径”的约束，又能把多 schema 的 `.json` 分开。

| `vendor/*/*/config.json`              | S3 / S4 / S5 / S7      | components / `target_cpu` / `force_link_libs` / `board`              |
| `productdefine/common/inherit/*.json` | S3                     | components（片段）                                                         |
| `*.ld`                                | S5 / S7                | symbols/sections / memory layout                                           |

因此 L1 的输出应是 `(path, lex_kind, [(kind, carrier), ...])`，而不是单值 `kind`。

### 32.9.4 与旧分工稿的差异

旧分工稿的 S3/S4/S7 描述基于“`bundle.json` + 产品 `config.json` + `target_cpu`”的简化模型。本研究实测后建议更新：

| 旧分工稿的表述                                                  | 实测差异                                                                                                                                    | 建议                                                                                      |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| S3：产品 `config.json` + 各部件 `bundle.json` 的 `deps`   | 1.0 没有 bundle；2.2 用 `ohos.build`；3.0 bundle 的 deps 为空；3.2 一个目录多个 bundle；6.1 还有 `device/**/ohos.build` 和 `lite_subsystem` | 增加 `ohosbuild`/`productdefine`/`lite.subsystem`/`device.ohosbuild` 四个 carrier |
| S4：编译器名 + `target_cpu`                                   | mini 产品没有 `target_cpu`；lite 用 `board_cpu`/`board_arch`/`board_toolchain*`                                                     | 增加 `board.gni` 路径；`target_cpu` 只用于标准系统                                    |
| S5：`BUILD.gn` 的 `-lfoo`/`libs` + `.ld` 的 `ENTRY()` | 还有 `LITEOS_BASELIB`、`force_link_libs`、`board_ld_flags`、`.map` 版本脚本                                                         | 增加 `make.link`/`versionmap`/`force_link_libs`                                     |
| S6：用了 `uint32_t` 却没有 `#include <cstdint>`             | 直接 include 可能通过传递头获得；条件编译分支会误报                                                                                         | 判据改为“直接/传递声明 + 目标平台分支”                                                  |
| S7：`defconfig` 名 / GN `target_cpu`                        | 4 层 defconfig；`kernel.mk` 用扁平布局；README 用分层模型；mini 无 `target_cpu`                                                         | 增加 `defconfig.base/type/chip/arch` 子类；S7 同时读 `config.gni`                     |
| S1：脚本 / Makefile / GN `action`                             | 还有 `setup.py`/`pyproject.toml`/`requirements.txt`/`CMakeLists.txt`/`.bb`/`SConscript`                                         | 增加 `pydep`/`cmake`/`bitbake`/`scons` carrier                                    |
