## 28. 修复段：检测出问题之后怎么办

前面 27 节解决的是「**查出问题**」。这一节解决「**查出之后**」——**用户要的不是一份报告，是「修好之后开始编译」**。

### 28.1 四档：分档依据不是问题类别，是「能否闭环验证」

六类分类回答「根因是什么」，但对「能不能自动修」**没有指导意义**——同一个类里，不同问题的可修复性天差地别。

真正的判据是：**修完之后，本机能不能确认它真的修好了？**

| 档                   | 判据                                            | 执行者                               | 闭环方式    | 例子                                                                                           |
| -------------------- | ----------------------------------------------- | ------------------------------------ | ----------- | ---------------------------------------------------------------------------------------------- |
| **A 装/配**    | 幂等命令，修完**重跑同一条 CHK** 即可确认 | 脚本                                 | ✅ 秒级     | `apt install mtools`、`git config --global safe.directory`、`chmod +x`、补拉仓库         |
| **B 改产物**   | 改文件内容，修完要**重扫**才能确认        | Agent 出 patch → 人审 → 脚本 apply | ✅ 但要重扫 | 补`#include <cstdint>`、`.ld` 补 `.ARM.exidx` 段、改 `bundle.json` 的 deps、改 GN 模板 |
| **C 换环境**   | 本机做不到；修完是「另一台机器」，本机验不了    | 人                                   | ❌          | Ubuntu 版本不在范围、Python 3.13、Windows 商店 stub、交叉编译器装不上                          |
| **D 根因未定** | 不知道改什么                                    | 人                                   | ❌          | `BUILD-006`、`BUILD-015`、`BUILD-016`、`NET-005`                                       |

**A / B 能闭环 → 可以自动走；C / D 不能闭环 → 必须停下来。**

> 自动化的前提不是「动作能执行」，而是「**执行完知道对不对**」。
> 一个能跑但无法验证的修复，比不修更危险——它把问题从「已知缺失」变成「未知损坏」。

> ⚠️ 下表的条数是**粗分**，还没有对着 61 条逐条走过。精确落点要按 27.2 那张表的方式重做一遍。
>
> | 档         | 粗估条数 |
> | ---------- | -------: |
> | A 装/配    |      ~17 |
> | B 改产物   |      ~17 |
> | C 换环境   |       ~9 |
> | D 根因未定 |        4 |

### 28.2 「根本性」的操作定义

**操作上它就是：修复动作无法在本机上闭环验证。** 落成四条硬规则：

| # | 规则                                             | 为什么                                         |
| - | ------------------------------------------------ | ---------------------------------------------- |
| 1 | 落在**C 档** → 放弃                       | 修了也得换机器，本机验不了                     |
| 2 | 落在**D 档** → 放弃                       | 不知道改什么                                   |
| 3 | A / B 档修了**N 次没收敛** → 放弃         | 反复修不好，说明判据本身有问题                 |
| 4 | 修复需要改**工具管辖范围外**的东西 → 放弃 | 例如要求改 manifest 的 remote 地址、动别人的仓 |

**关键：这个判定绝不能交给 Agent。** Agent 有强烈的「我再试一次」倾向，而放弃判据必须是硬的、可审计的。

**Agent 出候选，规则出裁决。**

### 28.3 Agent 分诊：每关一次

**粒度是「每个关一次调用」，不是「每条 finding 一次」。**

三种粒度比较：

| 粒度                    | 调用次数        | 问题                                                      |
| ----------------------- | --------------- | --------------------------------------------------------- |
| 每条 finding 一次       | 几十次          | 一半的调用在处理「缺个包」，而`command -v` 本身是毫秒级 |
| **每个关一次** ✅ | **~8 次** | —                                                        |
| 全局一次                | 1 次            | 丢掉关与关的上下文；且不尊重原则三的顺序                  |

**分诊的输入**：

```
本关全部 findings  +  knowledge.yaml  +  本关上下文 / 白名单
```

**「本关上下文」是能不能用上 Agent 的前置条件**——上下文不够，Agent 就得自己重扫源码树，又慢又容易跑偏。每关产出 finding 时要配齐：

| 字段                   | 为什么                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------- |
| `gate`               | 哪一关产出的，决定用哪套上下文、哪套允许动作                                          |
| `evidence`           | 原始输出。**半静态那关必须带冲突的两个 `.ninja` 的行号**，否则 Agent 得自己找 |
| `source_requirement` | 从`requirements.json` 里把源需求配上（`declared_at` / `declared_as`）           |
| `attempts`           | 已试过什么。**不然 Agent 会重复同一个修法**                                     |
| `allow`              | 本关允许的动作集（见 28.4）                                                           |

### 28.4 Agent 的围栏：只能四选一

**Agent 的输出是「决定」，不是「动作」。** 它不能自己改文件、不能自己跑命令——它说「这条走 `K1-IMG-005` 的 recipe」，然后**脚本**去执行。

| 动作              | 允许的档       | 说明                                         |
| ----------------- | -------------- | -------------------------------------------- |
| `apply_recipe`  | A / B          | 知识库里有`fix_recipe`，脚本执行           |
| `propose_patch` | **仅 B** | Agent 自己出 patch，**人审后**才 apply |
| `escalate`      | 全部           | 转人工，附上它已经查到的线索                 |
| `abandon`       | 全部           | 放弃 + 理由（**理由是要害**，见 28.6） |

**C / D 档的问题，连 `propose_patch` 都不给**——只能 `escalate` 或 `abandon`。

> 这一条是**安全围栏**，不是设计洁癖。
> `ENV-002`（Ubuntu 版本不在支持范围）如果放开了给 Agent，它可能去跑 `do-release-upgrade`——**那是灾难性的**。
> 从结构上让它够不着，比在提示词里叮嘱它别做更可靠。

**同时，这也是可审计、可回滚、可测试的前提**：决定是数据，动作是脚本。脚本路径能进 21.2 的 fixture 断言（「假树缺 mcopy → 断言产出 `apt-get install -y mtools`」）；「Agent 该说什么」没法这样断言。

### 28.5 闭环：两个回环，四条收敛判据

**A 档和 B 档的回环完全不同，不能混：**

|              | 小回环（A 档）                              | 大回环（B 档）                                                                               |
| ------------ | ------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 修复动作     | 执行命令                                    | 改文件                                                                                       |
| 修完重跑什么 | **只重跑产生该 finding 的那几条 CHK** | **必须回第 1 关重扫**                                                                  |
| 为什么       | 需求清单没变                                | 改了源码 →`requirements.json` 本身变了（补了 `#include` 后 S6 就不再产出那条 gap 需求） |
| 回滚         | 一般不需要（装东西不回滚）                  | **必须**（改坏了要撤销）                                                               |

**收敛判据（防死循环）：**

```
每轮结束，比对 findings 集合：
  ① 集合必须严格变小          否则 → 立即停（修复无效）
  ② 不允许多出新 finding      否则 → 立即停 + 回滚本轮全部改动
  ③ 单个 finding 修复上限 3 次
  ④ 整轮上限 5 轮
命中任一条 → 转「放弃」，并输出本轮改动清单
```

> **② 是最要紧的一条**：改 GN 模板很可能修好一条、弄坏三条。
> 不检测这个，循环会**越修越坏**。

### 28.6 知识库升级：`fix_recipe` 与自学习回路

现在 `knowledge.yaml` 只在**提取阶段**用（第 8 节：判 `mcopy` 缺 `-o` 这类语义）。给它加一个 `fix_recipe` 字段，它就能同时驱动**修复**：

```yaml
K1-IMG-005:
  problem: IMG-005
  detect:    mcopy 命令无 -o 参数
  fix_class: B
  fix_recipe: |
    在 mcopy 后加 -o，覆盖已存在的镜像内容
  patch_hint: 'mcopy -i "$IMG" rootfs/* ::'
            → 'mcopy -o -i "$IMG" rootfs/* ::'
  verify:    重跑该 finding 对应的 CHK
```

于是分诊变成：

```
每条 finding → 知识库里有没有 fix_recipe?
                 有 → Agent 只需确认适用 → apply_recipe（快、准）
                 无 → Agent 自己想办法 → propose_patch / escalate
```

**自学习回路**——这是这一节最值钱的地方。原来的第 12 节（增量模式）说的是「把新发现的**约束**写回知识库」。加上修复之后升级成：

> **把验证通过的修法也写回知识库。**

```
第 1 次遇到 → Agent 出 patch → 验证通过 → 写回 knowledge.yaml
第 2 次遇到 → 命中 fix_recipe → 脚本直接执行
```

**这让 Agent 的使用量随时间单调下降。** 知识库不只参与判断——它**因修复而成长**。

### 28.7 一个特例：第 2 关的修复对象是「工具自己」

第 2 关（[`03.2` §19.8](../src/l2_extract/README.md) 提取自检）报出来的是「某个扩展名的文件没人认领」。**它的修复动作是加一条提取规则——改的是扫描器自己的代码**，不是环境、不是源码树。

Agent 在这里很合适：读样本文件 → 判有没有声明形态 → 写规则。但**必须和运行期修复分开**：

|            | 对象                     | 在哪                                                 |
| ---------- | ------------------------ | ---------------------------------------------------- |
| 运行期修复 | 目标环境 / 源码树        | `fix/` 模块                                        |
| 自检修复   | **工具自己的代码** | **开发期动作**，产出 patch 给人，不进 `fix/` |

混在一起的后果是「工具在运行期把自己改了」——**这种改动没法回滚**。

### 28.8 诚实边界

**1. 判读那 6 条，编译前根本查不出。**

`BUILD-006` / `BUILD-015` / `BUILD-016` / `SYNC-001` / `BUILD-002` / `BUILD-020`——它们定义就是「只能读构建结果」。**所以预检的覆盖面天然少这 6 条**，方案不能假装全覆盖。

**2. Agent 改源码引入了原来没有的一类风险。** 见 24 节的 R11 / R12 / R13。

**3. `abandon` 时给的东西比「放弃」两个字重要得多。**

| 问题                    | 放弃时输出什么                                             |
| ----------------------- | ---------------------------------------------------------- |
| `ENV-002` Ubuntu 版本 | 支持区间 + 当前版本 + 「建议换 22.04」                     |
| `ENV-005` Python 3.13 | 「降到 3.11，命令：…」                                    |
| `ENV-007` 商店 stub   | 「关掉 Settings → App Execution Aliases 里的 python.exe」 |
| E 类网络不通            | 「哪个端点在哪个网络下测过 / 没测过」                      |
| **D 档根因未定**  | **Agent 查到的线索 + 候选根因排序**                  |

**最后一行是 D 档交给 Agent 的真正价值**——它不是自动修，是**把「根因未定」降级成「三个候选根因，按可能性排序」**，让人的判断成本大降。

### 28.9 默认选择

| 项               | 默认                            | 理由                              |
| ---------------- | ------------------------------- | --------------------------------- |
| Agent 改源码     | **dry-run**（只出 patch） | B 档是整条链上唯一有破坏性的动作  |
| A 档自动修       | **开**                    | 幂等且可验证；`--no-fix` 能全关 |
| C 档方案         | **含具体命令**            | 光说「Ubuntu 版本不对」没用       |
| `abandon` 裁决 | **规则**，Agent 只能建议  | 见 28.2                           |
