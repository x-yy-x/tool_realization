## 21. 离线自测：fixture 假树

这是方案能不能落地的分水岭。**没有真源码树，也能开发和验证全部提取器。**

### 21.1 假树内容

**内容已落盘**：[`../tests/fixture/`](../tests/fixture)，6 个文件。每个文件故意埋一条已知故障：

| 文件 | 埋的故障 / 用途 |
| --- | --- |
| `.repo/manifest.xml` | 4 个 project，含「目录缺失」和「revision 不符」两个故障；`src` 无 revision，用来验证继承 `refs/heads/master` |
| `build/build.sh` | 含包装器，且用了内建（用来验证黑名单） |
| `device/demo/chip/mkimage.sh` | 含 `IMG-005` 一个已知故障（`mcopy` 缺 `-o`）；`mformat` 写的是**正确**的 `::`，不埋故障 |
| `vendor/demo/board/config.json` | 1 个 subsystem、1 个 component，S3 闭包的输入 |
| `third_party/foo/bundle.json` | 依赖一个不存在的部件 |
| `src/a.cpp` | `BUILD-008` 的形态 |

> **文件内容以 `tests/fixture/` 下的实际文件为准。** 断言依赖字节精确（例如 `echo "config ok"` 必须**不**产生任何需求），改动假树前先看 §21.2 的断言清单。

### 21.2 断言清单

| 测试        | 断言                                                                                   |
| ----------- | -------------------------------------------------------------------------------------- |
| S1 正向     | 扫出 `timeout` / `hb`                                                          |
| S1 反向     | **不**扫出 `echo` / `if` / `fi` / `test` / `set`（内建与关键字被滤掉） |
| S1 包装器   | `timeout 500 hb build` 同时产出 `timeout` **和** `hb`                      |
| S1 树内引用 | `./build/genconfig.sh` **不**提取（`./` 相对路径 → 树内引用，见 §19.3.4）    |
| S1 引号     | `echo "config ok"` 不产生任何需求                                                    |
| S2 仓清单   | 4 个 project；`third_party/bar` 目录缺失被识别                                       |
| S2 revision | `build` 的 SHA 与 `git rev-parse` 不符被识别（落点不能是 `bar`——它目录都不在，没法 `rev-parse`） |
| S2 继承     | `src` 无 revision，继承到 `refs/heads/master`                                      |
| S3 闭包     | `foo → bar, missing_part`；`missing_part` 不在索引 → 报缺失                      |
| S6 缺口     | `src/a.cpp` 报 `uint32_t` 无 `<cstdint>`                                         |
| K1 语义     | `mcopy` 缺 `-o` 被报出；`mformat` 的 `::` 不误报                               |

### 21.3 收益

> **整套提取与知识库逻辑可以在 Windows 上开发、运行、验证，一次都不用连服务器。**
> 只有最后一关（拿真源码树跑覆盖率）需要上 目标机。

**这是「提取是环境无关的」这句话的兑现。**

## 22. 覆盖率实验怎么跑

`coverage/expected.yaml` 是靶子——把 61 条的「声明形态」逐条写出来：

```yaml
ENV-003:   {kind: tool, name: python}
ENV-009:   {kind: tool, name: ninja}
ENV-013:   {kind: tool, name: timeout}
IMG-001:   {kind: tool, name: mkfs.vfat}
IMG-002:   {kind: tool, name: mcopy}
BUILD-001: {kind: tool, name: genconfig}
SYNC-002:  {kind: repo, name: build}
SYNC-004:  {kind: repo, name: arkui_ace_engine}
BUILD-026: {kind: repo, name: third_party/asmjit}
BUILD-008: {kind: gap,  name: uint32_t-cstdint}
BUILD-009: {kind: gap,  name: mkdir-before-cp}
BUILD-028: {kind: arch, name: riscv32-arch-map}
```

> **键名一律用 `name`**，包括仓条目——因为提取器产出的就是 `name`（[`schema/requirements.schema.json`](../schema/requirements.schema.json) 里 `name` 是必填，没有 `path` 这个字段）。
> 靶子用 `path` 的话，下面的脚本对着 `v['name']` 取键会直接 `KeyError`。

跑法：

```python
expected = yaml.safe_load(open('coverage/expected.yaml'))
reqs     = json.load(open('out/requirements.json'))['requirements']
index    = {(r['kind'], r['name']) for r in reqs}

hit     = [k for k, v in expected.items() if (v['kind'], v['name']) in index]
missed  = [k for k in expected if k not in hit]
print(f'{len(hit)}/{len(expected)} = {len(hit)/len(expected):.0%}')
```

未命中的逐条人工归类：

| 归类                   | 含义               | 好坏                 |
| ---------------------- | ------------------ | -------------------- |
| (a) 该补一条新提取规则 | 扫描器漏了一类声明 | **最好的结果** |
| (b) 本就无声明来源     | 归知识库 / 白名单  | 可接受               |
| (c) 其实是环境侧问题   | 本就不该扫源码     | 可接受               |
| (d) 只能补特例         | 方法不收敛         | **危险信号**   |

**判据（第 9 节）**：未命中里 (b)(c) 比例越高越好；**大量落到 (d) 就说明这套方法没通过验收**。
