## 23. 实施顺序

**排序原则：先做输入结构化的，后做需要分词的。** 结构化的能做 golden test，分词只能靠 fixture 用例覆盖。

| 阶段          | 内容                                                                      | 依赖   | 在哪验证                |
| ------------- | ------------------------------------------------------------------------- | ------ | ----------------------- |
| **P0**  | 骨架 + config + requirements/findings 格式 + 报告渲染                     | —     | Windows                 |
| **P1**  | fixture 假树 + 测试框架（第 21 节）                                       | P0     | Windows                 |
| **P2**  | **两段预检（`precheck/`：`p_env` + `p_fetch` + `p_base`）** | P0     | **Windows / WSL** |
| **P3**  | 第 0 关 树完整性（`v_tree`）                                            | P1     | Windows                 |
| **P4**  | S2 仓 + S3 部件（确定性最高）                                             | P1     | Windows                 |
| **P5**  | S1 工具（分词器 + 黑名单 + 置信度）                                       | P1     | Windows                 |
| **P6**  | S4 工具链 + S7 配置架构                                                   | P1     | Windows                 |
| **P7**  | S5 库符号 + S6 缺口                                                       | P1     | Windows                 |
| **P8**  | 第 2 关 提取自检（`v_coverage`）                                        | P4–P7 | Windows                 |
| **P9**  | `v_exists` / `v_identity` / `v_consistency` / `v_reach`           | P3–P8 | 需目标环境              |
| **P10** | `knowledge.yaml` 规则化（61 → 规则）                                   | P0     | Windows                 |
| **P11** | **覆盖率实验（第 22 节）**                                          | 全部   | **目标机**      |
| **P12** | 修复段骨架：四档分级 + 收敛判据 + 回滚（**不含 Agent**）            | P9     | Windows / 服务器        |
| **P13** | A 档脚本修复 +`fix_recipe` 进 `knowledge.yaml`                        | P12    | 服务器                  |
| **P14** | **Agent 分诊（每关一次）+ 围栏 + dry-run**                          | P13    | 服务器                  |
| **P15** | B 档`propose_patch` + 人审流程 + **修法写回知识库**               | P14    | 服务器                  |

**P0–P8 全部可在 Windows 上完成并用 fixture 验证。** P9（四个验证器）**必须进目标环境**——`command -v` 的结果取决于当前系统，Windows 上跑没有意义。P10 是知识库整理，回到 Windows；**P11 起才需要服务器**。

到 P11 那一步，**手上已经有一个能跑的完整工具**，只是还没喂过真数据。

**P12 刻意不含 Agent。** 四档分级、收敛判据、回滚——这三样是**纯规则**，能用 fixture 完整测。先让它们跑通、跑对，再把 Agent 接进 P14。**反过来做的话，分诊出错时你分不清是规则错还是模型错。**

### 第一刀切在 P0–P2

顺序反过来了：**先做预检，再做扫描。**

理由有三条，按重要性排：

1. **拦的是最贵的动作。** 预检挡在 `repo sync`（小时级）前面，一次成功拦截就回本。
2. **不需要源码树。** 预检的全部输入是 `config.yaml` + manifest + WSL 环境——**Phase 0 就能验证，不用等 Phase 8**。
3. **它是流水线三段顺序在实施顺序上的投影。** 先做的应该是先跑的（第 7 节）。

对比原来的「第一刀切在 P0–P3」（骨架 + 第 0 关 + S2 + S3）：

|            | P0–P3（旧）                       | **P0–P2（新）**                 |
| ---------- | ---------------------------------- | -------------------------------------- |
| 代码量     | 大（含两个提取器 + 分词器地基）    | **小**                           |
| 需要源码树 | 第 0 关要（虽然可用 fixture 假树） | **完全不要**                     |
| 挡住的动作 | `hb build`                       | **`repo sync` + `hb build`** |
| 覆盖 61 条 | 4 条                               | **22 条**                        |

**用完最少的代码，覆盖最多的条目，挡住最贵的动作。** 这就是第一刀该切的地方。

## 24. 风险与不确定

| #   | 风险                                           | 影响               | 缓解                                                                                                                                                                          |
| --- | ---------------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **S1 假阳性**                            | 报告被淹没，没人看 | 置信度分级 + 黑名单 + 人工 denylist，默认只报 high/medium                                                                                                                     |
| R2  | **S1 假阴性**                            | 漏检               | **承认它**。漏掉的由真实失败补进来（增量模式），不假装完备                                                                                                              |
| R3  | **GN action 指向树内脚本**               | S1 在 GN 上零产出  | 已定为必须递归`script=`（[`03.2` §19.3.5](../src/l2_extract/README.md)）                                                                                                                                           |
| R4  | **S6 全量 include 又贵又和编译器重复**   | 白干               | 已主动缩到只做缺口（[`03.2` §19.6](../src/l2_extract/README.md)）                                                                                                                                                    |
| R5  | **树不完整时扫描结果静默错误**           | 后面全白干         | 第 0 关前置且默认阻断（第 18 节）                                                                                                                                             |
| R6  | **版本约束无声明来源**                   | 覆盖不到           | 只能人工维护`whitelist.yaml`。第 10 节已明确这是**结构性缺口，实现补不了**                                                                                            |
| R7  | 变量追踪做不深（`$CC`、`${VAR}` 层层间接） | 部分需求提取不到   | 标 low 并保留源码片段，**不猜**                                                                                                                                         |
| R8  | `arch_map.yaml` 的值可能与树不符             | 误报               | 落地前对着树核一遍（[`03.2` §19.7](../src/l2_extract/README.md) 已标注）                                                                                                                                             |
| R9  | **预检通过 ≠ 后续一定成功**             | 误以为万事大吉     | **预检是必要条件，不是充分条件**。`BUILD-026` 那类（源码引用 manifest 未声明的仓）**预检物理上看不见**，只能等第 6 关。报告里要写清这道门承诺了什么、没承诺什么 |
| R10 | 预检的**基线工具清单**无声明来源         | 清单过时则漏检     | 本来以为无解，**现已解**：清单来自 `config.yaml`/`whitelist.yaml`，完整覆盖仍靠第 3 关。两条腿不冲突（26.7）                                                        |
| R11 | **Agent 修好了 A、弄坏了 B**             | 越修越坏           | 收敛判据 ②（不允许多出新 finding）+ 不能通过就**回滚本轮全部改动**（28.5）                                                                                             |
| R12 | **Agent 的 patch 语法对、语义错**        | 静默引入错误       | 重扫 / 重验兜底；**默认 dry-run**，人审后才 apply（28.9）                                                                                                               |
| R13 | **修复段把树改脏了、回滚不回去**         | 无法恢复           | 改前快照；**拒绝在已有未提交改动的树上 apply**（28.5）                                                                                                                  |
| R14 | **把一条检查放在错误的层**               | 该拦的没拦住       | 判据是「**现象在哪台机器上出现，就放在哪一层查**」，不是「根因属于哪一类」（[`02` §26.6](02-流水线与关.md)）                                                             |

**R2 和 R6 是方法本身的边界，不是实现缺陷。** 写进文档而不是藏起来。
**R9 是新增的，它防的是「预检过了就放心了」这个误解。**
**R14 是唯一一条「关于编排本身」的风险**——它不是某个检查会算错，而是**检查被放错地方**。`ENV-007` 真被放错过一次：根因是版本（A2 类），现象却在 Windows 侧出现，所以它该在**第 -2 层**查，不在版本那一批里。

**R11–R13 是修复段带来的**，来源不同于前面十条：前十条是**方法**的风险，这三条是**新增能力**的风险。
代价换来的东西是明确的——**从「给你一份报告」变成「修好之后开始编译」**。但这三条不能被忽略：
**它们每一个的失败模式都是「本来只是缺东西，修完变成了坏东西」。**

## 25. 默认选择

| 项         | 选择                                                                 | 理由                                                                                   |
| ---------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 语言       | Python 3，仅标准库                                                   | 15.2                                                                                   |
| 工具形态   | 单个包 + 单一入口`scan.py`                                         | 关卡是有序编排，不是独立工具集                                                         |
| 开发位置   | Windows 上开发 + fixture 自测                                        | 15.1 让提取阶段环境无关                                                                |
| 运行位置   | 三段分工：段一在**Windows 侧**、段二/段三在 目标机 的 WSL 里 | 段一必须 Windows——那时 WSL 还不存在（7.3）；段二的`command -v` 只有 WSL 里才有意义 |
| 部署方式   | 沿用现有模式：bat + plink 调服务器端脚本，不内联复杂逻辑             | `ENV-011` 的教训                                                                     |
| 起步范围   | **P0–P2（骨架 + 探测原语 + 两段预检）**                       | 代码量最小、**不需要源码树**、拦的是最贵的动作（第 23 节）                       |
| 修复默认   | **`--dry-run`**：只出 patch，不自动改源码                    | B 档是整条链上唯一有破坏性的动作（28.9）                                               |
| A 档自动修 | **开**（`--no-fix` 可全关）                                  | 幂等且可验证——装完重跑`command -v` 就有答案                                        |
| 分诊粒度   | **每个关一次 Agent 调用**（约 8 次）                           | 每条一次太贵、全局一次丢上下文（7.2.1）                                                |
| 放弃裁决   | **规则判，Agent 只能建议**                                     | Agent 有「我再试一次」的倾向，而放弃判据必须是硬的（28.2）                             |
